# Step 60 across every family: the three open points, designed

For the owner's review. This is design only: nothing in `plan-approved/` is edited. It answers "Step 60's scope and edge cases (BE to BH)" in `INDEX.md`. Step 60 now covers every rewriting key change within one family, which leaves three gaps. Section 5 covers other things the families raise. Choices go on from BH, so they're lettered BI to BR, and each one has a recommendation.

Everything was tested on throwaway Postgres 18.6 and 17.11 servers in this worktree's `.claude/scratch/`. Both gave the same result in every test, unless a test says otherwise. Postgres 15 and 16 aren't installed here (section 8).

## 1. What "within one family" covers for a key

R-0612's families are integers (`smallint`, `integer`, `bigint`, `numeric(p,0)`), `numeric` for `Decimal`/`Numeric` (any precision and scale, plus the three integer types), `text`/`varchar`, `char` on its own, `timestamptz`, `timestamp`, and arrays of any of these. Step 60 runs only when the change rewrites the table. I measured which changes do by checking whether `relfilenode` changed. Both versions gave the same table:

| Change | Rewrites? |
|---|---|
| `numeric(10,2)` to `numeric(12,2)`, or to unbounded `numeric`; `numeric(10,0)` to `numeric(12,0)` | no |
| `numeric(10,2)` to `numeric(10,3)` or `numeric(9,2)`; `numeric(10,0)` to `bigint` or `numeric(8,0)`; `integer` to `bigint` or `numeric(12,0)` | yes |
| `timestamp(3)` to `timestamp(6)`; `timestamptz(3)` to `timestamptz` | no |
| `timestamp(3)` to `timestamp(1)`; `timestamptz(3)` to `timestamptz(1)` | yes |
| `varchar(5)` to `varchar(9)` or `text`; `varchar(10)` to `text` | no |
| `varchar(5)` to `varchar(2)`; `text` to `varchar(10)` | yes |
| `char(3)` to `char(5)` or `char(2)`, longer included | yes |
| `int[]` to `bigint[]`, `varchar(5)[]` to `varchar(9)[]` or `text[]` | yes, every array change |

So `char` and arrays reach step 60 even when they get longer, and so does any narrowing.

## 2. Gap 1: an identity key leaving the integer types

**What Postgres does:**

- `ALTER COLUMN ... TYPE numeric(20,0)` on an identity column fails with "identity column type must be smallint, integer, or bigint". So does `ADD GENERATED ... AS IDENTITY` on a `numeric` column, which is what step 60's cutover would run, and so does `CREATE TABLE` with a `numeric` identity column. So `--fast` can't do it either.
- `CREATE SEQUENCE ... AS numeric` fails: "sequence type must be smallint, integer, or bigint". No sequence can count past `bigint`'s maximum, so a generated key gains no room by becoming `numeric`.
- A `serial` key changed to `numeric(20,0)` keeps working. The `nextval` default stays, and the sequence stays `integer` with an `integer` maximum. So R-1124's `ALTER SEQUENCE ... AS <new type>` can't follow it.
- A `numeric(5,0)` key with a `nextval` default gets "numeric field overflow" on the insert after its sequence passes 99,999.
- `DROP IDENTITY` keeps the data and drops the sequence. An insert that leaves the key out then fails with `NOT NULL`.

**The options:**

- **A. Generated keys stay in the integer types.** `identity` on a field whose SQL type isn't `smallint`, `integer` or `bigint` is a compile error, because the macro knows the type from `sql` or inference, and scratch's error is the backstop. Step 60 refuses, with exit code `2` at `makemigrations`, a single op that takes a generated key (identity, or `serial` with its owned sequence) out of the integer types while dropping its generation. The fix is two migrations: first drop the identity or default, which changes no rows, then change the type, with no sequence involved.
- **B. Convert the identity into an owned sequence at cutover.** The sequence keeps its name and position as `bigint`, and the key gets `DEFAULT nextval(...)` and `OWNED BY`. That needs new model syntax for "a generated `numeric` key". It also loses `GENERATED ALWAYS`, because a default can be overridden. And it gains nothing, because values still can't pass `bigint`.
- **C. Refuse every change that takes a generated key out of the integer types, with no path.** It's simpler, but it blocks a legitimate case: ids that the app supplies itself and that are going `u64` on `numeric(20,0)`.

**Recommend A.** It matches Postgres's own limit, needs no new syntax, and leaves a clear path. Within the integer types, R-1124 stays as written. When a `serial` key moves between integer types, `ALTER SEQUENCE AS` applies only when the new type is an integer type.

**BI. Identity keys leaving the integer types:** A, B or C. Recommend A.

**Two related gaps that A sends developers through.** Both are outside step 60, but they need closing.

- **Adding identity to a populated column starts at 1.** I tested `ADD GENERATED BY DEFAULT AS IDENTITY` on a column holding 1 and 2: the next insert got "duplicate key value violates unique constraint", with key 1. Going back from `numeric(p,0)` to an identity `bigint` lands here.
- **Dropping identity under a running app.** A build that leaves the identity column out of its inserts (R-0352) fails every insert once identity is gone.

**BJ. Identity added or dropped on its own:**

- *A (recommend):* adding identity to a table with rows also runs `setval` on the new sequence to the column's highest value, in the same transaction. R-0612's insert check counts a lost identity as a lost default, so that build is refused at pool start (R-1116).
- *B:* refuse adding identity to a populated column.
- *C:* leave both as they are. That isn't acceptable, because inserts fail at runtime.

## 3. Gap 2: a key change that changes stored values

These are R-1108's silent narrowings on a key: a lower scale, a lower timestamp precision, or a shorter length that drops trailing spaces. `char(4)` to `char(3)` changes no value, because Postgres compares `char` without its padding.

**What Postgres does:**

- **Step 60's check can never pass.** With `numeric(20,4)` going to `numeric(20,2)` on 200,000 rows, `CHECK (new IS NOT NULL AND new = old)` failed `VALIDATE`.
- **The cast form passes, and keeps the no-scan `NOT NULL`.** `CHECK (new IS NOT NULL AND new = CAST(old AS numeric(20,2)))` validated on the key table and on the referencing table. The new foreign key between the two rounded shadow columns validated. `SET NOT NULL` logged "existing constraints ... are sufficient to prove that it does not contain nulls", and `ADD PRIMARY KEY USING INDEX` worked.
- **Referencing values change consistently.** The cast is deterministic on the value, so a key and its references round alike. Under load (below), no row was orphaned and no value disagreed.
- **Two keys can merge.** `1.0051` and `1.0149` both become `1.01`. `CREATE UNIQUE INDEX CONCURRENTLY` then fails with "Key (id_new)=(1.01) is duplicated" and leaves the index invalid. `timestamp` to `timestamp(3)` merged `.123456` with `.123`. `varchar(10)` to `varchar(3)` merged `'abc  '` with `'abc'`. `--fast` fails the same way.
- **`--fast` can't change the columns with the foreign key in place.** Changing the referencing column first fails its foreign key against the old key, and so does changing the key first ("Key (pid)=(1.0051) is not present"). Dropping the foreign keys, changing every column and adding them back worked in one transaction. `integer` to `numeric(20,0)` hits the same wall for another reason: the old foreign key "cannot be implemented: numeric and integer", because those two are in different operator families. `integer` to `bigint` needs none of this.

**A live run on both versions.** The key table had 300,000 rows of `numeric(20,4)` primary keys, each ending `.0051`. The referencing table had 400,000 `NOT NULL` references with `ON DELETE CASCADE`. I ran steps 1 to 6 and the cutover by hand, with the cast check and the key table locked first. `pgbench` ran 8 clients nonstop with a new-shape load, writing 2-decimal keys:

- insert a parent and a child
- delete by key range, which cascades
- update a parent, then read its children
- move a child to another parent
- a join

| | 18.6 | 17.11 |
|---|---|---|
| Transactions, failed | 89,098, 0 | 74,116, 0 |
| Copy batches (bounded) | 61 and 81 | 61 and 81 |
| Cutover attempt, locks held | 3, 8.3 ms | 2, 7.0 ms |
| Orphans after | 0 | 0 |
| Parents whose new key isn't the old key rounded | 0 | 0 |
| Children whose key differs from the retired one | 57,568, every one moved to another parent after the cutover | 48,580, likewise |
| End state | `numeric(20,2)` key and reference, `parent_pkey` and `child_pid_fkey` on the new columns, no trigger left | same |

**The options:**

- **A. Refuse it on a key, online and under `--fast`.** The developer would have to drop the foreign keys by hand.
- **B. Run it online, in `contract`, with these rules:**
  - Step 4's check becomes `new IS NOT DISTINCT FROM CAST(old AS <new type>)`, with `new IS NOT NULL AND` in front for a `NOT NULL` column. That's one rule for every change, because arrays need it too (section 5).
  - Preflight refuses, with exit code `2`, any key values that would merge, naming the values. There's one `GROUP BY` per key, built from the new type. No answer can make two keys one.
  - Every referencing column must take exactly the key's new type, or `makemigrations` refuses with exit code `2`. A reference left at the old scale would no longer match its key.
  - R-1111's `lossy` decision, and the live count from R-1113 and R-1115, are worded for a key. They name every referencing column, and say that the key's values change in every table with them. They also say that copies held outside the database (caches, URLs, other services, logs, exports) keep the old values and won't match.
  - R-1108's hold for `contract` applies unchanged.
  - Under `--fast`, see choice BL.
- **C. Allow it only under `--fast`.** It would be correct, but it takes a full lock on every table in the group, when the online form works (tested above).

**Recommend B.** It reuses the whole step 60 form, the check proves the cast's value exactly, and the only real hazards are refused or asked about up front. One more rule comes with it. During the window, a write that collides only after rounding fails on the shadow unique index. In `contract`, apps are built for the narrow shape, and R-0424 stops them writing extra decimals, so this is rare. The error still has to read right, so R-0434's `Error::Unique` maps the shadow index's name to the key's field.

**BK. A key change that changes values:** A, B or C. Recommend B.

**BL. `--fast` when the foreign keys block the change** (values change, or the operator family changes, as with `integer` to `numeric`):

- *A (recommend):* in the one transaction, drop the group's foreign keys, change every column, then add them back with the same names, actions, `MATCH` type and deferrability, validated under the lock already held. `max_rewrite_mb` applies per table, as R-1126 says.
- *B:* refuse `--fast` for these, so they run only online.

## 4. Gap 3: checking that a value fits the old type, outside integers

This applies wherever step 60 narrows a key: R-1127's inverse, a narrowing migration, or `rollback`. It only covers narrowings that raise a real error, because silent ones are gap 2. It also covers writes the old type can't hold, before, during and after the cutover.

**What Postgres does.** A write's assignment cast is the authority. `ALTER COLUMN TYPE`, `UPDATE ... SET` and a plpgsql trigger's `NEW.x := NEW.y` all use it.

- An assignment of `'abcd'` to `varchar(3)` fails with `22001`. An explicit `CAST('abcd' AS varchar(3))` silently gives `'abc'`, so a check can't rely on the explicit cast to raise errors.
- I compared 40 value-and-type pairs against a predicate built from the two `format_type` texts, as R-1113 does. The pairs covered:
  - numeric overflow after rounding (`99.995` into `numeric(4,2)`)
  - negative scale
  - `NaN` and `Infinity`
  - `numeric` into `integer` or `bigint` at the edges (`2147483647.50`)
  - `bigint` into `numeric(5,0)`
  - trailing spaces, tabs, newlines, non-breaking spaces and multibyte text into `varchar(3)` and `char(3)`
  - timestamps at the top of the range
  - one- and two-dimensional arrays

  These are the predicates:

  | New type | Misfit when |
  |---|---|
  | `numeric(p,s)` | `v <> 'NaN' AND (abs(round(v,s)) >= 10^(p-s) OR v in ±Infinity)` |
  | an integer type | `NaN`, `±Infinity`, or `round(v)` outside its range |
  | `numeric(p,0)` from an integer | `abs(v) >= 10^p` |
  | `varchar(n)` or `char(n)` | `length(rtrim(v, ' ')) > n` |
  | a lower timestamp precision | never (it rounds, it never errors) |
  | an array | any element, through `unnest` |

  On both versions, all 40 agreed with the assignment cast.
- My first `numeric` predicate left out the `NaN` guard. It disagreed on `NaN` (on 18.6), because Postgres sorts `NaN` above every number, while `NaN` fits `numeric(4,2)`. Hand-built predicates are easy to get wrong, so they need a test that pins them.
- Timestamp precision never errors, even at the top of the range: `294276-12-31 23:59:59.999999` rounded up to `294277-01-01 00:00:00` with no error.
- A writer's assignment through the sync trigger raised `22001` "value too long for type character varying(3)", naming the shadow type.

**The options:**

- **A. Predicates built from `format_type`, as R-1113 builds its counts:**
  - Preflight runs one `SELECT count(*), min(v)` per column, read-only, with no `statement_timeout`, and refuses with exit code `2`, naming the table, the column, an example value and the count.
  - The copy step runs the same check again once its sync trigger has committed. That catches a row written between preflight and the trigger, and stops with the same message rather than a raw error mid-copy. `rollback --failed` then drops the shadow objects.
  - From then on, the trigger's assignment fails a write that doesn't fit, which is R-1127's rule applied from the first step. After the cutover, the column is the narrow type, so the database's error applies (R-0612).
  - A sequence behind a `nextval` default on a `numeric(p,0)` key gets the check identity gets: its position against `10^(p-s)` at preflight, and again under the cutover's lock.
  - A test obligation runs the table above on Postgres 15–18 against the assignment cast, so a wrong predicate fails CI.
- **B. `pg_input_is_valid(v::text, '<new type>')`.** It doesn't exist on Postgres 15, so it can't be one rule across the supported versions.
- **C. A `pg_temp` plpgsql loop that assigns each value.** It's exact by construction, but it reads row by row in one backend, with no parallel scan, and needs the `TEMP` privilege. That's slower than A's single parallel count, which R-1113 measured at 0.31 s on 10 million rows.

**Recommend A.** It's the same shape as R-1113's counts, it's fast, and the CI table proves it against Postgres. The sync trigger and the copy are exact backstops, so a predicate bug can only cause a stop that `rollback --failed` cleans up, never wrong data.

**BM. How the fit check works outside integers:** A, B or C. Recommend A.

## 5. Other things the families raise

**Collation.**

- **The check needs a stated collation.** A shadow column whose collation differs from the old column's failed `VALIDATE` with "could not determine which collation to use for string comparison", with and without `CAST`. The check writes `COLLATE "<new column's collation>"` on the cast side.
- **`ALTER COLUMN TYPE` with no `COLLATE` resets the collation to the default.** I tested this with `"C"` to `varchar(3)` and with a nondeterministic collation to `text`. This affects every in-place and `--fast` change morm writes, not just keys, so morm must always restate `COLLATE`.
- **Postgres refuses some foreign keys across collations.** With a nondeterministic collation on either side, a foreign key between different collations "cannot be implemented ... both collations have to be the same".
- **A collation change can merge keys.** Changing a key from `"C"` to a case-insensitive collation failed on duplicates (`'abc'` and `'ABC'`).
- **A collation change alone rewrites the indexes.** It left the table's file alone but rebuilt the key's index, under `ACCESS EXCLUSIVE`. The plan has no online form for a collation-only change.

**BN. Collation on keys:**

- *A (recommend):* the check and every `ALTER ... TYPE` name the collation. A collation change on a key goes through step 60 when both collations are deterministic, where equality is byte equality, so nothing merges. With a nondeterministic collation on either side, it's refused online with exit code `2`, naming both collations, and `--fast` handles it, where a merge fails loudly on the unique index. A collation change alone on any column uses the online swap like a rewriting change, because it rebuilds every index on that column under the lock.
- *B:* refuse every collation change on a key online.

**Referencing columns of another operator family.** Postgres allows a `bigint` reference to a `numeric(20,0)` key, but it compares through a cast. Deleting 10 parents took 683 ms (668 on 17.11) against 2 ms with matching types, because the reference's index can't be used: the plan showed `Parallel Seq Scan ... Filter: ((pid)::numeric = ...)`. The reverse, `numeric` to `integer`, is refused by Postgres.

**BO. Mixed types in a group:**

- *A (recommend):* `makemigrations` refuses, with exit code `2`, a group where a referencing column's new type is in a different btree operator family from the key's new type, naming both columns. When values change, every reference must also be the key's exact new type (gap 2). Within one family, a reference that keeps its type is fine (tested: an `integer` key going `bigint` with a `bigint` reference), and step 5's new foreign key starts from that column itself.
- *B:* allow it with a warning.

**`timestamp` and `timestamptz`.** These stay separate families, so a key change between them keeps R-0567's refusal online. Under `--fast`, Postgres converts each value with the session's `TimeZone`. The same stored `12:00` became `12:00` UTC under `UTC` and `17:00` UTC under `America/New_York`. Mid-change, a `timestamptz` reference to a `timestamp` key was accepted, and its matches changed with the session zone (one insert passed under `UTC` and failed under `Asia/Dhaka`). In one transaction the key and its references move together, but the result still depends on where the migration ran. This applies to any column, not just keys.

**BP. The zone for `timestamp` and `timestamptz` changes:**

- *A (recommend):* `makemigrations` opens a decision asking which zone the stored values are in, and writes `USING col AT TIME ZONE '<zone>'` on every column it changes, so the result doesn't depend on the session.
- *B:* morm pins `TimeZone = 'UTC'` in migration sessions.
- *C:* leave it. That isn't acceptable, because the same migration would give different data on different hosts.

**`char(n)`.** Every length change rewrites the table. Equality ignores padding, so the cast check passes (`char(3)` to `char(5)`: 3 bytes became 5, still equal). Shortening changes no value. No change is needed beyond the cast check.

**Arrays.** `new = old` fails on `int[]` to `bigint[]` with "operator does not exist: bigint[] = integer[]". The cast form validates, the no-scan `NOT NULL` still works, and a foreign key between array shadow columns validates. Every array change rewrites (section 1), so R-1121's "needs no rewrite" examples never apply to arrays. With the cast check, no change is needed beyond it.

**Domains.** R-1125 already refuses domain keys online. A change from one domain to another is across families under R-0612, and `--fast` worked (domain over `integer` to domain over `bigint`) with choice BL's drop and re-add. No change is needed.

**Operator classes.** Step 60 builds each shadow index from scratch's text, so an `ops` that doesn't fit the new type fails on scratch ("operator class int4_ops does not accept data type bigint"). Under `--fast`, `ALTER TYPE` silently swapped an explicit `int4_ops` for the default class, and kept `varchar_pattern_ops` on `text`. So the result can differ from the models with no error.

**BQ. Indexes after `--fast`:**

- *A (recommend):* after `ALTER TYPE`, `--fast` compares each index on the group's columns with scratch's definition, and recreates any that differ, in the same transaction. The scratch error names the index and its `ops`.
- *B:* refuse `--fast` when a group column has an index with an explicit `ops`.

**Every refusal gets a README notice.** Every refusal, choice or rule above that stops a developer exits with code `2`, or `3` for a decision, and gets a loud README notice (section 6).

**BR. The README notices in section 6:** accept them as listed, or change them.

## 6. README notices these need

Each notice is loud, beside the step 60 notice (R-1129). It says what is refused, why, and how to go on.

1. **Generated keys stay in the integer types (BI, BJ).** Postgres allows identity, and sequences, only on `smallint`, `integer` and `bigint`, so a generated key gains nothing as `numeric`. To get there anyway, use two migrations: drop the identity (inserts must then supply ids, and a build that leaves the id out is refused at pool start), then change the type. Adding identity back sets its sequence past the highest key.
2. **Key values that would change (BK).** It's held for `contract` and asks a `lossy` decision with a count of the rows that change. It's refused if two keys would merge, naming them. Every referencing column changes with the key, and copies of the key outside the database won't match.
3. **A narrowed key that doesn't fit (BM).** It's refused, naming a value and the count. From the migration's first step until it's done, a write the narrow type can't hold fails with the database's error. A row that arrives before the trigger stops the copy, and `rollback --failed` cleans up.
4. **Mixed reference types (BO).** It's refused, naming both columns, because the foreign key would scan the referencing table on every delete (683 ms against 2 ms in the test).
5. **Collation (BN).** A nondeterministic collation change on a key is refused online, with `--fast` as the way through.
6. **Time zones (BP).** A `timestamp` to `timestamptz` change asks which zone the values are in, and why.
7. **`--fast` on a key (BL, BQ).** It drops and re-adds the group's foreign keys, and rebuilds indexes that `ALTER TYPE` changed, under the one lock.

## 8. What I couldn't settle

- **Postgres 15 and 16 weren't run,** because only 17.11 and 18.6 are installed. Everything here has been in Postgres since 12 or earlier, apart from negative `numeric` scale, which needs 15. Step 60's CI runs 15–18, and a different result means stop and ask.
- **Each live run was a single short run** per version, with no fault injection. Step 60's T-0230 and T-0231 cover those.
- **Nondeterministic collations were tested with one ICU collation.** BN refuses them online, so the online form never relies on their behaviour.
