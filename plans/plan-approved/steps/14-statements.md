## Goal

The two bounded caches, shape tracking, `query_typed` fallback, fragment renumbering and the error mapping every query uses.

## Deliverables

A load test with random and repeated shapes shows fixed statements staying cached, and a change to a table's result type or an enum type swap recovers outside a transaction.

### Models / Type inference

- **R-0208** **NUL bytes:** Postgres rejects `\0` in text. morm doesn't scan every string for it, which would cost time on every write; Postgres's error becomes a typed `InvalidText`.

### Reading and writing / Query safety

- **R-0433** **`$n` in a fragment is local.** `comp`, `set_expr` and `.q()` fragments each count from `$1`, and morm renumbers them. The scan skips quoted strings and comments, so `'$1'` stays text. The scanner lives in `morm-core`, and it writes each parameter's cast, as `($n::type)`.
- **R-1221** **The scanner places the casts.** It follows Postgres's `scan.l` for everything that can hide a `$n`: standard strings with `''`, escape strings `E'..'` with backslashes, and `B'..'`, `X'..'`, `N'..'` and `U&'..'`; quoted identifiers with `""`, and `U&".."`; `--` comments and nested `/* */` comments; dollar quotes `$$..$$` and `$tag$..$tag$`; identifiers that hold `$`, such as `a$1`; and operator splitting, including the rule on a trailing `+` or `-`. It refuses an unterminated quote or comment. In the pass that renumbers each `$n`, it writes the cast for that parameter's slot: the column's cast for a value bound through a field, as in `comp` (choice G), and each value's own `Param` cast for a free one, in `set_expr`, `.q()`, `q_unchecked` and `sql_unchecked`. So `price < $1 AND tag = '$1' AND x = ANY($2) -- $1`, numbered from 3, becomes `price < ($3::numeric) AND tag = '$1' AND x = ANY(($4::text[])) -- $1`. A call site's value types are fixed, so its casts are too, and the scanner runs once per shape. Owner decision DH2, choice F.
- **R-0434** Typed errors: `Unique { constraint, field }`, `ForeignKey`, `NotNull`, `Check`, `Serialization`, `Deadlock`, `LockTimeout`, `TransactionTimeout`, `TransactionAborted`, `CommitUnknown`, `NestedConnection`, `PoolerMode`, `NotFound`, `EmptyPatch`, `Conflict`, `Forbidden`, `Validation`, `PoolBusy`, `ConnectionLost`, `ReadOnly`, `OutOfRange`, `InvalidText`, `InvalidOrder`, `InvalidCursor`, `Decimal`. `Unique`'s `field` maps a unique index named `_morm_new_<name>`, made from a unique index's name `<name>` through the 63-byte name function, to the field it maps `<name>` to, because while an online swap in step 39, 52 or 60 changes a column, or step 39 rebuilds an index concurrently after a type change, a write can collide on that shadow index alone, such as one whose value equals another only once rounded, or an enum label a map turns into one another row holds.

- **R-0625** **Statement caches:** two bounded LRUs on each connection, below.

### Performance and memory / Statements

- **R-0703** Two bounded LRUs per connection. Evicted statements are closed when dropped, which also frees Postgres memory.

| ID | Setting | Default | Holds |
|---|---|---|---|
| R-0704 | `statement_cache` | 256 | SQL fixed at compile time: `get` and `delete` by primary key, a model's static `insert`, `sql!`, `db.sql()` and `db.raw()` |
| R-0705 | `shape_cache` | 128 | SQL put together at runtime: `select` builders including `filter_cols` and `.q()`, `get_by`, `get_where`, `get_q`, `delete_by`, `delete_where`, `delete_q`, inserts with defaulted fields, `update`, `update_q`, `.apply()`, and any query with a `.tag()` |

- **R-0706** **Why two:** each combination of columns is different SQL text, so a 10-field patch has up to 1,023 shapes, and a client chooses which one it sends. morm can't tell a fixed `.set()` chain from a conditional one, so the split is by how the SQL is made. A fixed chain is one busy shape and stays cached.
- **R-0707** **A shape is prepared the second time it's seen.** Its first use runs through `query_typed`, in one round trip, with no cache entry. A small fixed table of shape hashes per connection records what has been seen, and a collision only prepares a shape one use early.
- **R-0708** `.limit(n)` is always a bound parameter, so a client's page size can't create new shapes.
- **R-0709** **Worst case:** random one-off shapes are never prepared and evict nothing. A client repeating hundreds of shapes can churn `shape_cache`, but it can't touch `statement_cache`.
- **R-0711** **Query tags:** `.tag("orders.list")` adds a fixed comment, `/* orders.list */`, so server logs, `auto_explain` and `pg_stat_activity` show which code ran a query. It costs nothing unless used.
- **R-0712** It takes only `&'static str`, so it can't hold a request id, which would make every query text unique. Characters outside letters, digits, `.`, `_`, `:` and `-` become `_`, so a tag can't close the comment.
- **R-0713** One tag is one extra statement: the same SQL under two tags is prepared twice.
- **R-0714** `pg_stat_statements` ignores comments, so those two calls merge into one entry showing the first tag seen. Use logs for tags, and `pg_stat_statements` for totals per query.
- **R-0715** Built SQL text is kept in a small bounded map keyed by model and column bitmask, so a repeated shape doesn't rebuild the string.
- **R-0716** Other dynamic SQL and overflow go through `query_typed`, which needs no prepare round trips. It needs each parameter's Postgres type, and `ToSql` doesn't give that, so parameters are `&dyn morm::Param`, a trait that adds the cast and the built-in carrier. Builder code knows both from `F`.
- **R-1220** **Every parameter has a built-in carrier and a cast.** Every statement morm sends declares each parameter in Parse as its built-in carrier and casts it in the SQL as `($n::cast)`, so Postgres never infers a parameter's type: in `sql!`, every builder, model inserts and updates, `UNNEST`, keyset pages, runtime fragments, `.limit(n)` and morm's own advisory locks, the last two as `int8`. The parentheses are needed: without them, `$1[1]` would become `$1::int8[][1]`, which Postgres reads as the type `int8[][1]` and so returns the whole array, and `$1.n` would fail with `0A000`. A non-built-in type is cast by name, so no OID is looked up or sent. Built text is cached, in R-0715's map and in `shape_cache`, with its casts, and nothing about typing costs a round trip. Owner decision DH2, choices A and C.
- **R-1104** **Decoding follows the column's real type.** When a statement is prepared, morm reads each result column's type from the row description Postgres returns, chooses each field's decoder from it once, and keeps that choice with the statement in its cache entry. A `query_typed` call, which has no cache entry, chooses once from its own result's row description. The internal query entry point then reads all of that statement's rows through `from_row` when every column has the type the binary was built against, so that path is unchanged, and through `from_row_as` with the statement's choice otherwise, deciding once before the first row and never per row. A re-prepare after a migration, on `0A000` as R-0718 says, chooses again, so a statement cached before a cutover picks the new column type's decoder. Every statement is prepared with each parameter's built-in carrier, as `query_typed` sends it. Its SQL casts the parameter to the column type the binary was built against where it's bound through a field, and otherwise to the value's own type. So Postgres converts it when it's written: a widened column takes every value the binary writes, and a value a narrowed one can't hold gets the database's error for that write.

### Managed enums

**R-1245** **The stale-session signals, recognised in any language.** `lc_messages` translates every message but an `elog`'s, and a server set to another language sends that language to every client, so morm reads no translated text. It knows each signal by something that doesn't change with the language: the SQLSTATE, the routine field, which Postgres never translates, an identifier in the message, which is never translated either, or the message of an `elog`, which is always English. R-1270's machine sorts the signals into two classes by what cures them, which is all it needs to know. On Postgres 15 to 18:

| Any other error from a cached statement that casts a parameter to a non-built-in type, outside a transaction (choice I) | none | statement | a fresh statement, when it's stale | Yes: every ordinary error, such as `23505` |

| A lost connection, SQLSTATE class `08`, `40`, `53` or `57`, `55P03`, or `25P02` | the connection, or the SQLSTATE | not a signal; as a fresh run's outcome it neither confirms nor fails | | A timeout can be; `25P02` comes from the app's own transaction on a `db.hold()` connection |

**A confirmation** is a fresh run of the same statement text with the same parameter bytes, where the cached statement or the old connection failed, that succeeds, with or without rows, as an `INSERT`, `UPDATE` or `CALL` that returns only its command tag does, or that ends in a server error other than the first one and off the no-confirm list. The no-confirm list is the outcomes that can end a statement before it reaches the conversion: a lost connection, SQLSTATE class `08` (connection), `40` (a deadlock or serialization failure, a standby's recovery conflict among them), `53` (insufficient resources) or `57` (operator intervention, a statement timeout, a cancel or an admin shutdown among them), `55P03` (lock timeout), and `25P02` (a statement in a failed transaction, which never ran: a fresh run on a `db.hold()` connection inside a transaction the app opened itself gets it, and its row returns the original error, as R-1270 says). A fresh run that ends in the same error fails; one that ends on the no-confirm list neither confirms nor fails, and requests nothing. Three signals count as confirmed on their own, because what cures them cures them for certain: `0A000`, which a fresh statement cures; and, on an old connection that R-0981 replaces, `42804` and a session-class `XX000` `cache lookup failed for type`, from a fresh run or from a statement that isn't cached, such as a write whose trigger raises it, which a new session cures. The last two request *replace* once, at the failure, and the run on the new connection that follows requests nothing more, even when it confirms. A `0A000` requests *clear*, or *salt* behind PgBouncer, once, at the failure, outside a transaction and inside one alike, and inside one the confirming run of the pending entry it made requests nothing more, even when it confirms. So one failure never asks twice, and the same holds for row B2's `XX000` from a cached statement: its confirming run requests *replace* when the old connection was discarded, in place of *clear*, as R-1270 says. No other signal requests a pool-wide action without a confirmation.

An English message is a second signal for `0A000`, `cached plan must not change result type`, and for `42804`, `type of parameter ... does not match that when preparing the plan`, so a version that renames a routine still works on an English server. T-0151 and T-0152 assert each routine on every version, so a new major version runs them first, and a unit test feeds the matcher every row, the third `42804` routine among them. A miss is never silent: the error reaches the app as `Error::Postgres`. Postgres 18 also raises the `0A000` message from `sql_postrewrite_callback`, for a SQL function whose body starts or stops returning a row type; that isn't a stale statement, and it isn't treated as one. The recovery-conflict routine differs by version, so nothing here reads it. Owner decisions SC, SF, choice I, EF1, EH2, EJ6, EK4, MB, `0A000` requesting a repair once, and held connections never reading `<n>` for a request.

**R-1270** **The stale-session machine is one pure module.** Every stale-statement and stale-session rule of this step and of step 20 is one state machine, built as one module of `morm`, such as `stale.rs`, with no I/O. It holds the pool's stale-session state, below, and its functions take a signal, the call's context (straight to Postgres or behind PgBouncer, inside a transaction or not, inside a `tx.transaction(..)` savepoint or not, on a held connection or not, from a cached statement or a fresh run) and the clock, and return a decision: answer with a fresh run, replace the connection, discard it, retry on the same connection, retry on another connection, return `Error::SchemaChanged`, or return the error as it is, with any pool-wide action to request. The pool and connection code carries the decisions out, and step 20's simulation drives this same module, so it tests the code that ships. The machine keeps two things apart:

- **Every call is repaired locally, always.** A stale statement gets one fresh run of the same call. A stale session straight to Postgres gets the call retried on a newly opened connection that takes the old one's slot. Inside a transaction the call returns `Error::SchemaChanged`, which fails the whole transaction, inside `tx.transaction(..)`'s savepoint too, and `.retry(n)`'s later attempts run every statement unnamed, on a newly opened connection when the old one was discarded; a stale session's error it returns as it is inside a savepoint, row B4's, is a Postgres error the savepoint clears. Nothing about the window, the epoch or a table changes what one call returns, beyond what its row says.
- **Every pool-wide action passes one gate,** R-0982's: clearing every connection's statement caches, adding a salt behind PgBouncer, and replacing every connection, each at most once per pool per `stale_cooldown`, plus once per migration.

The rows are R-0718's (the statement class, both modes), R-0981's (the session class straight to Postgres, the parameter test and the transient `XX000`), R-1246's (the session class behind PgBouncer) and R-0982's (the gate and the events). This step builds the state, the rows outside a transaction, A and C, and the events, E; step 20 adds the rows inside one, B and D, which this step's requirements state so the machine is written once.

Per connection: the time it was opened, the two generations it last saw, and, on a `db.hold()` connection, whether it's marked for replacement on release. A cached statement carries nothing extra: while a pending entry exists its statement runs unnamed on every connection, so no connection's copy needs comparing with the entry, and a connection behind the statement or connection generation clears both caches before its next cached run, so a run that follows a pool-wide action never uses a copy that action was taken to clear, even when its connection was checked out before it. There are no per-statement records straight to Postgres: one epoch decides which connections may be stale, and no table a client can fill decides whether a connection is replaced.

Each call's context carries the savepoint bit: whether the call runs inside a `tx.transaction(..)` savepoint, at any depth, set by the transaction as it makes the call, read with no lock and never pool state. Per transaction, the call carries two things of its own, not pool state, read and set with no lock: whether an earlier attempt of its `.retry(n)` returned `Error::SchemaChanged`, after which every later attempt, whatever ended the one before it, runs each of its statements unnamed, through `query_typed`, in both modes, cached statements included, and prepares none of them; and row B2's or B3's mark on its next attempt, from `expect_confirm`.

**Steps and the stale lock.** The procedure below, with the five things listed after this paragraph that run with no lock, is the only code that reads or changes the pool's stale-session state, and it changes it only in steps, apart from the starting bit a checkout's compare-and-swap sets. A **step** is a stretch of one call's machine work with no I/O in it; the I/O points are the lines marked `# I/O`: a read of `<n>`, a run of the call, a rollback of the call's whole transaction, and a connection's open or close. Every step runs under the pool's stale lock, held for that step alone and never across I/O or an `.await`, so steps of different calls never interleave, and while one call waits on I/O, other calls' steps run. Each `# I/O` line ends a step and what follows it starts the next, so `arrive` and everything after it up to the call's next I/O is one step: `on_moved`, `old`, `entry`, `request` with its `take` or `set_due`, and `expect_confirm`. So is a confirming run's outcome, and so is `finish_take` after a checkout's take: a checkout's compare-and-swap only starts the take, and `finish_take` does all of it in one step, a *salt*'s fresh salt, then the raised generation, then the window. A statement generation is raised only after the marker it's raised for is set, in the same step, so no connection clears its caches for an action or an adoption before the text it moves to exists. Every begun take a step finishes, a checkout's whose compare-and-swap landed during the step included, is taken under the last-read `<n>` that step started with, while a take the step makes for its own request uses the last-read `<n>` as it stands when that take is made, after any move the step has made, so a take a checkout begins while a step that moves `<n>` runs counts as begun before the move, and the move's own request is judged against the window that take started and taken under the new `<n>`. The lock is taken only on the stale-session paths: a signal's handling, a read of `<n>` and what follows it, a confirming run's outcome, and the one checkout that takes a due action; a call that meets no stale signal and isn't a confirming run never takes it. A step tests the state as it finds it: the gate by the pool's last-read `<n>` and the window, `old` by the last-read `<n>` and the epoch, and the entries and the cool-down by their tables. Across its I/O a call carries only its own: its signal, whether its read counted as moved, the pending entry its run found, the epoch its test used, and in a transaction whether its attempt is retried.

Five things run with no lock, outside steps:

- **A read's ticket,** one atomic add when the read is sent.
- **The pending check** before a cached run: one acquire read of the generation word, which holds the entry count beside the two generations, so the same read tells whether the connection is behind either generation, which clears both its caches before the run, as a checkout would, and whether any entry exists; while one does, the lookup below.
- **A prepare's read of the marker,** behind PgBouncer with the caches on, when a cached run prepares its statement, after the pending check's read of the generation word: a step writes the marker as a sequence lock, making the sequence word odd, then a release fence, then storing the `<n>` and salt words, atomics stored relaxed, then making the sequence word even with a release store, and the prepare reads the sequence, an acquire read, then the two words, relaxed, then the sequence again after an acquire fence, and reads again if it was odd or changed, so it gets a whole marker some step wrote, whatever generation it read.
- **A pending entry's lookup,** while the pending check's read found the entry count above zero: a scan of the pending array's slots for the text's hash, each slot read as the marker is, its sequence word with acquire, its three words relaxed, an acquire fence and its sequence word again, reading that slot again if the sequence was odd or changed, so it gets each slot whole as a step left it, never one slot's key with another state's bytes or bits. Steps write a slot as they write the marker: sequence odd, a release fence, the three words, sequence even with release.
- **A checkout,** R-0982's: one acquire read of the generation word; while an action is due and the starting bit is clear, one acquire read of the window's end too; and once that window has ended, one acquire-release compare-and-swap that sets the starting bit and changes nothing else, so two checkouts can't both take the due action. The checkout whose compare-and-swap succeeds then runs `finish_take` as one step, which takes the action.

**Why no other interleaving matters.**

- **Steps don't interleave,** so each finds and leaves the state whole. Requests made at once are judged one after another, and each finds the window the one before it started. An epoch is tested and started in the step that applies its read, or inside a savepoint in the failure's own step, with no read, always by the last-read `<n>`, so no call starts an epoch under an `<n>` older than one another call's read has applied.
- **A ticket's add needs no lock.** The counter only rises, and `arrive` compares a read's ticket with the horizon in the step that applies it, so a read whose ticket is at or above the horizon was sent after the last applied read was applied, and its snapshot is newer than that read's, because every read that can apply runs on a snapshot of its own: outside a transaction, or after the call's whole transaction has rolled back, never in an open transaction or after a rollback to a savepoint, where a REPEATABLE READ or SERIALIZABLE snapshot is still the transaction's own, older than the read; and on a `db.hold()` connection only R-0981's read after a session-class failure, which, when the app opened a transaction there, Postgres has failed, so the read gets `25P02` and applies nothing.
- **The pending check only chooses** between a cached and an unnamed run, and whether to clear the connection's caches first. A run that misses an entry a step has just made, or a generation a step has just raised, counts as one already running when that step ran, and a confirming run's outcome is judged in a step, against the entry as its run found it.
- **A connection that sees a raised generation sees the marker it was raised for.** Every step sets the marker before the acquire-release compare-and-swap that raises the statement generation for it, and the pending check reads the word with acquire before a prepare reads the marker, so the marker that prepare reads is at least as new. A checkout that sees due bits sees the window they wait for, because each window is set in a step before any later step's compare-and-swap sets due bits, and the checkout reads the window's end, acquire, after the word.
- **A checkout changes the state only by its compare-and-swap,** which sets the starting bit only when the generation word is as the checkout read it, with an action due and the starting bit clear, and raises nothing. So until `finish_take` runs, every connection sees the generations as they were and runs or clears as before the action, and no connection prepares under the old marker for a generation raised for a new one. Steps change the word only by compare-and-swap too, and every step that judges the gate or changes the word first runs `finish_take` if it finds the starting bit set, the step that applies a read before `arrive`, and every begun take a step finishes, a checkout's whose compare-and-swap landed during the step included, is taken under the last-read `<n>` the step started with, while a take the step makes for its own request uses the last-read `<n>` as it stands when that take is made, so a begun take is finished under the last-read `<n>` it began under, even when the checkout's compare-and-swap lands after that step's own move of `<n>`. So no step judges the gate against a take that's begun and isn't finished, and a step whose compare-and-swap fails because a checkout's came first runs `finish_take` and judges again, except `on_moved` behind PgBouncer: its adoption takes the place of the due action, so its compare-and-swap clears the starting bit with the due bits, and a checkout whose compare-and-swap landed inside `on_moved` takes nothing, so no salt is taken under the adopted `<n>` beside the adoption.
- **So every pool-wide action,** taken in a step or by a checkout, is taken after the window before it ended or after the last-read `<n>` changed from that window's, as R-0982's bound needs, and every epoch starts after the last one ended or after the last-read `<n>` changed from its own, as R-0981's needs.

**The decision procedure.** `pooled` means behind PgBouncer, `ctx.out` and `call.out` outside a transaction, `ctx.held` a `db.hold()` connection, `ctx.sp` the savepoint bit, `read(conn)` a read of `<n>` on that connection, which returns whether it counted as moved, by the read order below, having called `on_moved` if so, and `several` the state table's servers bit, and `call.retried` that the call runs in an attempt after one of its transaction's that returned `Error::SchemaChanged`. `call.tx` is the call's transaction, and `rollback(call.tx)` rolls the whole of it back, savepoints included, never to a savepoint; after it the transaction is failed, and nothing more is sent on it, as step 20 says for savepoints. A request carries no `<n>`: `unread` says only that its call hasn't read `<n>`, isn't in an open transaction and isn't on a `db.hold()` connection, because a request made while its call's transaction is open, or on a held connection, whose session can be inside a transaction the app opened itself, never reads `<n>`.

**The read order.** A read of `<n>` is a catalog query, so reads of two calls can overlap, and one sent before a migration commits can arrive after one sent after it. So every read takes a ticket when it's sent, and the step that applies it compares that ticket with the horizon. A read sent after the last applied read was applied, its ticket at or above the horizon, is applied: it sets the horizon, moved or not, and in a pool that reaches one server it counts as it is, lowered or not. A read that overlapped the last applied one, its ticket below the horizon, never counts, its `<n>` greater or not: it counts as the last-read `<n>` and applies nothing, so a migration seen only by such a read is learned at the next read that doesn't overlap. Each applied read was sent after the read applied before it was applied, and every read that can apply runs on a snapshot of its own, outside a transaction or after the whole transaction's rollback, never in an open transaction's or after a rollback to a savepoint, and on a held connection only after an error that has failed any transaction the app opened there, so applied reads' snapshots come in order, and in a pool that reaches one server the last-read `<n>` is the `<n>` the database held at the latest applied read's snapshot. A lowered `<n>`, after a restore of a backup, a failover to a replica that lost the last migration, a database dropped and created again, which reads `0`, or a comment set by hand, is adopted by the first read that doesn't overlap, and a read that arrives late never sets the last-read `<n>`, the marker or the epoch back. Everything that consumes a read judges by the last-read `<n>` once the read is applied or refused: `on_moved`, the marker behind PgBouncer, R-0981's epoch test and R-0982's gate.

**A pool that reaches several servers.** A pool can reach more than one server when it's `read_only`, which may stand on standbys behind a host list or a load balancer, or when its host list, in its URL or its `host` field, names more than one host and its `target_session_attrs` isn't `"read-write"`, which finds the one primary; that's R-1289's `servers = "auto"`, the default. `servers = "several"` declares a pool whose one host stands for several servers morm can't see, such as a PgBouncer database entry listing several hosts, a load balancer or a DNS name with several addresses, and `servers = "one"` a pool that reaches one server, whatever `read_only` and its host list say. The state table's servers bit holds which, set when the pool starts. Such servers' `<n>` can differ, as when standbys replay a migration at different times, so in a pool that reaches several servers `<n>` only rises: an applied read moves the last-read `<n>` only when its `<n>` is greater, and a lower one counts as the last-read `<n>`, still setting the horizon. Standbys replaying one migration at different times then give one adoption behind PgBouncer, and straight to Postgres one new epoch and one action through a closed window. Such a pool doesn't adopt a lowered `<n>` until `<n>` passes the old value. Meanwhile a migration raising `<n>` back to a value the pool has read counts as no move, so it's handled as a change made by hand: it starts no epoch, so an epoch in force runs to its end; behind PgBouncer the marker keeps the old `g<n>`; it removes no pending or cool-down entry and lets no action through a closed window; and its stale statements are repaired through the gate within `stale_cooldown` of the first confirmation or `0A000`, and its stale sessions straight to Postgres by R-0981's epoch from `stale_cooldown` after it on, so the bounds step 20 states hold. A process started after the lowering takes it at its pool's start read, which every pool takes as it is. The README says so loudly beside `read_only`, host lists and `servers`, as step 50 says.

**R-0718** **Stale statements: the statement class.** A cached statement can go stale when a schema changes under it, and it then fails every time until it's prepared again. A statement that casts a parameter to a non-built-in type, such as an enum, a domain or a composite, survives a swap of that type made by a migration, because every migration `tx` step ends with a reset that marks every cached plan invalid, so Postgres parses it again and resolves the name again, whether or not it touches a table holding the type. Without that reset, as after a swap made by hand, one that touches no such table, such as `SELECT ($1::st)::text`, gets `XX000` `cache lookup failed for type` once the old type is dropped, or `22P02` naming the old type while it's kept, and while it's kept a label both types share runs on the old type's order with no error, which no retry can see. Each statement-class signal R-1245 lists is handled the same way whether Postgres returns it at prepare or at execute, as it does through PgBouncer. Postgres rolled the failed statement back, so running the call again is safe, and the statement parsed once, so its error comes from a schema change or the data, not a typo.

- **Replace,** outside a transaction. morm opens a new connection as the pool's one momentary extra, within the process's connection budget, which every pool in the process shares; when another replacement holds the extra, with the budget full, or when Postgres refuses the extra open with `53300`, too many connections for the server or for the role, which the budget can't see, it closes the old connection first and opens the new one in its slot. The new connection takes the old one's slot and the old one is closed, whatever that run returns, unless the new connection is lost. - **Discard,** inside a transaction, built in step 20. **R-0982** **The one gate for pool-wide actions.** Three actions reach the whole pool: *clear*, which raises the statement generation, so every connection clears both statement caches at its next checkout; *salt*, behind PgBouncer only, which adds a new random 64-bit salt to the marker, replacing any earlier one, and then raises the statement generation, in that order in one step, as R-1246 says; and *replace*, straight to Postgres only, which raises step 11's connection generation, so every connection is replaced at its next checkout, which clears its caches too. Every pool-wide action, whatever asked for it, a confirmation, `0A000`, `42804` or `XX000`, passes one gate:

- **A request** is judged in the step that makes it, R-1270's, by the pool's last-read `<n>` after any read the request makes itself; a request carries no `<n>` of its own. It's taken now when the window is open, or when the last-read `<n>` differs from the window's, the one the last action or adoption was taken under. Otherwise it's remembered as due, and taken at the first checkout after the window ends; a due *replace* outranks a due *clear*. Straight to Postgres, a request whose call hasn't read `<n>`, made while the window is closed outside a transaction, or after the whole transaction's rollback as row B1's is, and not on a `db.hold()` connection, reads `<n>` on that connection, one catalog read, so a migration's stale state isn't held back there, and a read that counts as moved, by R-1270's read order, is taken as event E1 says; that, R-0981's epoch and the read when the pool starts, R-1270's, are the only reads of `<n>` straight to Postgres. A request made while its call's transaction is open, a confirming run's inside a transaction, never reads, in either mode, because a REPEATABLE READ or SERIALIZABLE transaction's catalog reads see the snapshot of its first statement, which can be older than the pool's last applied read: it's judged by the last-read `<n>`, so when such a run is the first thing in the pool to meet a migration's stale state, its action is due until the window ends or the next read outside a transaction adopts the move, and every connection's stale statements are still cleared within `stale_cooldown` of the first confirmation. A request on a `db.hold()` connection never reads either, for the same reason, because its session can be inside a transaction the app opened, and is judged the same way. Behind PgBouncer a request never reads.
- **The window** starts when an action is taken and ends `stale_cooldown` later; it's closed from its start to its end and open after. Taking an action removes every pending entry and every cool-down entry and starts a window, under the last-read `<n>`; the epoch is kept.
- **The window never changes a call's own outcome.** Inside it or outside it each signal gets its row, a statement-class signal its fresh run and the caller its result; only the pool-wide action waits.
- **A checkout** does one atomic read of the generation word, as it already does: a connection behind the connection generation is replaced, and one behind the statement generation clears both caches. While an action is due it also reads the window's end, and once that window has ended it starts the due action's take with one compare-and-swap that sets R-1270's starting bit and nothing else, so two checkouts can't both take it, and finishes it in one step under R-1270's stale lock, `finish_take`, before any other step judges the gate: a *salt*'s fresh salt, then the raised generation with the due bits cleared, then the window, under the last-read `<n>` the finishing step started with, so a take whose compare-and-swap lands while a step moves `<n>` is taken under the old `<n>`, and the move's own request still passes the closed window. No generation is raised before the marker it's raised for is set, so no connection prepares the old text under a generation raised for a new one.

So a pool takes at most one pool-wide action per `stale_cooldown`, plus one per migration, whatever clients send and however many calls run at once. Every action is taken in a step, the request's own or `finish_take` after a checkout's compare-and-swap, before any other step judges the gate, as R-1270's steps say, and only when the window is open or the last-read `<n>` differs from the window's; so two actions less than `stale_cooldown` apart have between them a change of the last-read `<n>`: a migration, or another change of `<n>` R-1270's read order adopts, such as a lowered `<n>` in a pool that reaches one server, which counts as a migration here. A read that overlapped the last applied read never changes the last-read `<n>`, so a late read lets nothing through; and in a pool that reaches several servers `<n>` only rises, so standbys replaying a migration at different times let one action through for it, and a lowered `<n>` lets none through until `<n>` passes the old value.

- **What it costs.** One catalog read when a pool starts. **R-1262** **The stale-session settings.** Every tunable of the stale-session machine, these four, is a pool setting, set like any other: in `[pool]`, in one `[pools.<name>]`, or by its `MORM_POOL_*` variable for the pool a process opens at startup. Each holds per pool. The retry count and the hash and salt widths are part of the design, not settings. R-1289's `servers` is a pool setting the machine reads too, but it declares what the pool reaches rather than tuning the machine. Each default is the value the machine was designed and simulated with. A duration is written as a string with a unit, as every pool duration is.

| Setting | Default | Governs | Allowed |
|---|---|---|---|
| `stale_cooldown` | `"60s"` | R-0982's window for pool-wide actions; straight to Postgres, the length of R-0981's epoch; behind PgBouncer, how long R-1246's cool-down returns a statement's session-class error at once | `"1s"` to `"10m"`; shorter, `"0s"`, `0` or `"off"` is `Error::Config`, because with no window every request would clear or replace the whole pool, as `wait_timeout` can't be off |
| `stale_cooldown_max` | `64` | how many statements the cool-down holds per pool, behind PgBouncer, the oldest dropped; straight to Postgres it holds nothing | `1` to `4096`; `0` is `Error::Config`, because a cool-down that holds nothing would give a statement hitting a stale server session a retry or a `SchemaChanged` on every call |
| `stale_pending_expiry` | `"60s"` | how long a pending entry, R-0718's, lasts from its creation | `"off"` or `"0s"`, which turn pending entries off, or up to `"10m"`; `0` and `"0"` are bare numbers, refused like every other bare duration |
| `stale_pending_max` | `64` | how many pending entries a pool holds, the oldest dropped | `0` to `4096`; `0` turns pending entries off |

A value outside these bounds, or a duration written as a bare number, stops the pool at start with `Error::Config`, naming the key and the bound it broke, the floor or the ceiling, before any of the app's queries has run. The ceilings keep memory bounded, at most about 200 KB per pool, and keep a misset value from delaying a real stale session's healing for hours. There's no `stale_first_failure_max`: with one epoch per pool there are no first-failure records to bound, and a `stale_first_failure_max` key stops loading with `Error::Config`, naming the key and saying it was removed, in whichever table it's in, `[pool]`, any `[pools.<name>]` or any other, as step 10's config loading says, so a setting copied from an earlier draft of these rules can't seem to work while it does nothing. The values aren't changed at run time. Owner decisions on the tenth review, EO3, EO4, MA and MC.

**R-1289** **The `servers` pool setting.** Each pool says whether it can reach more than one Postgres server, for R-1270's servers bit, with `servers`, a pool setting set like any other: in `[pool]`, in one `[pools.<name>]`, which takes `[pool]`'s value when it sets none, as every pool setting does, or by `MORM_POOL_SERVERS` for the pool a process opens at startup.

| Value | The pool counts as reaching | Use it for |
|---|---|---|
| `"auto"`, the default | several servers when it's `read_only`, or when its host list, in its URL or its `host` field, merged as step 10 says, names more than one host and its `target_session_attrs` isn't `"read-write"`; one server otherwise | every pool whose servers morm can see in its own settings |
| `"several"` | several servers, so `<n>` only rises | a pool whose one host reaches several servers morm can't see: a PgBouncer database entry listing several hosts, which PgBouncer takes in turn by default, a load balancer, or a DNS name with several addresses |
| `"one"` | one server, whatever `read_only` and its host list say, so it follows a lowered `<n>` at its next read that doesn't overlap | a `read_only` pool on a single standby, or a host list whose hosts are one server, such as its IPv4 and IPv6 addresses |

`"one"` is the pool's declaration, and morm takes it: a `read_only` pool, or one with a host list, set to `"one"` follows the one-server read order, with no refusal and no warning at start, because morm can't tell one standby from several. If such a pool does reach several servers whose `<n>` differ, a read that reaches another of them can move `<n>` back and forth, each move counted as a migration's, the cost step 50's README notice beside `read_only` and host lists states. `"several"` on a pool `"auto"` would count as reaching one server gives up following a lowered `<n>`, as R-1270 says for every such pool. Any other value, `"Several"`, `"two"`, an empty string, or a value that isn't a string, such as `true` or `2`, stops loading with `Error::Config`, naming the key and its table, or `MORM_POOL_SERVERS` when the variable set it, and the three allowed values. `servers` is a key of `[pool]` and `[pools.<name>]` only, and in any other table it's refused as an unknown key, as step 10's config loading says. `server` written in `[pool]` is refused as an unknown key whose message names `servers`; in a `[pools.<name>]` profile, where `server` is the profile's `[pools.<name>.server]` table, a `server` that isn't a table, such as `server = "several"`, stops loading with `Error::Config` naming `servers` too. The value is read once, and the servers bit set from it when the pool starts, as R-1270 says; it isn't changed at run time. Owner decision: a `servers` pool setting.
