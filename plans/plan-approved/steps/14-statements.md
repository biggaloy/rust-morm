# Step 14: Statement caches and fragments

- **Phase:** Runtime
- **Depends on:** 11, 12, 13, 56
- **Can run beside:** 07, 08, 09, 29, 30, 31, 32, 33, 34, 35
- **Crates:** `morm`, `morm-core`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

The two bounded caches, shape tracking, `query_typed` fallback, fragment renumbering and the error mapping every query uses.

## Deliverables

- `statement_cache`, `shape_cache`, prepare on second use, built-SQL map, each parameter's carrier and `($n::cast)`, the scanner's casts in fragments, 0A000 and stale type handling, the decoder choice per statement, `$n` renumbering, `.tag()` text, typed error mapping, with an online swap's shadow unique index mapped to its field

## End-to-end check

A load test with random and repeated shapes shows fixed statements staying cached, and a change to a table's result type or an enum type swap recovers outside a transaction.

## Out of scope

- The query APIs that use the caches (steps 15, 17)

### Models / Type inference

- **R-0208** **NUL bytes:** Postgres rejects `\0` in text. morm doesn't scan every string for it, which would cost time on every write; Postgres's error becomes a typed `InvalidText`.

### Reading and writing / Query safety

- **R-0433** **`$n` in a fragment is local.** `comp`, `set_expr` and `.q()` fragments each count from `$1`, and morm renumbers them. The scan skips quoted strings and comments, so `'$1'` stays text. The scanner lives in `morm-core`, and it writes each parameter's cast, as `($n::type)`.
- **R-1221** **The scanner places the casts.** It follows Postgres's `scan.l` for everything that can hide a `$n`: standard strings with `''`, escape strings `E'..'` with backslashes, and `B'..'`, `X'..'`, `N'..'` and `U&'..'`; quoted identifiers with `""`, and `U&".."`; `--` comments and nested `/* */` comments; dollar quotes `$$..$$` and `$tag$..$tag$`; identifiers that hold `$`, such as `a$1`; and operator splitting, including the rule on a trailing `+` or `-`. It refuses an unterminated quote or comment. In the pass that renumbers each `$n`, it writes the cast for that parameter's slot: the column's cast for a value bound through a field, as in `comp` (choice G), and each value's own `Param` cast for a free one, in `set_expr`, `.q()`, `q_unchecked` and `sql_unchecked`. So `price < $1 AND tag = '$1' AND x = ANY($2) -- $1`, numbered from 3, becomes `price < ($3::numeric) AND tag = '$1' AND x = ANY(($4::text[])) -- $1`. A call site's value types are fixed, so its casts are too, and the scanner runs once per shape. Owner decision DH2, choice F.
- **R-0434** Typed errors: `Unique { constraint, field }`, `ForeignKey`, `NotNull`, `Check`, `Serialization`, `Deadlock`, `LockTimeout`, `TransactionTimeout`, `TransactionAborted`, `CommitUnknown`, `NestedConnection`, `PoolerMode`, `NotFound`, `EmptyPatch`, `Conflict`, `Forbidden`, `Validation`, `PoolBusy`, `ConnectionLost`, `ReadOnly`, `OutOfRange`, `InvalidText`, `InvalidOrder`, `InvalidCursor`, `Decimal`. `Unique`'s `field` maps a unique index named `_morm_new_<name>`, made from a unique index's name `<name>` through the 63-byte name function, to the field it maps `<name>` to, because while an online swap in step 39, 52 or 60 changes a column, or step 39 rebuilds an index concurrently after a type change, a write can collide on that shadow index alone, such as one whose value equals another only once rounded, or an enum label a map turns into one another row holds.

### Performance and memory / `morm::Pool`

- **R-0625** **Statement caches:** two bounded LRUs on each connection, below.

### Performance and memory / Statements

- **R-0703** Two bounded LRUs per connection. Evicted statements are closed when dropped, which also frees Postgres memory.

| ID | Setting | Default | Holds |
|---|---|---|---|
| R-0704 | `statement_cache` | 256 | SQL fixed at compile time: `get` and `delete` by primary key, a model's static `insert`, `sql!`, `db.sql()` and `db.raw()` |
| R-0705 | `shape_cache` | 128 | SQL put together at runtime: `select` builders including `filter_cols` and `.q()`, `get_by`, `get_where`, `get_q`, `delete_by`, `delete_where`, `delete_q`, inserts with defaulted fields, `update`, `update_q`, `.apply()`, and any query with a `.tag()` |

- **R-0706** **Why two:** each combination of columns is different SQL text, so a 10-field patch has up to 1,023 shapes, and a client chooses which one it sends. morm can't tell a fixed `.set()` chain from a conditional one, so the split is by how the SQL is made. A fixed chain is one busy shape and stays cached.
- **R-0707** **A shape is prepared the second time it's seen.** Its first use runs through `query_typed`, in one round trip, with no cache entry. A small fixed table of shape hashes per connection records what has been seen, and a collision only prepares a shape one use early.
- **R-0708** `.limit(n)` is always a bound parameter, so a client's page size can't create new shapes.
- **R-0709** **Worst case:** random one-off shapes are never prepared and evict nothing. A client repeating hundreds of shapes can churn `shape_cache`, but it can't touch `statement_cache`.
- **R-0711** **Query tags:** `.tag("orders.list")` adds a fixed comment, `/* orders.list */`, so server logs, `auto_explain` and `pg_stat_activity` show which code ran a query. It costs nothing unless used.
- **R-0712** It takes only `&'static str`, so it can't hold a request id, which would make every query text unique. Characters outside letters, digits, `.`, `_`, `:` and `-` become `_`, so a tag can't close the comment.
- **R-0713** One tag is one extra statement: the same SQL under two tags is prepared twice.
- **R-0714** `pg_stat_statements` ignores comments, so those two calls merge into one entry showing the first tag seen. Use logs for tags, and `pg_stat_statements` for totals per query.
- **R-0715** Built SQL text is kept in a small bounded map keyed by model and column bitmask, so a repeated shape doesn't rebuild the string.
- **R-0716** Other dynamic SQL and overflow go through `query_typed`, which needs no prepare round trips. It needs each parameter's Postgres type, and `ToSql` doesn't give that, so parameters are `&dyn morm::Param`, a trait that adds the cast and the built-in carrier. Builder code knows both from `F`.
- **R-0718** A cached statement can go stale when a migration changes something under it, and it then fails every time until it's re-prepared. Each stale-statement signal R-1245 lists, from a cached statement, is handled the same way whether Postgres returns it at prepare or at execute, as it does through PgBouncer: outside a transaction, straight to Postgres, morm evicts the statement, prepares it again and retries once; behind a pooler, R-1246's unnamed retry takes the place of the re-prepare, because PgBouncer would hand back the same stale server statement. The usual one is `0A000` from `RevalidateCachedQuery`, `cached plan must not change result type`, after a column's type changes. A statement that casts a parameter to a non-built-in type, such as an enum, a domain or a composite, survives a swap of that type, because every migration `tx` step ends with a reset that marks every cached plan invalid, so Postgres parses it again and resolves the name again, whether or not it touches a table holding the type. Without that reset, as after a swap made by hand, one that touches no such table, such as `SELECT ($1::st)::text`, gets `XX000` `cache lookup failed for type` once the old type is dropped, or `22P02` naming the old type while it's kept, and while it's kept a label both types share runs on the old type's order with no error, which no retry can see. So outside a transaction, any error from a cached statement that casts a parameter to a non-built-in type is retried once on a fresh statement, and a retry that fails again returns its error: that statement parsed once, so the error comes from a schema change and not a typo, and Postgres rolled the failed statement back, so the retry is safe. R-0981's handling still comes first for R-1245's stale-session signals. Owner decisions DH2, choice I, SA, SC and SD.
- **R-1220** **Every parameter has a built-in carrier and a cast.** Every statement morm sends declares each parameter in Parse as its built-in carrier and casts it in the SQL as `($n::cast)`, so Postgres never infers a parameter's type: in `sql!`, every builder, model inserts and updates, `UNNEST`, keyset pages, runtime fragments, `.limit(n)` and morm's own advisory locks, the last two as `int8`. The parentheses are needed: without them, `$1[1]` would become `$1::int8[][1]`, which Postgres reads as the type `int8[][1]` and so returns the whole array, and `$1.n` would fail with `0A000`. A non-built-in type is cast by name, so no OID is looked up or sent. Built text is cached, in R-0715's map and in `shape_cache`, with its casts, and nothing about typing costs a round trip. Owner decision DH2, choices A and C.
- **R-1104** **Decoding follows the column's real type.** When a statement is prepared, morm reads each result column's type from the row description Postgres returns, chooses each field's decoder from it once, and keeps that choice with the statement in its cache entry. A `query_typed` call, which has no cache entry, chooses once from its own result's row description. The internal query entry point then reads all of that statement's rows through `from_row` when every column has the type the binary was built against, so that path is unchanged, and through `from_row_as` with the statement's choice otherwise, deciding once before the first row and never per row. A re-prepare after a migration, on `0A000` as R-0718 says, chooses again, so a statement cached before a cutover picks the new column type's decoder. Every statement is prepared with each parameter's built-in carrier, as `query_typed` sends it. Its SQL casts the parameter to the column type the binary was built against where it's bound through a field, and otherwise to the value's own type. So Postgres converts it when it's written: a widened column takes every value the binary writes, and a value a narrowed one can't hold gets the database's error for that write.

### Performance and memory / Query path

- **R-0720** SQL for `get` and `delete` by primary key is a compile-time `&'static str`, as are a model's column list and its insert when it has no defaulted optional fields (section 8).
- **R-0723** Positional decoding; borrowed parameters (`&dyn morm::Param`), not boxed.
- **R-0725** Rows carry no per-row metadata.
- **R-0726** No dynamic dispatch in hot paths.

### Managed enums

- **R-0981** **Stale server state.** Three errors, from any statement, mean a session holds compiled code a re-prepare can't reach, each known by R-1245's signal: `XX000` `cache lookup failed for type`, from a dropped type; `42804` from one of plpgsql's three parameter routines, `type of parameter ... does not match that when preparing the plan`, from a plpgsql function compiled before a column or row type changed; and `22P02` from `enum_in` naming a type morm retired, `_morm_retired_...`, from a plpgsql variable compiled against an enum type a cutover kept under that name with its labels renamed. Each repeats on every call, and a new connection clears it. Evicting a statement can't, so outside a transaction, straight to Postgres, morm discards the connection, retries once on another, and raises the pool's connection generation: at once for the first two, and for the `22P02` only once the retry has succeeded, because a client can send a label holding that text. Behind a pooler it retries once on another connection, which may reach a fresh server session, and discards and raises nothing, because a client connection can't reach a server session. On a `db.hold()` connection nothing moves: morm returns `Error::SchemaChanged`, and the connection is replaced on release. A fourth error is transient: `XX000` `could not open relation with OID`, from a caller of a `BEGIN ATOMIC` function while a cutover replaces that function or a view under it. It doesn't repeat, and a new statement on the same connection works, so the connection isn't at fault: outside a transaction morm retries once on that connection, held or not, replaces nothing and raises no generation. Tested on Postgres 15 to 18: all 3,566 such errors, with plain and cached plans, cleared on the first retry on the same connection. Owner decisions SB, SC and SD.
- **R-0982** **Telling the rest of the pool.** A confirmed stale statement raises a statement generation, held in the same atomic word as the pool's connection generation. A statement is confirmed stale when its error is one of R-1245's certain signals, `0A000` from `RevalidateCachedQuery`, `XX000` `cache lookup failed for type` or `42804` from one of plpgsql's three parameter routines, or when the retry on a fresh statement succeeds where the cached one failed, which is how a `22P02` is confirmed, since its text can come from a client. A retry that fails the same way returns its error and raises nothing, so a client sending a bad enum label can't clear the caches on every request. A connection that checks out behind the generation clears both statement caches first, so connections don't each fail once per cached statement. The cost is the one atomic read a checkout already does. Owner decision SF.
- **R-0983** **Retrying is safe.** Postgres rolls back a failed statement outside a transaction, so a retry can't apply a write twice. A `42883`, or a `42804` from any routine but R-1245's three, from a statement that isn't in a cache is never retried, the errors in R-0981 are retried from any statement, nothing is retried once a row has reached the caller, and a retry that fails again returns its error. Owner decision SC.

**R-1245** **Recognising a stale error in any language.** `lc_messages` translates every message but an `elog`'s, and a server set to another language sends that language to every client, so morm reads no translated text. It knows each stale error by a signal that doesn't change with the language: the SQLSTATE, the routine field, which Postgres never translates, an identifier in the message, which is never translated either, or the message of an `elog`, which is always English. On Postgres 15 to 18:

| Error | Signal | Kind |
|---|---|---|
| `0A000` from a cached statement | routine `RevalidateCachedQuery` | stale statement |
| `42804` from any statement | routine `plpgsql_param_eval_recfield`, `plpgsql_param_eval_generic` or `plpgsql_param_eval_generic_ro` | stale session |
| `XX000` from any statement | message starting `cache lookup failed for type` | stale session |
| `XX000` from any statement | message starting `could not open relation with OID` | transient |
| `22P02` from any statement | routine `enum_in`, and the message holds `_morm_retired_` | stale session, once its retry succeeds |
| `22P02` from a cached statement that casts a parameter to a non-built-in type | routine `enum_in`, and the message doesn't hold that cast's type name as a whole identifier, with or without its schema, which Postgres prints only when the type isn't on the `search_path` | stale statement, from a swap made outside morm |
| Any other error from a cached statement that casts a parameter to a non-built-in type | none: retried once, as R-0718 says | stale statement only if the retry succeeds |

An English message is a second signal for `0A000`, `cached plan must not change result type`, and for `42804`, `type of parameter ... does not match that when preparing the plan`, so a version that renames a routine still works on an English server. T-0151 and T-0152 assert each routine on every version, so a new major version runs them first, and a unit test feeds the matcher every row, the third `42804` routine among them. A miss is never silent: the error reaches the app as `Error::Postgres`. Postgres 18 also raises the `0A000` message from `sql_postrewrite_callback`, for a SQL function whose body starts or stops returning a row type; that isn't a stale statement, and it isn't treated as one. The recovery-conflict routine differs by version, so nothing here reads it. Owner decision SC.

**R-1246** **Behind PgBouncer, a statement generation every process shares.** PgBouncer keeps one server statement per text and hands it to every client that prepares that text, so a stale one survives a re-prepare and a new client connection, and a counter inside each process starts at the same value in every process. So with `pooler = "transaction"` and the statement caches on, the text morm prepares for a cached statement starts with `/* morm g<n> */`, before any `.tag()`, where `<n>` is the database's statement generation, read from the `_morm` schema's comment, `morm statement generation <n>`, which every migration `tx` step raises in its own transaction, as `contracts.md` says. Any role reads it from `pg_description` with no grant, and a database with no `_morm`, or no such comment, reads as `0`. It's one fixed comment per generation, not per request, so R-0755 holds, and `pg_stat_statements` ignores it, as R-0714 says. Straight to Postgres, or with the caches off, there's no marker. A pool reads `<n>` when it starts, with one catalog query on its first connection, until step 41 folds that read into its startup statement.

- On one of R-1245's stale-statement signals from a cached statement, at prepare or at execute, outside a transaction, morm runs the call once more through `query_typed`, unnamed, which PgBouncer never shares. If that succeeds, the cached text was stale: morm reads `<n>` again on that connection and adopts it if it moved; if it didn't, because the DDL was made outside morm, morm adds a random 64-bit salt, `/* morm g<n>.<salt> */`, kept until `<n>` next moves, so the process's texts meet no stale server statement. Either way it raises the statement generation, as R-0982 says, so every connection drops its cached statements at checkout and prepares the new text. If the unnamed run fails too, its error is returned and nothing changes.
- Inside a transaction there's no retry: the signal returns `Error::SchemaChanged`, and once the transaction has rolled back morm reads `<n>` on that connection and applies the same rule, so `.retry(n)`'s next attempt prepares fresh text.
- `pool_stats()` counts the stale statements retried unnamed and shows the pool's current marker, `g<n>` or `g<n>.<salt>`.
- The cost is one catalog read when a pool starts, and on a stale error one unnamed run and one catalog read, once per process per generation. While old and new processes run side by side, each server connection holds one set of statements for each generation in use, which `max_prepared_statements` bounds.

Owner decisions SD, SE and SF.
