### Models / Type inference

- **R-0208** **NUL bytes:** Postgres rejects `\0` in text. morm doesn't scan every string for it, which would cost time on every write; Postgres's error becomes a typed `InvalidText`.

### Reading and writing / Query safety

- **R-0433** **`$n` in a fragment is local.** `comp`, `set_expr` and `.q()` fragments each count from `$1`, and morm renumbers them. The scan skips quoted strings and comments, so `'$1'` stays text. The scanner lives in `morm-core`, and it writes each parameter's cast, as `($n::type)`.
- **R-1221** **The scanner places the casts.** It follows Postgres's `scan.l` for everything that can hide a `$n`: standard strings with `''`, escape strings `E'..'` with backslashes, and `B'..'`, `X'..'`, `N'..'` and `U&'..'`; quoted identifiers with `""`, and `U&".."`; `--` comments and nested `/* */` comments; dollar quotes `$$..$$` and `$tag$..$tag$`; identifiers that hold `$`, such as `a$1`; and operator splitting, including the rule on a trailing `+` or `-`. It refuses an unterminated quote or comment. In the pass that renumbers each `$n`, it writes the cast for that parameter's slot: the column's cast for a value bound through a field, as in `comp` (choice G), and each value's own `Param` cast for a free one, in `set_expr`, `.q()`, `q_unchecked` and `sql_unchecked`. So `price < $1 AND tag = '$1' AND x = ANY($2) -- $1`, numbered from 3, becomes `price < ($3::numeric) AND tag = '$1' AND x = ANY(($4::text[])) -- $1`. A call site's value types are fixed, so its casts are too, and the scanner runs once per shape. Owner decision DH2, choice F.
- **R-0434** Typed errors: `Unique { constraint, field }`, `ForeignKey`, `NotNull`, `Check`, `Serialization`, `Deadlock`, `LockTimeout`, `TransactionTimeout`, `TransactionAborted`, `CommitUnknown`, `NestedConnection`, `PoolerMode`, `NotFound`, `EmptyPatch`, `Conflict`, `Forbidden`, `Validation`, `PoolBusy`, `ConnectionLost`, `ReadOnly`, `OutOfRange`, `InvalidText`, `InvalidOrder`, `InvalidCursor`, `Decimal`. `Unique`'s `field` maps a unique index named `_morm_new_<name>`, made from a unique index's name `<name>` through the 63-byte name function, to the field it maps `<name>` to, because while an online swap in step 39, 52 or 60 changes a column, or step 39 rebuilds an index concurrently after a type change, a write can collide on that shadow index alone, such as one whose value equals another only once rounded, or an enum label a map turns into one another row holds.

### Performance and memory / `morm::Pool`

- **R-0625** **Statement caches:** two bounded LRUs on each connection, below.

### Performance and memory / Statements

- **R-0703** Two bounded LRUs per connection. Evicted statements are closed when dropped, which also frees Postgres memory.

| ID | Setting | Default | Holds |
|---|---|---|---|
| R-0704 | `statement_cache` | 256 | SQL fixed at compile time: `get` and `delete` by primary key, a model's static `insert`, `sql!`, `db.sql()` and `db.raw()` |
| R-0705 | `shape_cache` | 128 | SQL put together at runtime: `select` builders including `filter_cols` and `.q()`, `get_by`, `get_where`, `get_q`, `delete_by`, `delete_where`, `delete_q`, inserts with defaulted fields, `update`, `update_q`, `.apply()`, and any query with a `.tag()` |

- **R-0706** **Why two:** each combination of columns is different SQL text, so a 10-field patch has up to 1,023 shapes, and a client chooses which one it sends. morm can't tell a fixed `.set()` chain from a conditional one, so the split is by how the SQL is made. A fixed chain is one busy shape and stays cached.
- **R-0707** **A shape is prepared the second time it's seen.** Its first use runs through `query_typed`, in one round trip, with no cache entry. A small fixed table of shape hashes per connection records what has been seen, and a collision only prepares a shape one use early.
- **R-0708** `.limit(n)` is always a bound parameter, so a client's page size can't create new shapes.
- **R-0709** **Worst case:** random one-off shapes are never prepared and evict nothing. A client repeating hundreds of shapes can churn `shape_cache`, but it can't touch `statement_cache`.
- **R-0711** **Query tags:** `.tag("orders.list")` adds a fixed comment, `/* orders.list */`, so server logs, `auto_explain` and `pg_stat_activity` show which code ran a query. It costs nothing unless used.
- **R-0712** It takes only `&'static str`, so it can't hold a request id, which would make every query text unique. Characters outside letters, digits, `.`, `_`, `:` and `-` become `_`, so a tag can't close the comment.
- **R-0713** One tag is one extra statement: the same SQL under two tags is prepared twice.
- **R-0714** `pg_stat_statements` ignores comments, so those two calls merge into one entry showing the first tag seen. Use logs for tags, and `pg_stat_statements` for totals per query.
- **R-0715** Built SQL text is kept in a small bounded map keyed by model and column bitmask, so a repeated shape doesn't rebuild the string.
- **R-0716** Other dynamic SQL and overflow go through `query_typed`, which needs no prepare round trips. It needs each parameter's Postgres type, and `ToSql` doesn't give that, so parameters are `&dyn morm::Param`, a trait that adds the cast and the built-in carrier. Builder code knows both from `F`.
- **R-1220** **Every parameter has a built-in carrier and a cast.** Every statement morm sends declares each parameter in Parse as its built-in carrier and casts it in the SQL as `($n::cast)`, so Postgres never infers a parameter's type: in `sql!`, every builder, model inserts and updates, `UNNEST`, keyset pages, runtime fragments, `.limit(n)` and morm's own advisory locks, the last two as `int8`. The parentheses are needed: without them, `$1[1]` would become `$1::int8[][1]`, which Postgres reads as the type `int8[][1]` and so returns the whole array, and `$1.n` would fail with `0A000`. A non-built-in type is cast by name, so no OID is looked up or sent. Built text is cached, in R-0715's map and in `shape_cache`, with its casts, and nothing about typing costs a round trip. Owner decision DH2, choices A and C.
- **R-1104** **Decoding follows the column's real type.** When a statement is prepared, morm reads each result column's type from the row description Postgres returns, chooses each field's decoder from it once, and keeps that choice with the statement in its cache entry. A `query_typed` call, which has no cache entry, chooses once from its own result's row description. The internal query entry point then reads all of that statement's rows through `from_row` when every column has the type the binary was built against, so that path is unchanged, and through `from_row_as` with the statement's choice otherwise, deciding once before the first row and never per row. A re-prepare after a migration, on `0A000` as R-0718 says, chooses again, so a statement cached before a cutover picks the new column type's decoder. Every statement is prepared with each parameter's built-in carrier, as `query_typed` sends it. Its SQL casts the parameter to the column type the binary was built against where it's bound through a field, and otherwise to the value's own type. So Postgres converts it when it's written: a widened column takes every value the binary writes, and a value a narrowed one can't hold gets the database's error for that write.

### Performance and memory / Query path

- **R-0720** SQL for `get` and `delete` by primary key is a compile-time `&'static str`, as are a model's column list and its insert when it has no defaulted optional fields (section 8).
- **R-0723** Positional decoding; borrowed parameters (`&dyn morm::Param`), not boxed.
- **R-0725** Rows carry no per-row metadata.
- **R-0726** No dynamic dispatch in hot paths.

### Managed enums

**R-1245** **The stale-session signals, recognised in any language.** `lc_messages` translates every message but an `elog`'s, and a server set to another language sends that language to every client, so morm reads no translated text. It knows each signal by something that doesn't change with the language: the SQLSTATE, the routine field, which Postgres never translates, an identifier in the message, which is never translated either, or the message of an `elog`, which is always English. R-1270's machine sorts the signals into two classes by what cures them, which is all it needs to know. On Postgres 15 to 18:

| Signal | Recognised by | Class | Cured by | Can client input cause it? |
|---|---|---|---|---|
| `0A000` from a cached statement | routine `RevalidateCachedQuery` | statement | a fresh statement | Yes: a `search_path` set per transaction over tables of different shapes, with no schema change |
| `22P02` from a cached statement that casts a parameter to a non-built-in type, not holding that cast's type name as a whole identifier, with or without its schema, which Postgres prints only when the type isn't on the `search_path` | routine `enum_in` and that name test | statement | a fresh statement, when it's stale | Yes: a client's label converted to another enum, or a row it changed between two runs |
| Any other error from a cached statement that casts a parameter to a non-built-in type, outside a transaction (choice I) | none | statement | a fresh statement, when it's stale | Yes: every ordinary error, such as `23505` |
| `XX000` from a cached statement | message starting `cache lookup failed for type` | statement first: a fresh run tells it from compiled code | a fresh statement, or a new session when plpgsql raised it | No: it needs DDL |
| `XX000` from a fresh run, or from a statement that isn't cached | message starting `cache lookup failed for type` | session | a new session | No |
| `42804` from any statement | routine `plpgsql_param_eval_recfield`, `plpgsql_param_eval_generic` or `plpgsql_param_eval_generic_ro` | session | a new session, when stale | Yes: a record variable fed rows of the caller's choice, with no schema change |
| `22P02` from any statement, holding `_morm_retired_`, with no bound parameter's text holding it | routine `enum_in` and the identifier | session | a new session, when stale | Yes: stored or transformed text |
| `22P02` holding `_morm_retired_` that a bound parameter's text holds | R-0981's parameter test | none: returned as it is | | It's the client's own label |
| `XX000` from any statement | message starting `could not open relation with OID` | transient, R-0981 | | No |
| A lost connection, SQLSTATE class `08`, `40`, `53` or `57`, or `55P03` | the connection, or the SQLSTATE | not a signal; as a fresh run's outcome it neither confirms nor fails | | A timeout can be |

**A confirmation** is a fresh run of the same statement text with the same parameter bytes, where the cached statement or the old connection failed, that succeeds, with or without rows, as an `INSERT`, `UPDATE` or `CALL` that returns only its command tag does, or that ends in a server error other than the first one and off the no-confirm list. The no-confirm list is the outcomes that can end a statement before it reaches the conversion: a lost connection, SQLSTATE class `08` (connection), `40` (a deadlock or serialization failure, a standby's recovery conflict among them), `53` (insufficient resources) or `57` (operator intervention, a statement timeout, a cancel or an admin shutdown among them), and `55P03` (lock timeout). A fresh run that ends in the same error fails; one that ends on the no-confirm list neither confirms nor fails, and requests nothing. Three signals count as confirmed on their own, because what cures them cures them for certain: `0A000`, which a fresh statement cures; and, on an old connection that R-0981 replaces, `42804` and an `XX000` `cache lookup failed for type` from a fresh run, which a new session cures. No other signal requests a pool-wide action without a confirmation.

An English message is a second signal for `0A000`, `cached plan must not change result type`, and for `42804`, `type of parameter ... does not match that when preparing the plan`, so a version that renames a routine still works on an English server. T-0151 and T-0152 assert each routine on every version, so a new major version runs them first, and a unit test feeds the matcher every row, the third `42804` routine among them. A miss is never silent: the error reaches the app as `Error::Postgres`. Postgres 18 also raises the `0A000` message from `sql_postrewrite_callback`, for a SQL function whose body starts or stops returning a row type; that isn't a stale statement, and it isn't treated as one. The recovery-conflict routine differs by version, so nothing here reads it. Owner decisions SC, SF, choice I, EF1, EH2, EJ6, EK4 and MB.

**R-1270** **The stale-session machine is one pure module.** Every stale-statement and stale-session rule of this step and of step 20 is one state machine, built as one module of `morm`, such as `stale.rs`, with no I/O. It holds the pool's stale-session state, below, and its functions take a signal, the call's context (straight to Postgres or behind PgBouncer, inside a transaction or not, on a held connection or not, from a cached statement or a fresh run) and the clock, and return a decision: answer with a fresh run, replace the connection, discard it, retry on the same connection, retry on another connection, return `Error::SchemaChanged`, or return the error as it is, with any pool-wide action to request. The pool and connection code carries the decisions out, and step 20's simulation drives this same module, so it tests the code that ships. The machine keeps two things apart:

- **Every call is repaired locally, always.** A stale statement gets one fresh run of the same call. A stale session straight to Postgres gets the call retried on a newly opened connection that takes the old one's slot. Inside a transaction the call returns `Error::SchemaChanged`, and `.retry(n)`'s next attempt gets the fresh statement or the new connection. Nothing about the window, the epoch or a table changes what one call returns, beyond what its row says.
- **Every pool-wide action passes one gate,** R-0982's: clearing every connection's statement caches, adding a salt behind PgBouncer, and replacing every connection, each at most once per pool per `stale_cooldown`, plus once per migration.

The rows are R-0718's (the statement class, both modes), R-0981's (the session class straight to Postgres, the parameter test and the transient `XX000`), R-1246's (the session class behind PgBouncer) and R-0982's (the gate and the events). This step builds the state, the rows outside a transaction, A and C, and the events, E; step 20 adds the rows inside one, B and D, which this step's requirements state so the machine is written once.

**The state, per pool.** Each item is stated here once, with its bound and what clears it.

| State | What it is | Bound | Set or cleared by |
|---|---|---|---|
| Marker `g<n>` or `g<n>.<salt>` | behind PgBouncer with the caches on, the comment starting each cached text, R-1246 | one value | `<n>` read at pool start; adopted when a read finds it moved, after a migration, which drops the salt; a salt added by the gate's *salt* action, replacing any earlier salt |
| Statement generation | a counter; a connection behind it clears both statement caches at checkout | one word | raised by the gate's *clear* and *salt* actions and by adopting a moved `<n>` |
| Connection generation | step 11's counter; a connection behind it is replaced at checkout | the same atomic word | raised by the gate's *replace* action, straight to Postgres only |
| The window | the time of the last pool-wide action, the `<n>` it was taken under, and one due action | O(1); the due action is two bits in the generation word | an action starts it; it ends `stale_cooldown` later; a request inside it sets the due action, and the first checkout after it ends takes that action |
| The epoch, straight to Postgres | its start `T`, the `<n>` read at `T`, its end `T + stale_cooldown`, and whether it's suspended | O(1) | started by a session-class failure when there's no epoch, it has ended, or the `<n>` just read differs from its own; suspended for the rest of its life when a replacement connection can't be opened |
| Pending entries | per statement text, keyed by a 64-bit hash of the text: the hash of the confirming parameter bytes, a horizon and an expiry | at most `stale_pending_max`, the oldest dropped | created by a statement-class signal inside a transaction, after any request that signal makes, unless `<n>` moved; a later signal of the same statement moves its horizon and confirming bytes, never its expiry; removed when it expires, `stale_pending_expiry` after its creation, when its confirming run fails or ends on R-1245's no-confirm list, when its statement hits a session-class signal behind PgBouncer, and all at once when a pool-wide action is taken or `<n>` moves |
| Cool-down, behind PgBouncer | per statement text, keyed by a 64-bit hash of the text: an expiry | at most `stale_cooldown_max`, the oldest dropped | added by a session-class failure that got `Error::SchemaChanged` or a failed retry on another connection; removed `stale_cooldown` later, and all at once when a pool-wide action is taken or `<n>` moves |

Per connection: the time it was opened, the two generations it last saw, and for each cached statement the sequence number at which it was prepared, 8 bytes, which a pending entry's horizon is compared with. There are no per-statement records straight to Postgres: one epoch decides which connections may be stale, and no table a client can fill decides whether a connection is replaced.

**The decision procedure.** `pooled` means behind PgBouncer, `ctx.out` outside a transaction, and `old(conn, n)` R-0981's test:

```text
on_error(call, conn, err, ctx):
    if param_holds_retired(call): return AsIs
    if err is transient XX000:     return ctx.out ? RetrySameConn : SchemaChanged
    cls = class(err, cached = !call.fresh)        # R-1245
    if cls == Statement:
        if ctx.out:
            r = fresh_run(call)
            if confirms(r, err) or err == 0A000: request(pooled ? Salt : Clear, read_n_if_needed())
            if err is XX000 and r is XX000: return session(call, conn, r, ctx)
            return r
        else:
            if !pooled: evict(conn, call.stmt)
            n = read_n(conn); if pooled and n moved: adopt(n) else:
                if err == 0A000: request(pooled ? Salt : Clear, n)
                entry(call.stmt, call.bytes)
            if !pooled and err is XX000 and old(conn, n): discard(conn); expect_confirm(call, Replace)
            return SchemaChanged
    if cls == Session: return session(call, conn, err, ctx)
    return AsIs

session(call, conn, err, ctx):
    if pooled:
        remove_entry(call.stmt)
        if in_cooldown(call.stmt): return AsIs
        if ctx.out: r = run_on_other_conn(call); if r fails the same way: cooldown(call.stmt); return r
        cooldown(call.stmt); return SchemaChanged
    n = read_n(conn)
    if !old(conn, n): return AsIs                  # opened since T, or the epoch suspended
    if err in {42804, XX000}: request(Replace, n)
    if ctx.out: r = replace(conn, call); if confirms(r, err): request(Replace, n); return r
    discard(conn); expect_confirm(call, Replace); return SchemaChanged

request(action, n):
    if window_open() or n != window.n: take(max(action, due)); else due = max(due, action)
```

`adopt(n)` is the moved-`<n>` rule of R-0982's event E1; `expect_confirm` marks the run whose confirmation requests *replace*; `read_n_if_needed` reads `<n>` behind PgBouncer on a confirmation or `0A000`, and straight to Postgres only when the window is closed. A statement whose pending entry exists runs fresh before any of this, as R-0718 says. Owner decisions MA and MB.

**R-0718** **Stale statements: the statement class.** A cached statement can go stale when a schema changes under it, and it then fails every time until it's prepared again. A statement that casts a parameter to a non-built-in type, such as an enum, a domain or a composite, survives a swap of that type made by a migration, because every migration `tx` step ends with a reset that marks every cached plan invalid, so Postgres parses it again and resolves the name again, whether or not it touches a table holding the type. Without that reset, as after a swap made by hand, one that touches no such table, such as `SELECT ($1::st)::text`, gets `XX000` `cache lookup failed for type` once the old type is dropped, or `22P02` naming the old type while it's kept, and while it's kept a label both types share runs on the old type's order with no error, which no retry can see. Each statement-class signal R-1245 lists is handled the same way whether Postgres returns it at prepare or at execute, as it does through PgBouncer. Postgres rolled the failed statement back, so running the call again is safe, and the statement parsed once, so its error comes from a schema change or the data, not a typo.

- **A fresh run:** straight to Postgres, morm evicts the statement on this connection, prepares it again and runs it; behind PgBouncer, it runs the call once unnamed through `query_typed`, which PgBouncer never shares, because a re-prepare would get the same stale server statement back. A stale statement gets one fresh run and no other retry.
- **A pending entry,** R-1270's, keeps a statement fresh while a confirmation is outstanding. Before any row, a statement whose entry exists runs fresh: straight to Postgres, a copy cached on this connection before the entry's horizon is prepared again first; behind PgBouncer, the run is unnamed. If its parameter bytes are the entry's, it's the confirming run: a confirmation, R-1245's, requests *clear* straight to Postgres or *salt* behind PgBouncer, through R-0982's gate; the same error removes the entry and goes on through the rows as from a fresh run; an outcome on R-1245's no-confirm list removes the entry and returns as it is. Runs with other parameter bytes run fresh too, so they get the right answer at once, even while an old type is kept and a cached run would answer by its order, and they confirm nothing.
- **Entry,** in a row, means: create the statement's pending entry, or refresh it, its horizon set to now and its confirming bytes to this call's, its expiry unchanged. Nothing, if pending entries are off.

|---|---|---|---|---|---|
| A1 | Straight to Postgres, outside a transaction, a `db.hold()` connection included: a statement-class signal, the `XX000` from a cached statement included | Fresh run | The fresh run's result | A confirmation, or `0A000`, requests *clear*. Rows B1, B2 and D1 are built in step 20. Any other error from a cached statement that casts a parameter to a non-built-in type gets its fresh run only outside a transaction; inside one it returns as it is, as step 20 says.

**Pending entries off.** With `stale_pending_expiry = "off"` or `"0s"`, or `stale_pending_max = 0`, no entry is kept. B1 and B2 still evict, so straight to Postgres each connection's copy fails at most once. Behind PgBouncer, D1 returns `Error::SchemaChanged` on every call of the statement inside transactions, `.retry(n)`'s attempts included, until a call outside a transaction confirms it, C1, or PgBouncer replaces the server connection through `RECONNECT` or `server_lifetime`; and while an old type is kept, a value both types share can run on the old type's order meanwhile, with no error.

**What it costs.** Each row costs what it says, besides the failed call itself. While no entry exists, the pending check is one relaxed atomic read of the pool's entry count per cached run; the text's hash, which the statement cache already holds, is compared only when the count isn't zero, the horizon only when the text matches, and the parameter bytes are hashed only then. A client's label can create an entry, so it can keep a statement running unnamed behind PgBouncer, or prepared again once per connection straight to Postgres, for every caller, for one `stale_pending_expiry` per entry: a later signal moves an entry's horizon, never its expiry. Owner decisions DH2, choice I, SA, SC, SD, EL1, EM1, EM3, EN1, EN5 and MB, with this fix's choice the owner approves through PR #3: one entry per statement text, holding the latest failing call's bytes, so client values add no entries and every value of a pending statement runs fresh.

**R-0981** **Stale sessions straight to Postgres: the session class and the epoch.** R-1245's session class means the session holds compiled code that no fresh statement can reach: `XX000` `cache lookup failed for type` from a fresh run or a statement that isn't cached, from a dropped type; `42804` from one of plpgsql's three parameter routines, from a plpgsql function compiled before a column or row type changed; and `22P02` from `enum_in` holding `_morm_retired_`, from a plpgsql variable compiled against an enum type a cutover kept under that name with its labels renamed. Each repeats on every call in that session, and a new session compiles the code fresh, so a connection opened after a change can't hold code compiled before it. Straight to Postgres one pool-wide **epoch**, R-1270's, decides which connections may be stale:

- **Old connection.** On a session-class failure morm reads `<n>` on the failing connection, from the `_morm` schema's comment, one catalog read, and starts an epoch at the moment of that read, `T`, if there's none, it has ended, or the `<n>` just read differs from the epoch's, which means a migration ran since; so a migration that commits between the failure and the read is inside the epoch. An epoch ends `stale_cooldown` after `T`. A connection is old when it was opened before `T` and the epoch isn't suspended. An old connection is replaced on its first such failure; one opened since `T` can't hold code compiled before the change, so its failure is data, and returns as it is at no cost.
- **Replace,** outside a transaction. morm opens a new connection as a momentary extra within the process's connection budget, which every pool in the process shares; with the budget full, or when Postgres refuses the extra open with `53300`, too many connections for the server or for the role, which the budget can't see, it closes the old connection first and opens the new one in its slot. It runs the call on the new connection as a fresh run. The new connection takes the old one's slot and the old one is closed, whatever that run returns, unless the new connection is lost. If the new connection can't be opened, the caller gets the original error, the old connection keeps its slot if it's still open, a slot already emptied is left to the pool, which reopens a connection on demand with its backoff on too many clients, and the epoch is suspended. So the pool's slots never pass `max`, its connections never pass `max + 1` or the budget, and one server slot is enough for a stale session to heal.
- **Discard,** inside a transaction, built in step 20. After the rollback morm closes the connection, and `.retry(n)`'s next attempt opens a new connection in that slot through the pool's ordinary open, with its backoff. If that open fails, `.retry(n)` returns its error and the epoch is suspended.

Before any row, in every mode and context:

- **The parameter test.** A `22P02` holding `_morm_retired_` can come from a client, because its message holds the input value. morm encodes every parameter itself, and no `PgEnum` label can start `_morm_`, so when a bound parameter's text holds `_morm_retired_`, the client sent it: morm returns the error as it is, with nothing done and nothing requested, at no cost.
- **The transient `XX000`.** `XX000` `could not open relation with OID`, from a caller of a `BEGIN ATOMIC` function while a cutover replaces that function or a view under it, doesn't repeat, and a new statement on the same connection works, so the connection isn't at fault: outside a transaction morm retries once on that connection, held or not; inside one it returns `Error::SchemaChanged`; nothing is replaced or requested. Tested on Postgres 15 to 18: all 3,566 such errors, with plain and cached plans, cleared on the first retry on the same connection.

So straight to Postgres, a client's stored or transformed text costs at most the connections open at an epoch's `T`, each replaced once, then nothing until the epoch ends: at most `max` replacements per `stale_cooldown`, plus `max` per migration, whatever it sends and however many statements. A real stale session stops reaching callers outside a transaction `stale_cooldown` after the change at the latest, because any epoch in force by then started after the change, and every connection holding code compiled before it is old in it. When Postgres refuses connections, a failed replacement suspends the epoch and the error returns as it is until the epoch ends, so healing comes within `stale_cooldown` of the first moment Postgres accepts a connection again. **R-0982** **The one gate for pool-wide actions.** Three actions reach the whole pool: *clear*, which raises the statement generation, so every connection clears both statement caches at its next checkout; *salt*, behind PgBouncer only, which adds a new random 64-bit salt to the marker, replacing any earlier one, and raises the statement generation, as R-1246 says; and *replace*, straight to Postgres only, which raises step 11's connection generation, so every connection is replaced at its next checkout, which clears its caches too. Every pool-wide action, whatever asked for it, a confirmation, `0A000`, `42804` or `XX000`, passes one gate:

- **A request** is taken now when the window is open, or when `<n>` has moved since the last action. With the window closed it's remembered as due, and taken at the first checkout after the window ends; a due *replace* outranks a due *clear*. Straight to Postgres, a request made while the window is closed reads `<n>` on that connection, one catalog read, so a migration's stale state is never held back; that and R-0981's epoch are the only reads of `<n>` straight to Postgres.
- **The window** starts when an action is taken and ends `stale_cooldown` later. Taking an action removes every pending entry and every cool-down entry and starts a window; the epoch is kept.
- **The window never changes a call's own outcome.** Inside it or outside it each signal gets its row, a statement-class signal its fresh run and the caller its result; only the pool-wide action waits.
- **A checkout** does one atomic read of the generation word, as it already does: a connection behind the connection generation is replaced, one behind the statement generation clears both caches, and a due action whose window has ended is taken.

So a pool takes at most one pool-wide action per `stale_cooldown`, plus one per migration, whatever clients send: a request takes an action only when the window is open or `<n>` moved since the last one, so two actions less than `stale_cooldown` apart have a migration between them.

- **R-0983** **Retrying is safe.** Postgres rolls back a failed statement outside a transaction, so a retry can't apply a write twice. A `42883`, or a `42804` from any routine but R-1245's three, from a statement that isn't in a cache is never retried, R-0981's session-class errors are retried from any statement, on the new connection that replaces an old one, nothing is retried once a row has reached the caller, and a retry that fails again returns its error. A stale statement gets one fresh run, R-0718's, and no other retry. Owner decision SC.

**R-1246** **Behind PgBouncer, a statement generation every process shares.** PgBouncer keeps one server statement per text and hands it to every client that prepares that text, so a stale one survives a re-prepare and a new client connection, and a counter inside each process starts at the same value in every process. So with `pooler = "transaction"` and the statement caches on, the text morm prepares for a cached statement starts with `/* morm g<n> */`, before any `.tag()`, where `<n>` is the database's statement generation, read from the `_morm` schema's comment, `morm statement generation <n>`, which every migration `tx` step raises in its own transaction, as `contracts.md` says. Any role reads it from `pg_description` with no grant, and a database with no `_morm`, or no such comment, reads as `0`. It's one fixed comment per generation, not per request, so R-0755 holds, and `pg_stat_statements` ignores it, as R-0714 says. Straight to Postgres, or with the caches off, there's no marker. A pool reads `<n>` when it starts, with one catalog query on its first connection, until step 41 folds that read into its startup statement; a pool whose startup check is off keeps that catalog query, so it reads `<n>` at start too.

- **The marker moves two ways.** A read that finds `<n>` moved, after a migration, is adopted, as R-0982's event E1 says: the marker becomes `g<n>`, dropping any salt, the statement generation rises, and every pending and cool-down entry is removed, with no gate, because migrations pace it. A *salt* action, taken through R-0982's gate when a stale statement is confirmed, or on `0A000`, with `<n>` unmoved, as after DDL made outside morm, makes it `g<n>.<salt>`, a new random 64-bit salt replacing any earlier one, and raises the statement generation, so every connection clears its caches at checkout and prepares the new text, and the process's texts meet no stale server statement. Behind PgBouncer `<n>` is read in R-0718's row C1, on a confirmation or `0A000`, and in row D1, after the rollback.
- **Fresh runs are unnamed,** R-0718's, and while a statement has a pending entry every run of it is unnamed.
- **A stale session is never acted on pool-wide.** morm reaches a server session only through a client connection, so R-1245's session class behind PgBouncer moves no marker, adds no salt, raises nothing, and opens or discards no client connection. The statement's pending entry is removed, and after its first failure its session-class errors return at once for `stale_cooldown`, through the cool-down, R-1270's. It heals when PgBouncer replaces the server connection, through `RECONNECT` or its `server_lifetime`, as step 59 says.

**R-1262** **The stale-session settings.** Every tunable of the stale-session machine, these four, is a pool setting, set like any other: in `[pool]`, in one `[pools.<name>]`, or by its `MORM_POOL_*` variable for the pool a process opens at startup. Each holds per pool. The retry count and the hash and salt widths are part of the design, not settings. Each default is the value the machine was designed and simulated with. A duration is written as a string with a unit, as every pool duration is.

| Setting | Default | Governs | Allowed |
|---|---|---|---|
| `stale_cooldown` | `"60s"` | R-0982's window for pool-wide actions; straight to Postgres, the length of R-0981's epoch; behind PgBouncer, how long R-1246's cool-down returns a statement's session-class error at once | `"1s"` to `"10m"`; shorter, `"0s"`, `0` or `"off"` is `Error::Config`, because with no window every request would clear or replace the whole pool, as `wait_timeout` can't be off |
| `stale_cooldown_max` | `64` | how many statements the cool-down holds per pool, behind PgBouncer, the oldest dropped; straight to Postgres it holds nothing | `1` to `4096`; `0` is `Error::Config`, because a cool-down that holds nothing would give a statement hitting a stale server session a retry or a `SchemaChanged` on every call |
| `stale_pending_expiry` | `"60s"` | how long a pending entry, R-0718's, lasts from its creation | `"off"` or `"0s"`, which turn pending entries off, or up to `"10m"`; `0` and `"0"` are bare numbers, refused like every other bare duration |
| `stale_pending_max` | `64` | how many pending entries a pool holds, the oldest dropped | `0` to `4096`; `0` turns pending entries off |

A value outside these bounds, or a duration written as a bare number, stops the pool at start with `Error::Config`, naming the key and the bound it broke, the floor or the ceiling, before any of the app's queries has run. The ceilings keep memory bounded, at most about 200 KB per pool, and keep a misset value from delaying a real stale session's healing for hours. There's no `stale_first_failure_max`: with one epoch per pool there are no first-failure records to bound, and a `stale_first_failure_max` key in `[pool]` or in any `[pools.<name>]` stops the pool at start with `Error::Config`, naming the key and saying it was removed, so a setting copied from an earlier draft of these rules can't seem to work while it does nothing. The values aren't changed at run time. Owner decisions on the tenth review, EO3, EO4, MA and MC.
