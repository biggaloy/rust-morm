## Goal

Transactions whose commit is confirmed, never assumed.

## Deliverables

- `db.transaction`, `tx` with `db`'s query calls, savepoints through `tx.transaction`, `.isolation` and `.retry(n)` on `db` only, per-transaction settings, immediate settings on `tx`, `tx.set_local`, `tx.get_for_update`, confirmed commit, `TransactionAborted`, `CommitUnknown`, pipelining on `tx`
- The stale-session machine's rows inside a transaction, B and D, and its randomised simulation, with `proptest` as a dev-dependency of `morm`

## End-to-end check

A swallowed error can never report a commit, a lost connection during `COMMIT` returns `CommitUnknown`, and a deadlock retried with `.retry(3)` succeeds with fresh rows.

## Out of scope

- Lock helpers (step 22)

### Reading and writing / Transactions

**R-0435**

```rust
db.transaction(async |tx| {
    tx.insert(&mut p).await?;
    Ok(())
}).await?;

db.isolation(Serializable).retry(3).transaction(async |tx| {   // runs again on 40001 or 40P01
    let mut order = Order { user_id, ..Default::default() };   // built inside
    tx.insert(&mut order).await?;
```

**R-0436** `tx` has every query call `db` has, and `contracts.md` lists its other methods. `tx.transaction(async |tx| ..)` opens a savepoint, released when the closure returns `Ok` and rolled back to when it returns an error. `tx` has no `isolation` or `retry`, so both are compile errors: the isolation level is fixed before a transaction's first query, and a savepoint can't recover from a deadlock, a serialization failure or an `Error::SchemaChanged`, R-0441's. Each per-transaction setting on `tx` (`statement_timeout`, `lock_timeout`, `transaction_timeout`) applies at once, as in `tx.lock_timeout(d).await?`, one `SET LOCAL` that holds for the rest of the transaction, through savepoints that are released; rolling back to a savepoint opened before it undoes it, as Postgres does. On Postgres 15 and 16, `tx.transaction_timeout(d)` moves the client-side timer instead. `tx.set_local("app.user", &id)` sets a value for RLS through `set_config(..., true)`, so it takes a parameter, which `SET LOCAL` can't. Owner decision DH5.

**R-1229** **`set_local`'s value is cast.** `set_config` takes `text`, so `tx.set_local` casts its value to its own type and then to `text`, as `set_config(($1::text), (($2::int8))::text, true)`. Owner decision DH2.

**R-0437** **A commit is confirmed, never assumed.** After a failed statement, Postgres turns `COMMIT` into `ROLLBACK` with no error, and tokio-postgres's `commit()` returns `Ok` either way, so a swallowed error would look like a saved transaction. Two checks prevent that:

- **R-0438** Any Postgres error marks the transaction as failed. Further use returns that error, and a closure returning `Ok` still gets it.
- **R-0439** `COMMIT` is sent as `SELECT 1; COMMIT` in one message. In a failed transaction the `SELECT` errors and Postgres skips the `COMMIT`, so this also catches errors morm didn't see, with no extra round trip. morm then rolls back and returns `TransactionAborted`.

**R-0441** **Savepoints** clear the failed mark, except after a deadlock or serialization error or an `Error::SchemaChanged`, which always fails the whole transaction. Rolling back to a savepoint keeps earlier locks, so a deadlock could repeat; a serialization failure can't succeed on the same snapshot; and a stale statement or session needs the whole transaction rolled back before morm reads the database's statement generation, because after a rollback to a savepoint a REPEATABLE READ or SERIALIZABLE transaction still sees its first statement's snapshot, which can hold an older generation, and a connection step 14's row B3 discards must not be one whose transaction goes on. So at a stale signal that returns `Error::SchemaChanged`, step 14's rows B1 to B3, D1, D2 outside the cool-down and the transient `XX000`, and at row B4 outside a savepoint, which reads the generation, morm rolls the whole transaction back before any read, with `ROLLBACK`, never `ROLLBACK TO SAVEPOINT`, and sends nothing more on it: the savepoint's own rollback, every later statement of the closures and the `COMMIT` aren't sent, each returning the error, as R-0438 says, so nothing an outer closure runs after catching it can run outside the transaction. The transaction returns the error even when the outer closure catches it and returns `Ok`, and `.retry(n)` runs the whole closure again. Inside a savepoint rows B3 and B4 read no generation, as step 14 says: B3 still rolls the whole transaction back and returns `Error::SchemaChanged`, and B4's stale session, returned as it is, is a Postgres error the savepoint clears, like every other error inside a savepoint, B5 and D3, the parameter test's `22P02` and D2's in the cool-down among them, so an outer closure can catch it and go on. Owner decisions: `SchemaChanged` fails the whole transaction, and a stale session's error inside a savepoint stays catchable.

**R-0442** **`.retry(n)`** goes before the closure, with `.isolation` and the per-transaction settings, as in `db.retry(n).transaction(async |tx| ..)`, and takes only a closure that can run again: `AsyncFnOnce(&Tx) -> Result<T> + Clone`, run as a fresh copy on each attempt, so a closure that changes a captured row doesn't compile. Rows are built inside the closure, so each attempt starts fresh and `pre_insert` can't run twice on one row, for example hashing a password twice. Between attempts the transaction rolls back and the connection is released during the jittered backoff.

**R-0444** **Read-only pools:** Postgres refuses `SERIALIZABLE` on a hot standby, so `.isolation(Serializable)` on a `read_only` pool returns `ReadOnly` before reaching the server.
