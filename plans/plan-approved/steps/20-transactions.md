## Goal

Transactions whose commit is confirmed, never assumed.

## Deliverables

- `db.transaction`, `tx` with `db`'s query calls, savepoints through `tx.transaction`, `.isolation` and `.retry(n)` on `db` only, per-transaction settings, immediate settings on `tx`, `tx.set_local`, `tx.get_for_update`, confirmed commit, `TransactionAborted`, `CommitUnknown`, pipelining on `tx`
- The stale-session machine's rows inside a transaction, B and D, and its randomised simulation, with `proptest` as a dev-dependency of `morm`

## End-to-end check

A swallowed error can never report a commit, a lost connection during `COMMIT` returns `CommitUnknown`, and a deadlock retried with `.retry(3)` succeeds with fresh rows.

## Out of scope

- Lock helpers (step 22)

### Reading and writing / Transactions

**R-0435**

```rust
db.transaction(async |tx| {
    tx.insert(&mut p).await?;
    Ok(())
}).await?;

db.isolation(Serializable).retry(3).transaction(async |tx| {   // runs again on 40001 or 40P01
    let mut order = Order { user_id, ..Default::default() };   // built inside
    tx.insert(&mut order).await?;
    Ok(())
}).await?;
```

**R-0436** `tx` has every query call `db` has, and `contracts.md` lists its other methods. `tx.transaction(async |tx| ..)` opens a savepoint, released when the closure returns `Ok` and rolled back to when it returns an error. `tx` has no `isolation` or `retry`, so both are compile errors: the isolation level is fixed before a transaction's first query, and a savepoint can't recover from a deadlock or a serialization failure. Each per-transaction setting on `tx` (`statement_timeout`, `lock_timeout`, `transaction_timeout`) applies at once, as in `tx.lock_timeout(d).await?`, one `SET LOCAL` that holds for the rest of the transaction, through savepoints that are released; rolling back to a savepoint opened before it undoes it, as Postgres does. On Postgres 15 and 16, `tx.transaction_timeout(d)` moves the client-side timer instead. `tx.set_local("app.user", &id)` sets a value for RLS through `set_config(..., true)`, so it takes a parameter, which `SET LOCAL` can't. Owner decision DH5.

**R-1229** **`set_local`'s value is cast.** `set_config` takes `text`, so `tx.set_local` casts its value to its own type and then to `text`, as `set_config(($1::text), (($2::int8))::text, true)`. Owner decision DH2.

**R-0437** **A commit is confirmed, never assumed.** After a failed statement, Postgres turns `COMMIT` into `ROLLBACK` with no error, and tokio-postgres's `commit()` returns `Ok` either way, so a swallowed error would look like a saved transaction. Two checks prevent that:

- **R-0438** Any Postgres error marks the transaction as failed. Further use returns that error, and a closure returning `Ok` still gets it.
- **R-0439** `COMMIT` is sent as `SELECT 1; COMMIT` in one message. In a failed transaction the `SELECT` errors and Postgres skips the `COMMIT`, so this also catches errors morm didn't see, with no extra round trip. morm then rolls back and returns `TransactionAborted`.

**R-0441** **Savepoints** clear the failed mark, except after a deadlock or serialization error, which always fails the whole transaction. Rolling back to a savepoint keeps earlier locks, so a deadlock could repeat, and a serialization failure can't succeed on the same snapshot.

**R-0442** **`.retry(n)`** goes before the closure, with `.isolation` and the per-transaction settings, as in `db.retry(n).transaction(async |tx| ..)`, and takes only a closure that can run again: `AsyncFnOnce(&Tx) -> Result<T> + Clone`, run as a fresh copy on each attempt, so a closure that changes a captured row doesn't compile. Rows are built inside the closure, so each attempt starts fresh and `pre_insert` can't run twice on one row, for example hashing a password twice. Between attempts the transaction rolls back and the connection is released during the jittered backoff.

**R-0444** **Read-only pools:** Postgres refuses `SERIALIZABLE` on a hot standby, so `.isolation(Serializable)` on a `read_only` pool returns `ReadOnly` before reaching the server.

- **R-0985** `.retry(n)` also retries `Error::SchemaChanged`, because the next attempt runs on fresh statements.

- **R-1247** **A hot standby ends a connection inside a transaction.** Replaying DDL on a hot standby, such as a migration's `ALTER TABLE`, ends a standby session that sits in a transaction that read the table, after `max_standby_streaming_delay`, with `FATAL` `40001` `terminating connection due to conflict with recovery`, and its next statement finds the connection closed. That transaction never committed and, on a standby, wrote nothing, and Postgres's own SQLSTATE says it may run again. So when a statement in a transaction finds its connection closed, the error morm's connection task kept, as step 12 says, was a `FATAL` with `40001`, and the statement wasn't the `COMMIT`, morm returns `Error::Serialization` and discards the connection, so `.retry(n)` runs the transaction again on a fresh one. A connection found closed by the `COMMIT` stays `Error::CommitUnknown`, as for any connection lost then. The routine Postgres names for the conflict differs by version, `ProcessInterrupts` on 15 and 16 and `ProcessRecoveryConflictInterrupt` on 17 and 18, so morm reads only the severity and the SQLSTATE. Owner decision SG.

- **R-1271** **What the stale-session machine guarantees, per pool.** Step 14's machine, with this step's rows, keeps these bounds whatever clients send and however many calls run at once, because its steps run one at a time under step 14's stale lock, and this step's simulation asserts them. `W` is `stale_cooldown`, `E` is `stale_pending_expiry`, `L` is PgBouncer's `server_lifetime`, and `max` is the pool's `max`. A change is a schema change committed at `t0`, by a migration or by hand; something is stale when it was prepared or compiled before `t0` and fails or answers wrongly after it; an error is visible when it reaches the caller and a fresh session with a fresh statement wouldn't return it. A process with several pools on one database has each pool's bounds.
  - **Stale statements straight to Postgres:** never visible outside a transaction; inside one each connection's stale copy fails at most once, and none is visible under `.retry(n)` with `n` at least 1; every connection's stale statements are cleared within `W` of the first confirmation or `0A000`.
  - **Stale sessions straight to Postgres:** from `t0 + W` on, never visible outside a transaction, nor inside one under `.retry(n)` with `n` at least 1; without `.retry(n)`, each connection holding one fails one transaction and is replaced. Before `t0 + W` the only visible case is a connection opened between an earlier epoch's start and `t0`, until that epoch ends. When Postgres refuses connections, healing comes within `W` of the first moment it accepts one again.
  - **Stale statements behind PgBouncer:** never visible outside a transaction; inside one the first call per process returns `Error::SchemaChanged`, and none is visible under `.retry(n)` with `n` at least 1; the salt comes within `W` of the first confirmation or `0A000`. A statement run only inside transactions, with no `.retry(n)` and different values each time, returns `Error::SchemaChanged` once per `E` per process, until it runs outside a transaction, `RECONNECT`, or `L`.
  - **Stale sessions behind PgBouncer:** healed at once after `RECONNECT`, and otherwise within `L`; calls that reach another server session are answered meanwhile, and morm adds nothing pool-wide.
  - **A `search_path` set per transaction** over tables of different shapes, which fails a cached statement with `0A000` on a switch with no schema change, costs the same in both modes, because a pending statement runs unnamed straight to Postgres too: never visible outside a transaction; inside one, without `.retry(n)`, at most one failed transaction per statement per `E`, and one more after each pool-wide action, which removes every pending entry and comes at most once per `W` plus once per migration, beyond calls of that statement already running when the first failed; none visible under `.retry(n)` with `n` at least 1; meanwhile the statement runs unnamed while its entry lasts, and its `0A000` requests at most one cache clear or salt per `W`. Each `0A000` requests its action once, at the failure, and a run of the pending statement with the failing call's values, such as the same `id`, is its confirming run and requests nothing more, so values that recur ask for nothing. So one such statement fails about once per `E`, its values recurring or not; with `E` shorter than `W`, once more per `W`, because a failure inside the window its last failure opened asks for an action taken when that window ends, which ends its new entry. Another such statement's `0A000` does request an action, and each action ends every entry, so with more than one such statement the action comes about once per `W`, and each such statement fails about once per `W`, or once per `E` when `E` is the shorter, because then its entry expires before the due action ends it.
  - **Conditions.** "None visible under `.retry(n)`" needs pending entries on, no more than `stale_pending_max` statements pending at once, and `stale_pending_expiry` at least `stale_cooldown`, so that no entry expires before the action its statement's signal asked for is taken; an entry pushed out, or expired first, costs that statement one more `Error::SchemaChanged`. Three more cases each cost a transaction one more `Error::SchemaChanged`, so `.retry(1)` can return it: an attempt checked out before a pool-wide action or a move of `<n>` and run after it, whose statement's entry that removed, runs the stale copy its connection still holds; behind PgBouncer, a marker that returns to a `g<n>` the pool has used before, when a lowered `<n>` is adopted or `<n>` is raised back to it, meets server statements prepared under it before a later change; and an entry that another call's confirming run removes, by an outcome on step 14's no-confirm list or by its own same error, leaves a transaction's next attempt that counted on it to run its stale copy. A stale statement no call ever errors on is the second silent case below.
  - **Churn:** at most one pool-wide action per `W`, plus one per migration; straight to Postgres at most `max` stale-driven replacements per `W`, plus `max` per migration, and at most `2 × max + 2` connection opens from stale handling per `W`, the `+ 2` being the two opens that can fail in an epoch before it's suspended, one beside the old connection and one in its slot on `53300`, plus `2 × max` per migration, because a migration starts a new epoch of up to `max` replacements and lets one *replace* through a closed window; behind PgBouncer no client connection opened or discarded, at most one salt per `W` plus one adoption per migration, and the server statements salts leave bounded by `max_prepared_statements` per server connection. A change of `<n>` other than a migration's, such as a lowered `<n>` step 14's read order adopts after a restore or a failover, counts as a migration in these bounds, and a read of `<n>` that overlaps another never loosens them, because it never counts. Per call, outside a transaction at most one fresh run, one catalog read and, behind PgBouncer for a stale session, one retry on another connection; inside one at most one catalog read after the rollback; and while a statement has a pending entry, each of its runs is unnamed, in both modes, for at most `E` per entry.
  - **Size:** the pool's slots never pass `max`, its connections never pass `max + 1` or the process's budget, and a replacement takes the old connection's slot, so the pool's size is unchanged, except after a failed open once the old connection was closed, which leaves the slot to the pool's next checkout.

  - **Silent wrong answers,** exactly two, both from changes Postgres itself gives no error for. A transaction open across a cutover, morm's or anyone's, whose statements that take no new lock see the catalog as it was. And a type swap made outside morm that keeps the old type without renaming its labels: a cached statement, or plpgsql compiled before the swap, that compares or converts a label both types share answers by the old type's order, with no error. For a statement that ends when it's prepared again, within `W` of the pool's first confirmation or `0A000` after the swap, when its own stale error is repaired, or when its connection is replaced; for plpgsql, when the session ends, straight to Postgres at the connection's replacement and behind PgBouncer at `RECONNECT` or `L`; if nothing in the pool ever errors, when the connection or server session is replaced. In both modes, while the statement has a pending entry its runs are unnamed and right; between entries, and always with entries off, the old order can come back until one of those ends it; and behind PgBouncer a marker that returns to a `g<n>` the pool has used before can bring back a copy prepared under it before the swap, until the next salt. morm's own migrations leave only the first: the reset re-plans every cached statement, and the relabel makes compiled code fail loudly.

  Owner decisions MA, MB, MD, ME, EQ2, `0A000` requesting a repair once, overlapping reads of `<n>` ordered by ticket, an overlapping read never counting, `<n>` only rising in a pool that reaches several servers, and the machine's steps running under a short pool lock.
