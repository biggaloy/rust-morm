# Step 59: Managed enums: stale functions and standbys

- **Phase:** Migrations
- **Depends on:** 53, 12, 39
- **Can run beside:** 08, 09, 19, 20, 21, 22, 23, 24, 25, 26, 27, 42, 43, 44, 45, 46, 47, 48
- **Crates:** `morm-migrate`, `.github`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

Find the code Postgres doesn't track, keep managed functions working through any op that R-1038 covers, check every path of them with `plpgsql_check`, and prove apps recover behind PgBouncer and on a standby.

## Deliverables

- The source search before any op that R-1038 covers, function refresh in that op's transaction, a real call on scratch for every managed function it finds, or step 38's search finds before a retire or a rename, the unmanaged function decision, `plpgsql_check` in its own scratch database with its stops and decisions, the `ci.yml` job for a hot standby, the extension in every CI job R-1083 names, and the `no-plpgsql-check` job

## End-to-end check

On Postgres 15–18, a swap under a plpgsql function that names a removed label proposes the rewritten function, every stale managed function works in open sessions afterwards, and an unmanaged function stops `migrate` until its decision is accepted. The same holds for every other op R-1038 covers, including a composite type recreate, a plain column type change under a trigger, with `--fast` and through the online swap's cutover, and a view's own shape change. A `RETURNS TABLE` body that no longer matches its column stops `makemigrations` with exit code `2`, with no file written, and so does a managed function that still names a column a retire or a rename took away. On Postgres 15–18, a managed plpgsql function whose real call passes, with that column only in a branch the call never reaches, stops `makemigrations` the same way, through `plpgsql_check` in a database of its own, as a scratch user that isn't superuser, and `_morm_proof` keeps its limits.

## Requirements

Copied word for word from the approved plan. Every ID must end with a test tagged with it, as `rules.md` describes. Section references such as "section 8" mean the frozen `plans/rust-morm-plan.md`; everything a step needs is copied here or in `contracts.md`.

### Migrations / Managed enums / Dependents

- **R-1038** **Code Postgres doesn't track.** Before any op, or its inverse, that changes a column's type, changes a composite type's attributes, drops and recreates a type or view, or renames or removes an enum label, step 38's source search also runs, in every schema. It looks for the name of every type and view the op changes or replaces, including a domain or composite type, for each label that changes, and for each table and column whose type changes. For such a table, `pg_trigger` also gives its trigger functions and `pg_depend` gives every function with its row type or that type's array in the signature, and `pg_depend` does the same for a changed type. Every view in this rule includes a materialized view. A hit on a managed function is a decision, `makemigrations` proposes the rewritten function, and R-1066 and R-1076 prove it. A `plpgsql` body can name a removed label, and a `s::text = 'old'` comparison never fails, it just stops matching.

- **R-1039** **Refreshing managed functions.** Every managed plpgsql function R-1038 finds, which includes every one an affected table's triggers call, is refreshed in that op's transaction. A trigger function needs this even when it never names the type: on Postgres 18 a trigger comparing `NEW.s` failed on every call in every open session until it was refreshed.

- **R-1040** **Unmanaged functions** R-1038 finds can't be proven, because scratch can't see them, so they're a decision, repeated in preflight on the live database, that names each one and says it may fail until it's rewritten. The default refuses. Accepting says other services must reconnect, because morm doesn't change unmanaged functions. morm apps recover by themselves from a dropped type and from a changed parameter type, the two errors step 14 replaces a connection on, and must reconnect too after any other change. On a column type change the decision's text also says, in these terms, that a function with a `%TYPE` variable of that column can fail in an open session with `integer out of range` once a value needs the new type, that it keeps failing until the session reconnects, and that apps must reconnect, morm apps included, because ordinary bad data returns the same `22003`, so morm can't safely recover from it.

- **R-1066** **Managed functions are proven by a real call.** Every managed function or procedure R-1038 finds, and every one step 38's source search finds before a retire or a rename, is proven on scratch after `up`, in the with-data proof, once its rows are written. Each call runs in its own transaction that's rolled back, with a 30-second statement timeout. A failure stops `makemigrations` with exit code `2`, naming the function and the error, so a broken one never ships, and the developer fixes the definition in the same migration. A function or procedure callable with no arguments gets `SELECT * FROM f()` or `CALL p()` automatically. If it declares `proof` lines, those run instead, each in its own rolled-back transaction, in the order written, and any failure stops `makemigrations`, naming that `proof`. One that needs arguments and has no `proof` stops `makemigrations` with exit code `2`, asking for one. Nothing is skipped silently. A passing call can't show that a body still means what it did, such as a `s::text = 'old'` comparison, so a hit stays a decision too. A trigger function can't be called directly, so it's proven by a write that fires it: for each managed trigger on it, morm runs an insert, an update of every column or a delete, as the trigger's events need, under `EXPLAIN (ANALYZE, FORMAT JSON)`, after `SET CONSTRAINTS ALL IMMEDIATE`, and the plan must list that trigger. A write that doesn't fire it, such as under a `WHEN`, stops `makemigrations` with exit code `2`, asking for a `proof`, and each `proof` is a write checked the same way. A trigger function with no managed trigger on it, one that only a `TRUNCATE` trigger fires, and an event trigger function need a `proof` too, run as written.

- **R-1067** **What a call may touch.** A rollback undoes what a call does in the database, including volatile functions' writes, session settings and `NOTIFY`, and scratch is thrown away, so a moved sequence or an advisory lock doesn't matter. It can't undo what leaves the server, so morm's own calls and writes run as `_morm_proof`, a role morm creates on scratch if it's missing, which isn't superuser, has rights on every table, sequence and schema in that database, and has no `EXECUTE` on any function from an extension or in a language other than `sql` or `plpgsql`. The scratch user keeps those, and any it can't take from `_morm_proof` stops `makemigrations` with exit code `2`. So a body that reaches `dblink`, an HTTP extension or `COPY ... PROGRAM` fails with `42501`, directly, through another function or through `EXECUTE`, and `makemigrations` stops with exit code `2`, asking for a `proof`. A `SECURITY DEFINER` function, or one in another language, gets past that role, so it always needs a `proof`. Each `proof` is one statement, and it runs with the scratch user's rights, because the developer wrote it and vouches for it: it must not reach outside Postgres, and morm can't check that. One that ends the transaction fails the same way as a failed call. A procedure that commits can't run in a transaction, so on `2D000` morm runs the same call with no transaction on a throwaway copy of that database, made with `CREATE DATABASE ... TEMPLATE` and dropped afterwards.

- **R-1076** **Every path is checked statically.** A real call proves only the path it takes, and Postgres checks a plpgsql statement only when it first runs, so a column dropped from a branch the call misses passes R-1066 with no error. So every managed plpgsql function and procedure R-1066 proves is also checked by `plpgsql_check`, at the same point in the with-data proof. It needs no preload and runs nothing. morm calls `plpgsql_check_function_tb` with the function's `regprocedure`, `fatal_errors => false` and `all_warnings => true`, so overloads stay apart and every finding comes back at once. A procedure, an event trigger function and a polymorphic function need nothing more. A trigger function fails with `22023` `missing trigger relation` with no table, so it's checked once for each managed trigger on it, with that trigger's table as the second argument, plus `oldtable` and `newtable` from `pg_trigger` when the trigger has transition tables, because without them a healthy function gets `42P01`. A trigger function with no managed trigger has no table to check against, so the `proof` R-1066 asks for is all it gets. A `language sql` function fails with `22023` here, so morm never sends one, and R-1066 alone covers it. With no managed plpgsql function in scope, none of this runs, and the extension isn't needed.

**R-1077** **The check has its own database.** It runs in a database of its own on the scratch server, made for that run and dropped afterwards, and the database `_morm_proof` uses never holds the extension, so R-1067 keeps its limits. A scratch user that isn't superuser couldn't take `EXECUTE` on the extension's functions from `_morm_proof`, so R-1067 would stop `makemigrations` if the extension were there. That user also gets `42501` from `CREATE EXTENSION plpgsql_check`, because the extension isn't trusted, so it can't add the extension to a database of its own either. So a superuser makes a template database called `morm_plpgsql_check`, once per scratch server, and installs the extension in that:

```sql
CREATE DATABASE morm_plpgsql_check;
\c morm_plpgsql_check
CREATE EXTENSION plpgsql_check;
\c postgres
ALTER DATABASE morm_plpgsql_check IS_TEMPLATE true ALLOW_CONNECTIONS false;
```

morm makes each check database with `CREATE DATABASE ... TEMPLATE morm_plpgsql_check`, which needs only the `CREATEDB` that `makemigrations` already needs, replays the chain and `up` into it, runs the check as the scratch user, and drops it, after a stop too. A scratch user that's a superuser and finds no template makes it the same way. The extension doesn't go in `template1`, because the database `_morm_proof` uses would get it too.

- **R-1078** **Without the extension.** With a managed plpgsql function in scope, `makemigrations` stops with exit code `2` and writes nothing if the check can't run: `plpgsql_check` isn't in `pg_available_extensions` on scratch, there's no template and the scratch user can't make it, or the clone fails or holds no extension. It names each function and says what to do: install the extension on the scratch server, `postgresql-NN-plpgsql-check` from PGDG, with R-1077's statements printed in full when the scratch user isn't a superuser, or add `proof` lines to the function and accept the risk. Accepting is a decision that names the function and says only the paths its `proof` lines take are proven. The default refuses, and a function with no `proof` can't be accepted, even one R-1066 would call by itself. Accepted functions still get their real calls.

- **R-1079** **Findings stop `makemigrations`.** Any finding at level `error` stops it with exit code `2`, naming the function, the line and the message, with no file written. No other level stops it, apart from R-1080. A healthy function can get a false `error`, from a temp table, a table created in the body or by the caller, a record filled by `EXECUTE`, a record with different fields by branch, `set_config` of `search_path`, or a constant `1/0`. There are two ways past a false one. A `PERFORM 'PRAGMA:...'` line in the function stays there, so later checks pass too, and to Postgres it's only a string, so the function runs with no extension: `PRAGMA:TABLE: x (a int)` declares a table, `PRAGMA:TYPE: r (a int)` declares a record's fields, and `PRAGMA:DISABLE:CHECK` stops checking until its block ends. Or a decision that names the function, the line and the message accepts that one finding for that migration, and its default refuses. Both can hide a real break, which is why the README says so loudly.

- **R-1080** **A narrowing is a decision.** An `int` variable reading a column now `bigint` isn't an error. It works until a value needs the new type, and with default arguments the check reports nothing. With `all_warnings` it's a finding at level `performance`, with SQLSTATE `42804` and detail `cast "bigint" value to "integer" type`. A widening looks the same, so morm reads both type names from the detail, and it's a narrowing when `pg_cast` holds that pair with a `castcontext` other than `i`. Each narrowing is a decision that names the function, the line and both types, and says the function fails once a value doesn't fit. Its default refuses, so `makemigrations` stops with exit code `2` until it's accepted. Every other `all_warnings` finding is ignored. A length or precision limit doesn't show up: `varchar(3)` reading `text` is a cast `pg_cast` calls implicit, and `numeric(6,2)` reading `numeric(20,4)` gave no finding at all.

- **R-1081** **`EXECUTE` needs a `proof`.** The check can't read a query built at run time, and it gives no marker when it skips one. It caught a dropped column in a constant string and in a `format` of constants, and reported nothing for `EXECUTE 'SELECT ' || c || ' FROM t'`. So a body holding the word `EXECUTE` must declare a `proof`, even if it takes no arguments, and without one `makemigrations` stops with exit code `2`, asking for one. The search reads `pg_proc.prosrc`, whole words, in any case, so `EXECUTE` in a comment or a string asks for a `proof` it didn't need, which is fine, because a false hit costs one line.

- **R-1082** **morm won't run a disabled check.** With `plpgsql_check.mode` set to `disabled`, the check returns no findings and only a `NOTICE`, so it looks like a pass. Before checking, in the session that runs the check, morm reads `current_setting('plpgsql_check.mode', true)`, which shows a role or connection setting even before the library loads, and is NULL when nothing sets it. It also reads each function's `pg_proc.proconfig`, because `SET plpgsql_check.mode = 'disabled'` on a function turns the check off for that function alone, and `current_setting` doesn't show it. Either one stops `makemigrations` with exit code `2`, naming the setting and any function.

**R-1083** **The extension in CI.** Every job whose tests run `makemigrations` over a managed plpgsql function installs the extension into its running service, which needs no restart. These are `integration` and `pooler` in `ci.yml`, `property` and `full-chain` in `nightly.yml`, `test` in `release.yml`, and T-0172's job:

```yaml
- name: Install plpgsql_check
  env:
    PG_CONTAINER: ${{ job.services.postgres.id }}
  run: |
    docker exec "$PG_CONTAINER" apt-get update
    docker exec "$PG_CONTAINER" apt-get install -y "postgresql-$MORM_TEST_PG_MAJOR-plpgsql-check"
```

A new `ci.yml` job, `no-plpgsql-check`, runs the plain `postgres` image on Postgres 15–18 with no install step, because R-1078 needs a server without the extension. Its test has its own Cargo feature, `no_plpgsql_check`, with `required-features`, as `pooler` does. The feature sits on `morm-tests`, because `integration` runs `morm-migrate` with `--all-features`. The `ci` job waits for the new job, and `tests/tests/repo_policy.rs` gets its command, with `docker exec ` added to `SETUP`.
