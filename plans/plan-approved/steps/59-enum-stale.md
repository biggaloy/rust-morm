# Step 59: Managed enums: stale functions and standbys

- **Phase:** Migrations
- **Depends on:** 53, 12, 39
- **Can run beside:** 08, 09, 19, 20, 21, 22, 23, 24, 25, 26, 27, 42, 43, 44, 45, 46, 47, 48
- **Crates:** `morm-migrate`, `.github`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

Find the code Postgres doesn't track, keep managed functions working through any op that R-1038 covers, check every path of them with `plpgsql_check`, and prove apps recover behind PgBouncer and on a standby.

## Deliverables

- The walk of R-1038 before any op it covers, function refresh in that op's transaction, a real call on scratch for every managed function it finds, or step 38's search finds before a retire or a rename, the one decision per migration that lists what a column change's walk finds and R-1102 keeps, on scratch and again in preflight, the decisions of every other op, `plpgsql_check` in its own scratch database with its stops and decisions, tests in the `standby` job step 12 adds, the extension in every CI job R-1083 names, and the `no-plpgsql-check` job

## End-to-end check

On Postgres 15–18, a swap under a plpgsql function that names a removed label proposes the rewritten function, every stale managed function works in open sessions afterwards, and an unmanaged function stops `migrate` with exit code `3` until `--decide` accepts its decision. The same holds for every other op R-1038 covers, including a composite type recreate, a plain column type change under a trigger, with `--fast` and through the online swap's cutover, and a view's own shape change. A `RETURNS TABLE` body that no longer matches its column stops `makemigrations` with exit code `2`, with no file written, and so does a managed function that still names a column a retire or a rename took away. On Postgres 15–18, a managed plpgsql function whose real call passes, with that column only in a branch the call never reaches, stops `makemigrations` with exit code `3`, with no file written, through `plpgsql_check` in a database of its own, as a scratch user that isn't superuser, and `_morm_proof` keeps its limits. A column changed from `numeric(6,2)` to `numeric(20,4)` under a managed plpgsql function that names it stops `makemigrations` with exit code `3` until a decision naming the function and both definitions is accepted. Anything else that reaches the column and carries code or an expression, of any kind, goes on that decision's one list for the migration, even when it names neither the table nor the column: a sample is a `numeric(6,2)` variable set through a chain of two functions or by a query a managed function builds with `EXECUTE`, a function that reads a found view, a trigger's `WHEN`, a policy, and an operator in a plpgsql body. So does a view on that table that reads the column through `to_jsonb(x)` and names only another column. A plain index, a `NOT NULL` or a constant default on the column stays off the list, and so does a `DEFAULT now()` on another column, and a column with nothing else opens no decision. A widening's decision carries R-1092's fixed line, and a widening with nothing listed prints it in `makemigrations` output and as a comment in the migration, without stopping. A cycle of calls ends the walk. Preflight repeats the walk on the live database, so what only an unmanaged object shows, such as a caller of an unmanaged function using `EXECUTE`, stops `migrate` on one list, and stops `rollback` until its own answer.

### Migrations / Managed enums / Dependents

- **R-1038** **Code Postgres doesn't track.** Before any op, or its inverse, that changes a column's type, length or precision, changes a composite type's attributes, drops and recreates a type or view, or renames or removes an enum label, morm walks everything that reaches what changed, of any kind, and repeats until nothing new turns up. This is one rule with no list of kinds, so a kind this text never names is found the same way, and every example here is only an example. The walk starts from what the op reports: each table and column whose type, length or precision changes, each type and view it changes or replaces, including a domain or composite type, and the text of each label that changes. Each round sends everything found so far down two routes. The first is `pg_depend`. It gives every object with a row against something found, and the object something found is part of, which is the target of its row with `deptype` `a` or `i`: a default brings in its column, a check, an index, a policy or a trigger brings in its table, a domain's check brings in its domain, and a view's stored query brings in its view. A break carries on from these: once a table's check calls a found function, whatever writes to that table fails too. From a changed column's own table, rows against that column or against the table as a whole count for any object, and rows against its other columns count for any object R-1102 calls code, because a whole row can carry the changed column while `pg_depend` holds only the column a query names. So a view, a function, a trigger, a policy, a rule, a check, a default or an index that carries code is found on that table whatever column it's on, and a plain index or a foreign key on another column isn't found, and doesn't lead on to anything. From any other table or view found, rows against any of its columns count, because what reads any of it is reached. A trigger also brings in its function, because a row reaches that function whatever it names, and that's the only call the walk follows downward. The second route is the source search. It reads `pg_proc.prosrc`, in every schema but those R-1102 leaves out, for the name of everything found, in whole words, in any case, because a body has no `pg_depend` row for what it names, and a name hits every overload of that name. A `BEGIN ATOMIC` body isn't in `prosrc`, so `pg_depend` gives it instead. An object's name is the word a body writes to use it, such as a function's, an aggregate's, a view's, a table's, a type's or a column's name, or a cast's target type. An operator has no word to match, so its symbol is matched as plain text anywhere in a body, which covers `1 ~~~ 2`, `1~~~2` and `OPERATOR(public.~~~)`, and a longer symbol holding it is a false hit. A name is searched once and an object is found once, so each round can only add to a finite set, and the walk stops at the first round that adds nothing. So it ends whatever shape it meets: a cycle of calls, a function that calls itself, or `pg_depend` rows that lead back to something already found. It has no limit on rounds. On a change to a column's type, length or precision, every function and procedure holding the word `EXECUTE`, by R-1081's search, counts as found from the start, even one that names nothing the change touches, because no tool can see what a built query reads, and whatever calls it is then found by its name. The walk follows objects, not values. A function that a found object only passes the value to as an argument, and that names nothing the change touches, isn't found, such as `pass_f` in `pass_f(max(n))`, because a value can flow through arguments, other tables, application code and other services, further than any tool can follow. That's the walk's stated limit: R-1092's fixed line says it on every widening, and the README says why. The preflight of `migrate`, `rollback` and `rehearse` repeats all of this on the live database, and `makemigrations` stores what the walk starts from in `op_data`, for each direction, because preflight doesn't have the models and `rollback` must work from the ledger's `meta.json` when the files are gone. What counts as a hit is what R-1102 keeps, and everything else found is only walked. A hit on a managed function is a decision, `makemigrations` proposes the rewritten function, and R-1066 and R-1076 prove it. A managed object of another kind that's a hit is a decision too, and it has nothing to call, so the decision is all it gets. After a change to a column's type, length or precision all of these are one decision, as R-1092 says, and after any other op, an enum swap included, each keeps its own. A `plpgsql` body can name a removed label, and a `s::text = 'old'` comparison never fails, it just stops matching.

- **R-1039** **Refreshing managed functions.** Every managed plpgsql function R-1038 finds, which includes every one an affected table's triggers call, is refreshed in that op's transaction. A trigger function needs this even when it never names the type: on Postgres 18 a trigger comparing `NEW.s` failed on every call in every open session until it was refreshed. In the same transaction, each unmanaged plpgsql function the walk finds, where the migrating role owns it or is a member of its owner, gets a no-op `ALTER FUNCTION <regprocedure> COST <its current cost>`, and each such procedure `ALTER PROCEDURE <regprocedure> SECURITY <its current setting>`, because a procedure has no cost. Either writes a new catalog row and changes nothing in the definition, so every session compiles the function again on its next call, behind PgBouncer and on a standby too, as a reconnect would. It isn't a change to the unmanaged object, and the object stays in R-1040's decision, because a refresh fixes a stale copy and not the body's logic. On Postgres 15 to 18 the `ALTER FUNCTION` cured a `DECLARE v st` function that the reset doesn't, and on 18.6 `ALTER PROCEDURE ... SECURITY INVOKER` on a procedure that was already `INVOKER` wrote a new row as `ALTER FUNCTION ... COST` does. Owner decision SB.

- **R-1040** **Unmanaged objects** R-1038 finds can't be proven, because scratch can't see them, so each goes in a decision, repeated in the preflight of `migrate`, `rollback` and `rehearse` on the live database, that names it, says whether R-1039 refreshed it, and says it may fail until it's rewritten. On a change to a column's type, length or precision that's R-1099's one list, and after any other op each object has its own decision. The default refuses, so the run stops with exit code `3` until `--decide ID=OPT` on that command accepts it. Accepting says other services must reconnect, because morm doesn't change unmanaged objects. morm apps connected straight to Postgres recover by themselves from a dropped type, a changed parameter type and a retired type's labels, the errors step 14 replaces a connection on, the last by retrying once on a newly opened connection and then replacing the rest of the pool, or, inside a transaction, through `.retry(n)`'s next attempt on a newly opened connection, apart from an enum value a function builds from stored or client text holding `_morm_retired_`, which costs one new connection, or inside transactions at most the pool's connections that were open when it first failed, and again after each migration, and then returns that statement's error at once for 60 seconds, as for up to 60 seconds when the new connection can't open even in place of the stale one, and must reconnect too after any other change. Behind PgBouncer a new client reaches the same server session, so a function R-1039 couldn't refresh stays stale there until PgBouncer replaces that server connection: at the end of the migration, or when the run stops after a committed step, when `[migrations] pgbouncer_admin_urls` lists it, as R-1256 says, and otherwise within its `server_lifetime`, 3600 seconds by default, or at once after `RECONNECT` run by hand; the text says which applies and suggests lowering `server_lifetime`. On a change to a column's type, length or precision the decision's text also says, in these terms, that a function with a `%TYPE` variable of that column can fail in an open session with an error such as `integer out of range`, `numeric field overflow` or `value too long` once a value needs the new definition, that it keeps failing until the session reconnects, and that apps must reconnect, morm apps included, because ordinary bad data returns the same errors, so morm can't safely recover from them. Owner decisions SB and EJ5.
- **R-1256** **Healing server sessions behind PgBouncer.** A function the migration couldn't refresh stays compiled against the old type in each PgBouncer server session that called it, and morm reaches a server session only through a client connection, so it can't end or refresh one. So `[migrations] pgbouncer_admin_urls`, a list of PgBouncer admin-console URLs, such as `["postgres://pgbouncer_admin:${MORM_PGBOUNCER_ADMIN_PASSWORD}@pgb1:6432/pgbouncer"]`, overridden by `MORM_PGBOUNCER_ADMIN_URLS`, a comma-separated list, names every PgBouncer in front of the database; this step adds the key to the config structs, with the same `${VAR}` interpolation as every other URL, and a URL whose database isn't `pgbouncer` is `Error::Config`. When it's set, `migrate`, at the end of every migration it applies, after that migration's last step has committed and the ledger records it as applied, connects to each listed admin console in turn and sends `RECONNECT` as a simple query with no parameters, because the console refuses the extended query protocol, as with `extended query protocol not supported by admin console` on 1.20.1 and 1.26.1, which closes each server connection of every database on that PgBouncer once it's released and opens new ones as clients need them, so a server connection in a transaction is never interrupted and the next one compiles every function fresh. `rollback` and `purge` do the same, because their steps change types too. A run that stops with an error after committing any `tx` step of a migration, such as an online swap whose cutover has committed and whose next step fails, also sends `RECONNECT` to each listed PgBouncer before it exits with that step's error, reporting failed sends as below, because the swapped type is live. - **R-1066** **Managed functions are proven by a real call.** Every managed function or procedure R-1038 finds, and every one step 38's source search finds before a retire or a rename, is proven on scratch after `up`, in the with-data proof, once its rows are written. - **R-1078** **Without the extension.** With a managed plpgsql function in scope, `makemigrations` writes nothing if the check can't run: `plpgsql_check` isn't in `pg_available_extensions` on scratch, there's no template and the scratch user can't make it, or the clone fails or holds no extension. - **R-1079** **Findings stop `makemigrations`.** Any finding at level `error` is an open decision, so it stops `makemigrations` with exit code `3`, naming the function, the line and the message, with no file written. No other level stops it, apart from R-1080. A `PERFORM 'PRAGMA:...'` line in the function stays there, so later checks pass too, and to Postgres it's only a string, so the function runs with no extension: `PRAGMA:TABLE: x (a int)` declares a table, `PRAGMA:TYPE: r (a int)` declares a record's fields, and `PRAGMA:DISABLE:CHECK` stops checking until its block ends. - **R-1080** **A narrowing is a decision.** An `int` variable reading a column now `bigint` isn't an error. - **R-1092** **A changed column is one decision, in either direction.** `plpgsql_check` can't see a length or precision limit, so morm uses what it already knows: the old and new definition of the column the op changes. A widening such as `numeric(6,2)` to `numeric(20,4)` opens one too, because that's the change that breaks a `numeric(6,2)` variable, and it passes the check and every call until a value needs it. A widening's decision also carries this fixed line, word for word and once, however many columns widen: `Values can now exceed the old limit anywhere that reads them, including code morm can't see.` That's the walk's stated limit, in plain words, and it isn't a gap to close: `pass_f(max(n))` isn't found, because R-1038's walk follows objects and not values. The changed column and its table aren't listed, so a change with nothing on the table that R-1102 keeps, on a table and a column nothing names, opens no decision. A migration that widens a column and opens no decision, because nothing is listed, still shows the fixed line, word for word and once, however many columns widen: `makemigrations` prints it in its output and writes it as a comment in the migration file, and it stops nothing, so `makemigrations` exits as it would without it. A managed function on the list is still refreshed by R-1039 and proven by R-1066 and R-1076, what those report stays a decision of its own, because it names a line or a path, and an object another op in the migration hits keeps that op's decision. Its default refuses, so `makemigrations` stops with exit code `3` until it's accepted.

- **R-1102** **What the walk lists.** R-1038's walk can find anything, and it keeps only what carries code or an expression, because nothing else can hold a stale type. That holds for every decision the walk opens, after any op. morm decides it from the catalog, with no SQL parser. An object is kept if it's one of these: a `pg_proc` row of any `prokind`; a view or a materialized view, a `pg_class` row with `relkind` `v` or `m`; a `pg_rewrite` row; a `pg_trigger` row with `tgisinternal` false; a `pg_policy` row; an index whose `pg_index` row has `indexprs` or `indpred`; a `pg_attrdef` row, or a `pg_constraint` row with `conbin`, whose stored expression isn't constant; a `pg_constraint` row whose `conindid` index has `indexprs` or `indpred`, such as an exclusion constraint over an expression; a `pg_statistic_ext` row with `stxexprs`; a partitioned table whose `pg_partitioned_table` row has `partexprs`; a `pg_publication_rel` row with `prqual`; or a row of any catalog this rule doesn't name, so a kind it never names costs one line and is never hidden. An expression is constant when the text of its `adbin` or `conbin` holds no node but `CONST`, `RELABELTYPE` and `FUNCEXPR`, when every `FUNCEXPR` is a cast, with `funcformat` `1` or `2`, and when every `funcid` is below `16384`, so a cast a user wrote counts as code. So `0` on a `numeric(6,2)` column, `'ab'` on a `varchar(3)`, `1.5::numeric(6,2)` and `'{}'` are constant, and `now()`, `nextval(...)`, `1 + 1`, `ARRAY[1, 2]` and a default through a domain aren't. A check that reads a column holds a `VAR` node, so it's never constant, and `CHECK (true)` is. Anything that isn't sure comes out as not constant, which costs one line. On a table with a column whose type, length or precision changes, a default or a check on its other columns that only calls built-ins isn't kept either, because it can't depend on the changed column. That's a `pg_attrdef` row that isn't a generated column's expression, or a `pg_constraint` row with `conbin`, whose `pg_depend` rows against that table all name its other columns, with none against the changed column or the table as a whole, and whose other `pg_depend` rows are each against a sequence or an object with an OID below `16384`, and which calls no built-in that runs query text or reads whole tables. Those built-ins count as code, because what they run can read any column: the `query_to_xml` family, which is `query_to_xml`, `query_to_xmlschema` and `query_to_xml_and_xmlschema`; `schema_to_xml`, `schema_to_xmlschema`, `schema_to_xml_and_xmlschema`, `database_to_xml`, `database_to_xmlschema` and `database_to_xml_and_xmlschema`, which read every table in a schema or the database, so their output holds the changed column's values and the xmlschema forms its type; `table_to_xml`, `table_to_xmlschema` and `table_to_xml_and_xmlschema`, which read the table they're given as a `regclass` that can be built at run time, such as `('t'::text)::regclass`, so no `pg_depend` row names that table; `cursor_to_xml` and `cursor_to_xmlschema`, which read whatever query a cursor opened elsewhere runs, found only by its name; `ts_stat`; and `ts_rewrite(tsquery, text)`. morm finds such a call in the stored expression, as a `FUNCEXPR` in the text of its `adbin` or `conbin` whose `funcid` is one of them, looked up in `pg_catalog` by name and argument types, so it doesn't rest on `pg_depend`. So `DEFAULT now()`, `DEFAULT nextval(...)`, `DEFAULT ARRAY[1, 2]` and `CHECK (a > abs(-1))` on another column aren't kept, while a default or a check there that calls a user's function, or goes through a domain or a user's cast, is, because it holds a `pg_depend` row against that object, and so is one that calls one of those built-ins, such as `CHECK (b > 0 AND query_to_xml('SELECT max(n)::numeric(6,2) FROM t', true, false, '') IS NOT NULL)` on another column `b`. A check holding a whole row, such as `to_jsonb(t)`, has its `pg_depend` row against the table as a whole, and so does a check that reads no column, so both stay on, and so does a generated column. On the changed column itself the rule above stands, so a default there that isn't constant is kept. Not kept, and walked all the same where a row leads to them, because they're how the walk reaches what lies beyond: a table and its columns, a partition, a TOAST table, a type of any kind, such as a row type, an array, a domain or a composite type, a sequence, a plain index, a plain statistics object, a constant default, a `pg_constraint` row with no expression, which is a `NOT NULL`, a primary key, a unique constraint or a foreign key, an operator, a cast and an operator class. A `NOT NULL` has `conbin` null on Postgres 18, where it's a `pg_constraint` row, and it has no row on a table before that, so both come out the same. A function in `pg_catalog` or `information_schema` is never found, by a row, by the source search or through a trigger, because it ships with Postgres, so the `RI_FKey_*` functions behind a foreign key aren't kept, and a word that names one doesn't lead on to everything that calls it. An object Postgres keeps as an internal part of another, with `deptype` `i`, is walked, and it's left off the list only when the object it's part of is on it. So a view's stored query and an exclusion constraint's index are left off, and a generated column's expression stays on, because its column isn't listed. The list test is the one place the walk's code looks at a kind, apart from a trigger's function.

- **R-1081** **`EXECUTE` needs a `proof`.** The check can't read a query built at run time, and it gives no marker when it skips one. - **R-1082** **morm won't run a disabled check.** With `plpgsql_check.mode` set to `disabled`, the check returns no findings and only a `NOTICE`, so it looks like a pass. - **R-1093** **In-comment options are refused.** `plpgsql_check` can read options from a comment, in a line holding `@plpgsql_check_options`, and a body could carry one that hides an `error`. The text in a string stops it too, and taking the text out is the fix. `plpgsql_check` reads a pragma from a string constant after Postgres has decoded it, so an `E'...'` or `U&'...'` literal can spell one with escapes the raw source doesn't show. It reads the `E` and `U&` prefixes in either case, as Postgres does. A plain `'...'` literal is decoded as an `E` string too whenever `standard_conforming_strings` is off for the function: which in morm's check session only the function's own `SET` clause can do, in `pg_proc.proconfig`, which `plpgsql_check` applies before it checks, because the session sets `standard_conforming_strings = on` itself, overriding any database or role default. On Postgres 15 to 18 with `plpgsql_check` 2.10.16, `PERFORM 'PRAGMA:DISABLE:PERFORMANCE_WARNINGS';` in either case, and `plpgsql_check_pragma('disable:performance_warnings')` in a `PERFORM` or a `DECLARE`, each hid R-1080's narrowing, as did `PERFORM E'PRAGMA:DISABLE:PERFORMANCE\x5fWARNINGS';`, `PERFORM U&'PRAGMA:DISABLE:PERFORMANCE\005FWARNINGS';` and `plpgsql_check_pragma(E'disable:performance\x5fwarnings')`, which a search of the raw text misses, while `'disable:performance' || '_warnings'` didn't, because only a constant is read, and nothing morm acts on is a `performance` finding but that one. Owner decisions SH, EF3, EG5 and EH7, with this fix's choices the owner approves through PR #3: plain literals decoded only under the function's own `SET` clause, and the check session setting `standard_conforming_strings = on` itself.
