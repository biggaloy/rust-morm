# Step 39: Safe forms

- **Phase:** Migrations
- **Depends on:** 38
- **Can run beside:** 08, 09, 19, 20, 21, 22, 23, 24, 25, 26, 27, 42, 43, 44, 45, 46, 47, 48
- **Crates:** `morm-migrate`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

Default to migrations that are safe on live tables.

## Deliverables

- Every row of the safe forms table, batched backfills, sync triggers for type changes, carrying a managed view through a column swap's cutover, building a materialized view beside the old one and swapping it at cutover, the shadow column's definitions read from Postgres on scratch, the check for the same meaning, `--fast`, refusal of key type changes

## End-to-end check

Each safe form runs under live traffic with no long lock, and no write is lost during a type-change copy. A managed view above a swapped column serves reads through the cutover and ends on the new column, and a materialized view above it is built beside the old one and swapped in the same cutover of milliseconds.

### Migrations / Safe forms are the default on existing tables

| ID | Change | Generated steps |
|---|---|---|
| R-0559 | Add FK or CHECK | `ADD ... NOT VALID`, then `VALIDATE` in a **separate** transaction (one transaction would hold the lock through the scan) |
| R-0560 | Add unique | `CREATE UNIQUE INDEX CONCURRENTLY`, then `ADD CONSTRAINT ... USING INDEX` |
| R-0561 | Add primary key | As above, after the `Set NOT NULL` steps for any nullable key column. `ADD PRIMARY KEY USING INDEX` otherwise runs `SET NOT NULL` itself, which scans the table under the strongest lock |
| R-0562 | Add index | `CREATE INDEX CONCURRENTLY` (no-tx) |
| R-0563 | Set NOT NULL | Batched backfill, `CHECK NOT VALID`, `VALIDATE`, `SET NOT NULL`, drop the check |
| R-0564 | Add NOT NULL column | Add nullable, batched backfill, then as above |
| R-0565 | Add column with a volatile default, such as `gen_random_uuid()` | Add with no default, `SET DEFAULT` so new rows get it, then batched backfill. A constant default is instant and stays one step |
| R-0566 | Type change that is lossy or rewrites the table, such as `int` to `bigint` | New column, sync trigger so writes during the copy aren't lost, batched copy, swap (old column retired) |
| R-0567 | Type change on a key referenced by foreign keys | Refused with guidance on a live table, because every referencing column and the identity sequence must change together. `--fast` does it in one rewrite for small tables or maintenance windows. An online form is in `later-defo-build.plan` |
| R-0568 | Widening type change | In place when no rewrite is needed |

**R-0569** New tables use plain DDL in one transaction. `--fast` allows the simple forms for small tables or maintenance windows.

**R-1061** **A view above an online column swap.** R-0566's swap carries a managed view above the column instead of stopping at the retire. Its cutover is one short transaction with `lock_timeout`, retried with backoff. It takes each carried view's lock with its own `DROP VIEW`, from the outside in, dropping anything carried above a view before that view, then locks the table and walks `pg_depend` again. A reader locks the view first, so the table comes last, and it never runs `LOCK TABLE` on a view, because that takes every table under the view at once and deadlocked. It drops the sync trigger and any carried objects left, from the outside in, renames the old column to its retired name and the new column to the real name, and recreates the objects from their declarations in the fixed kind order, keeping their owner, comment and grants, so the view reads the new column. Its inverse carries them back the same way. A view no model declares, materialized or not, is refused with the full list before the swap's first step, and `migrate` preflight repeats that. An object the walk can't carry that appears during the copy stops the cutover, which changes nothing: the second walk finds one on the column, and `DROP VIEW`, which never uses `CASCADE`, refuses one on a carried view with `2BP01`. A view that would still read the retired column once recreated, materialized or not, such as `SELECT *`, is refused the same way, which the scratch proof finds in `pg_depend`. A materialized view anywhere above the column follows R-1063. `--fast` still handles all of these in one transaction.

**R-1063** **A materialized view above an online column swap.** Recreating one would run its query under the table's lock, so it's built beside the old one. After the copy, `VALIDATE` and `ANALYZE`, as late as possible before the cutover, a step of its own creates it under a temporary name on the shadow column, using R-1064's query, with its indexes, owner, comment and grants, and runs `ANALYZE`. Reads and writes carry on during the build. A view, materialized view or `BEGIN ATOMIC` function between it and the column is built beside it in the same way, innermost first. The cutover swaps each one by rename: the old one is retired, as step 38 says, and the new one and its indexes take the real names. `LOCK TABLE` refuses a materialized view, so the rename takes its lock, from the outside in, before the table's. A view, function or other object above it would stay on the old copy, so R-1061 carries it in the same cutover, recreating it on the new one, and a view no model declares is refused. A rebuild opens a decision naming the view: its contents will come from today's table, and the old copy stays until `purge`, because a view can hold rows the table no longer has, and one may be frozen on purpose. One created `WITH NO DATA` holds nothing, so it's built `WITH NO DATA`, stays unpopulated and opens no decision. `--resume` drops an unfinished build and builds again, so the new copy stays as late as possible, and `rollback --failed` drops it and leaves the old one in place.

**R-1064** **Text on the shadow column.** morm has no SQL parser and replaces no names in text, so R-1063's text comes from Postgres. In a throwaway scratch database, in the state the cutover leaves, with the old column under its retired name and in the live table's column order, morm creates each object from its declaration. It renames the new column to the shadow column's name and each object built beside to its temporary name, sets an empty `search_path` so every name is qualified, and reads `pg_get_viewdef`, or `pg_get_functiondef` for a `BEGIN ATOMIC` function. Postgres holds a view's columns by number, so this carries a same-named column on a second table, `JOIN ... USING (n)`, `NATURAL JOIN`, and the column inside a CTE or a subquery, keeps every output column's name, and leaves strings and comments alone. The scratch proof confirms the result: after cutover, each definition must match the one built from the models, output names and types included, under R-1070 where the text differs. A wrong definition fails the proof and writes no file.

**R-1070** **Same meaning when the text differs.** Postgres keeps an alias once it has one, so after cutover a `USING` view reads `FROM (t t JOIN t2 USING (n))` where the models' reads `FROM (t JOIN t2 USING (n))`, and a later rename of another column on that table prints the whole column list again. The view is the same, so neither is a change. Where the text of a view or `BEGIN ATOMIC` function differs from the model's, morm checks the meaning on the database that holds it. It builds the model's definition there under a temporary name, `WITH NO DATA` for a materialized view, reads both stored query trees, `pg_rewrite.ev_action` or `pg_proc.prosqlbody`, removes every `location`, `stmt_location`, `stmt_len`, `isNatural`, `alias` and `eref` field, compares what's left, and drops the temporary object. Both trees are on one database, so tables, columns and types compare by number, and the join's `usingClause` and every output name stay in. Equal is a match. Anything else is a difference, and so is a model definition that can't be built there. In the scratch proof a difference fails the proof and writes no file. Step 30's diff runs this check before it counts a text difference as a change, so `makemigrations` proposes nothing for a matching view. A match found while a migration is made stores the two texts, the database's and the model's, in `op_data`, and `migrate` copies that pair to the ledger. `verify` can't build anything on a live database, so it treats a live view as matching when its text and the model's are a pair the ledger holds, and any other text is drift. On a `pg_major` mismatch, step 34's replay runs the check in its temporary database in place of the pair.

**R-1071** **Column positions.** A `USING` view's text holds a column list, such as `t t(id, _morm_retired_0007_n, note, n)`, and Postgres applies it by position, so it's only right if the live table's columns sit where scratch's do. An unmanaged column on the live table moved them, and the view read that column and returned wrong rows with no error. morm finds a list with no parser: the object's stored query tree has an `alias` field with `colnames`. So `makemigrations` stores in `op_data` the columns of each table with a list, in order, and the columns each built object reads, from `pg_depend`. `migrate` preflight refuses with exit code `2`, naming the table and saying `--fast` handles it, when the live table's columns differ from the stored list, before the swap's first step. Each build's own transaction reads `pg_depend` for the new object, and if it reads any other column, the transaction rolls back and the migration stops as `failed`, because a column can change after preflight.
