# Step 39: Safe forms

- **Phase:** Migrations
- **Depends on:** 38
- **Can run beside:** 08, 09, 19, 20, 21, 22, 23, 24, 25, 26, 27, 43, 44, 45, 46, 47, 48
- **Crates:** `morm-migrate`, `morm-admin`, `morm-core`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

Default to migrations that are safe on live tables.

## Deliverables

- Every row of the safe forms table, batched backfills, sync triggers for type changes, carrying a managed view through a column swap's cutover, building a materialized view beside the old one and swapping it at cutover, the shadow column's definitions read from Postgres on scratch, the check for the same meaning, a cutover that gives way to live transactions, its three settings and `--terminate-blockers`, `--fast`, refusal of key type changes across families
- The copy's key for a table with no primary key, the collation named in every type change and shadow column, a collation change on its own going through the online swap, and the zone decision for a change between `timestamp` and `timestamptz`
- Refusal of partitioned and inherited tables online, the shared index check after every `ALTER COLUMN ... TYPE`, and the swap's indexes under `_morm_new_<name>`
- Inherited columns changed only through their top parent, foreign keys dropped and added back around an index rebuild, the check for values that would merge on a unique index, and refusal of partitioned tables in the other safe forms
- Refusal of a `NOT VALID` foreign key from a partitioned table on Postgres 15 to 17, and every statement Postgres carries to children and partitions run once on the top parent, refused when it would reach a child or a partition no model declares, and a partition's `pk` added or removed with no statement on the partition

## End-to-end check

Each safe form runs under live traffic with no long lock, and no write is lost during a type-change copy. A managed view above a swapped column serves reads through the cutover and ends on the new column, and a materialized view above it is built beside the old one and swapped in the same cutover of milliseconds. A cutover that can't get in stops with nothing changed and no app transaction killed, and running it again finishes.

### Migrations / Safe forms are the default on existing tables

| ID | Change | Generated steps |
|---|---|---|
| R-0559 | Add FK or CHECK | `ADD ... NOT VALID`, then `VALIDATE` in a **separate** transaction (one transaction would hold the lock through the scan) |
| R-0560 | Add unique | `CREATE UNIQUE INDEX CONCURRENTLY`, then `ADD CONSTRAINT ... USING INDEX` |
| R-0561 | Add primary key | As above, after the `Set NOT NULL` steps for any nullable key column. `ADD PRIMARY KEY USING INDEX` otherwise runs `SET NOT NULL` itself, which scans the table under the strongest lock |

| R-0565 | Add column with a volatile default, such as `gen_random_uuid()` | Add with no default, `SET DEFAULT` so new rows get it, then batched backfill. A constant default is instant and stays one step |
| R-0566 | Type change that is lossy or rewrites the table, such as `int` to `bigint` | New column, sync trigger so writes during the copy aren't lost, batched copy up to the highest key read once the trigger has committed, swap (old column retired). `CREATE TRIGGER` waits for every open write, so any row above that bound was written through the trigger, while a copy that walked until nothing was left would chase new inserts for as long as they came |
| R-0567 | Type change on a key referenced by foreign keys | Every referencing column and the identity sequence must change together. **R-0569** New tables use plain DDL in one transaction. `--fast` allows the simple forms for small tables or maintenance windows.

**R-1061** **A view above an online column swap.** R-0566's swap carries a managed view above the column instead of stopping at the retire. Its cutover is one short transaction that gives way to live transactions, as R-1072 says. It takes each carried view's lock with its own `DROP VIEW`, from the outside in, dropping anything carried above a view before that view, then locks the table and walks `pg_depend` again. A reader locks the view first, so the table comes last, and it never runs `LOCK TABLE` on a view, because that takes every table under the view at once and deadlocked. It drops the sync trigger and any carried objects left, from the outside in, renames the old column to its retired name and the new column to the real name, and recreates the objects from their declarations in the fixed kind order, keeping their owner, comment and grants, so the view reads the new column. Its inverse carries them back the same way. A view no model declares, materialized or not, is refused with the full list before the swap's first step, and `migrate` preflight repeats that. An object the walk can't carry that appears during the copy stops the cutover, which changes nothing: the second walk finds one on the column, and `DROP VIEW`, which never uses `CASCADE`, refuses one on a carried view with `2BP01`. A view that would still read the retired column once recreated, materialized or not, such as `SELECT *`, is refused the same way, which the scratch proof finds in `pg_depend`. A materialized view anywhere above the column follows R-1063. `--fast` still handles all of these in one transaction.

**R-1063** **A materialized view above an online column swap.** Recreating one would run its query under the table's lock, so it's built beside the old one. After the copy, `VALIDATE` and `ANALYZE`, as late as possible before the cutover, a step of its own creates it under a temporary name on the shadow column, using R-1064's query, with its indexes, owner, comment and grants, and runs `ANALYZE`. Reads and writes carry on during the build. A view, materialized view or `BEGIN ATOMIC` function between it and the column is built beside it in the same way, innermost first. The cutover swaps each one by rename: the old one is retired, as step 38 says, and the new one and its indexes take the real names. `LOCK TABLE` refuses a materialized view, so the rename takes its lock, from the outside in, before the table's. A view, function or other object above it would stay on the old copy, so R-1061 carries it in the same cutover, recreating it on the new one, and a view no model declares is refused. A rebuild opens a decision naming the view: its contents will come from today's table, and the old copy stays until `purge`, because a view can hold rows the table no longer has, and one may be frozen on purpose. One created `WITH NO DATA` holds nothing, so it's built `WITH NO DATA`, stays unpopulated and opens no decision. `--resume` drops an unfinished build and builds again, so the new copy stays as late as possible, and `rollback --failed` drops it and leaves the old one in place.

**R-1064** **Text on the shadow column.** morm has no SQL parser and replaces no names in text, so R-1063's text comes from Postgres. In a throwaway scratch database, in the state the cutover leaves, with the old column under its retired name and in the live table's column order, morm creates each object from its declaration. It renames the new column to the shadow column's name and each object built beside to its temporary name, sets an empty `search_path` so every name is qualified, and reads `pg_get_viewdef`, or `pg_get_functiondef` for a `BEGIN ATOMIC` function. Postgres holds a view's columns by number, so this carries a same-named column on a second table, `JOIN ... USING (n)`, `NATURAL JOIN`, and the column inside a CTE or a subquery, keeps every output column's name, and leaves strings and comments alone. The scratch proof confirms the result: after cutover, each definition must match the one built from the models, output names and types included, under R-1070 where the text differs. A wrong definition fails the proof and writes no file.

**R-1070** **Same meaning when the text differs.** Postgres keeps an alias once it has one, so after cutover a `USING` view reads `FROM (t t JOIN t2 USING (n))` where the models' reads `FROM (t JOIN t2 USING (n))`, and a later rename of another column on that table prints the whole column list again. The view is the same, so neither is a change. Where the text of a view or `BEGIN ATOMIC` function differs from the model's, morm checks the meaning on the database that holds it. It builds the model's definition there under a temporary name, `WITH NO DATA` for a materialized view, reads both stored query trees, `pg_rewrite.ev_action` or `pg_proc.prosqlbody`, removes every `location`, `stmt_location`, `stmt_len`, `isNatural`, `alias` and `eref` field, compares what's left, and drops the temporary object. Both trees are on one database, so tables, columns and types compare by number, and the join's `usingClause` and every output name stay in. Equal is a match. Anything else is a difference, and so is a model definition that can't be built there. In the scratch proof a difference fails the proof and writes no file. Step 30's diff runs this check before it counts a text difference as a change, so `makemigrations` proposes nothing for a matching view. A match found while a migration is made stores the two texts, the database's and the model's, in `op_data`, and `migrate` copies that pair to the ledger. `verify` can't build anything on a live database, so it treats a live view as matching when its text and the model's are a pair the ledger holds, and any other text is drift. On a `pg_major` mismatch, step 34's replay runs the check in its temporary database in place of the pair.

**R-1071** **Column positions.** A `USING` view's text holds a column list, such as `t t(id, _morm_retired_0007_n, note, n)`, and Postgres applies it by position, so it's only right if the live table's columns sit where scratch's do. An unmanaged column on the live table moved them, and the view read that column and returned wrong rows with no error. morm finds a list with no parser: the object's stored query tree has an `alias` field with `colnames`. So `makemigrations` stores in `op_data` the columns of each table with a list, in order, and the columns each built object reads, from `pg_depend`. `migrate` preflight refuses with exit code `2`, naming the table and saying `--fast` handles it, when the live table's columns differ from the stored list, before the swap's first step. Each build's own transaction reads `pg_depend` for the new object, and if it reads any other column, the transaction rolls back and the migration stops as `failed`, because a column can change after preflight.

**R-1072** **A cutover gives way.** A cutover can deadlock with an app transaction: one that touched the table and then reads the view waits on the cutover, while the cutover waits on it. Once either has waited for `deadlock_timeout`, Postgres kills one of them. So by default a migration never kills a live app transaction. Each attempt runs with `lock_timeout` set to `[migrations] cutover_lock_timeout`, default `"50ms"`, well under `deadlock_timeout`, so the attempt rolls back before Postgres looks for a deadlock. An attempt that hits the timeout with `55P03`, or that Postgres picks as a deadlock's victim with `40P01`, changes nothing, and morm waits `cutover_pause`, default `"250ms"`, and tries again, up to `cutover_attempts`, default `600`, so a cutover that can't get in gives up after about 3 minutes. The three settings are plain values in `morm.toml`, and they hold for the cutover's inverse too. An attempt holds its first lock through every later wait, so `migrate` and `rollback` preflight read the server's `deadlock_timeout`, and each lock in that cutover waits `min(cutover_lock_timeout, deadlock_timeout / (2 × locks))`, where `locks` is the number of locks the cutover takes. So a whole attempt stays under half of `deadlock_timeout` however many locks it takes, with no setting to change, and when that wait is shorter than `cutover_lock_timeout`, the output says so, naming the three numbers and the wait. Postgres rounds `lock_timeout` to a whole millisecond and reads 0 as no timeout, so morm rounds the wait down to a whole millisecond, and when that's under 1 ms preflight refuses with exit code `2` before the swap's first step, naming the three numbers. The message says how to go on: raise `deadlock_timeout`, or `cutover_lock_timeout` when it's set under 1 ms, or write the migration with `makemigrations --fast` for a maintenance window. After the last attempt the cutover step stops as `failed` with exit code `2` and nothing changed, saying how many attempts it made and that `migrate --resume` carries on from there. The sync trigger stays, so the shadow column keeps up while the migration waits. `--resume` starts this step again with a full set of attempts, after dropping and rebuilding any materialized view built beside the old one, because a copy that sat waiting is no longer as late as possible. `rollback --failed` also still works. `--terminate-blockers`, on `migrate` and `rollback`, is the one way to push a cutover through. While an attempt runs, a second connection calls `pg_terminate_backend` every 10 ms on every backend `pg_blocking_pids` names for it, and each one goes in `_morm.history` with its user and application name. Those transactions die, and their apps lose the connection. It acts only during a cutover, never in any other step, and each lock waits `cutover_lock_timeout`, with no shorter wait and no `deadlock_timeout` check. A longer wait is no substitute, because Postgres may pick the cutover as the victim every time. A role that may not terminate a backend gets `42501`, and the step stops as `failed`, changing nothing. `pg_signal_backend` gives that right.

**R-1133** **The copy's key.** R-0566's batched copy walks by the table's primary key. A table with none is walked by a unique `NOT NULL` key: a unique constraint or unique index with no predicate and no expression, whose columns are all `NOT NULL`, the one with the fewest columns, then the first by name, with the cursor and the bound on it as on a primary key. A table with neither is refused online with exit code `2` before the swap's first step, naming the table and saying `--fast` handles it, because the copy would have nothing to bound it or resume it by.

**R-1134** **The collation is always named.** `ALTER COLUMN ... TYPE` with no `COLLATE` resets the column's collation to its type's default: on Postgres 18.6 and 17.11, a `"C"` column changed to `varchar(3)`, and a column with a nondeterministic collation changed to `text`, each lost its collation. So every `ALTER COLUMN ... TYPE` morm writes, in place or under `--fast`, names the column's collation with `COLLATE`, and so does every shadow column the online swap adds, so a type change never changes a collation the models didn't change. A collation change on its own, with the type kept, leaves the table's file alone but rebuilds every index on the column under `ACCESS EXCLUSIVE`, so on any column of an existing table it uses R-0566's online swap like a rewriting type change, and `--fast` does it in place. On a key that foreign keys reference, it's step 60's form.

**R-1135** **A change between `timestamp` and `timestamptz` asks for the zone.** Postgres converts each value through the `TimeZone` of the session that runs the change, with no error: on Postgres 18.6 and 17.11 the same stored `12:00` became `12:00` UTC under `UTC` and `17:00` UTC under `America/New_York`, so the same migration would give different data on different hosts. So `makemigrations` opens a decision for each column that changes between the two, in either direction, naming the table, the column and both types, and asking which zone the stored values are in. The answer is given as `--decide ID=<zone>` and checked against `pg_timezone_names` on scratch, and the migration then changes every such column with `USING <col> AT TIME ZONE '<zone>'`, so the result doesn't depend on the session. The online swap's copy and sync trigger convert through the same zone, and the down converts back through it. On a key that foreign keys reference, this change is across families, so it's refused on a live table and `--fast` runs it, as R-0567 says.

**R-1151** **Partitioned and inherited tables.** R-0566's online swap, and so R-1134's collation change through it, refuses a partitioned table, a partition, and a table in old-style inheritance, as a parent or as a child, with exit code `2` before the swap's first step, naming the table and its partitions, parent or children, and saying `--fast` handles it, under R-1157's rule for inherited columns. `migrate` and `rollback` preflight check the live database, and the cutover reads `pg_inherits` again under its lock and stops with nothing changed if the table has gained a parent, a child or a partition since. On Postgres 18.6, `CREATE INDEX CONCURRENTLY` on a partitioned table failed with `cannot create index on partitioned table ... concurrently`, `ADD COLUMN` on a partition failed with `cannot add column to a partition`, `ADD COLUMN` on an inheritance parent added the column to its child, `ALTER TABLE ONLY` was refused with `column must be added to child tables too`, and changing an inherited column's type on a child or a partition alone was refused with `cannot alter inherited column`, while the same change on the parent changed it on every child. So the shadow column would land on every child, and the swap can't change a child's column on its own.

**R-1152** **Indexes after a type change.** `ALTER COLUMN ... TYPE` rebuilds a column's indexes from their stored definitions without checking them against the models: on Postgres 18.6 and 17.11 it silently swapped an explicit `int4_ops` for `bigint`'s default class and kept `varchar_pattern_ops` on a column changed to `text`, so an index could end unlike the models with no error. So every `ALTER COLUMN ... TYPE` morm writes, in place, under `--fast`, in a `down.sql` or in a later step's one-transaction form, is followed by one shared check. Once the change has run on scratch, `makemigrations` reads `pg_get_indexdef` for each index on that table that holds a changed column, compares it with the definition the target schema builds on scratch, the models' for an up and the chain's before the migration for a down, and the migration recreates each that differs from the target's definition. Under `--fast` and in a one-transaction form, it's dropped and created again in the same transaction, right after the change, under the lock that transaction already holds. In place on a live table, it's rebuilt as R-0319 says, with no long lock: `CREATE INDEX CONCURRENTLY`, or `CREATE UNIQUE INDEX CONCURRENTLY` for a unique one, under the name `_morm_new_<name>`, made from its name `<name>` through the 63-byte name function, then `DROP INDEX CONCURRENTLY` on the old one and a rename to `<name>`, and a build left `indisvalid = false` is dropped and built again on `--resume`. An index that a primary key or unique constraint owns can't be dropped on its own, so in one short transaction that gives way under R-1072's rule, its constraint is dropped and attached again to the new index with `ADD CONSTRAINT <name> PRIMARY KEY USING INDEX` or `UNIQUE USING INDEX`, which takes no scan, because the columns keep their `NOT NULL`. An index a foreign key references is rebuilt as R-1158 says, and one on a partitioned table as R-1160 says. An index that matches is left alone. Nothing is dropped with `CASCADE`. An `ops` that doesn't accept the new type fails the target's build on scratch, naming the index and its `ops`, as `operator class "int4_ops" does not accept data type bigint`, so `makemigrations` writes no file. The online swap runs no `ALTER COLUMN ... TYPE`, and builds its indexes from scratch's definitions, as R-1153 says. Steps 52 and 60 run this same check after the one-transaction enum swap and after `--fast` on a referenced key.

**R-1153** **The swap's indexes.** R-0566's swap builds each index that holds the swapped column again on the shadow column, after the copy, with `CREATE INDEX CONCURRENTLY`, or `CREATE UNIQUE INDEX CONCURRENTLY` for a unique one, so writes carry on, taking its text from Postgres on scratch by R-1064's route, with `pg_get_indexdef`. Each is named `_morm_new_<name>`, made from the real index's name `<name>` through the 63-byte name function. At cutover, the retire drops the old indexes, as step 38 says, each new one is renamed to `<name>`, and a primary key or unique constraint is re-attached with `ADD CONSTRAINT <name> PRIMARY KEY USING INDEX` or `UNIQUE USING INDEX`. Until then a write can collide on a shadow unique index alone, when its new value equals another row's only once converted, such as `1.0051` and `1.0149` going to `numeric(10,2)` as `1.01`, and step 14's `Error::Unique` maps the name `_morm_new_<name>` to the field of `<name>`, so the error reads as one on that field. On Postgres 18.6, such a write failed with `duplicate key value violates unique constraint "_morm_new_<name>"` while the old column's index held both values.

**R-1157** **Inherited columns.** Postgres changes an inherited column only through the table it comes from. On Postgres 18.6 and 17.11, `ALTER COLUMN ... TYPE` on a child's or a partition's inherited column alone failed with `cannot alter inherited column`, and so did a collation change, while the same change on the top parent changed it on every child, grandchild and partition. `ALTER TABLE ONLY` on the parent was refused with `type of inherited column ... must be changed in child tables too`, and a column a child inherits from two parents couldn't be changed from either, each failing with `cannot alter inherited column ... of relation`. So every `ALTER COLUMN ... TYPE` morm runs, in place, under `--fast`, in a `down.sql` or in a later step's one-transaction form, changes an inherited column only through its top parent, in one `ALTER`. Scratch is built from the models, so it has no inheritance, and `migrate` and `rollback` preflight read `pg_inherits` and `pg_attribute` on the live database for every column the migration changes. A column on a table with children or partitions, or one a table inherits, changes only when the migration makes the same change, to the same type and collation, on its top parent and on every child and partition the change reaches, each declared by a model. Then preflight runs the top parent's step where the first step in that tree sits. That step takes the top parent's lock, reads `pg_inherits` again and stops with nothing changed if the tree has changed since preflight, then runs the one `ALTER`. Each other step in the tree finds by its precondition that its column already has the new type and collation, so it changes nothing apart from R-1152's check on its own table. Otherwise preflight refuses with exit code `2` before the first step, changing nothing, naming the column, its top parent and every child and partition the change reaches: a change to a child's or a partition's inherited column without the same change on its top parent, a change that would reach a child or a partition no model declares or whose model doesn't make the same change, and a change to a column inherited from more than one parent, which no one `ALTER` can make. morm never changes a table it doesn't manage, and Postgres would change such a child with no model asking for it. The message says to declare every child and partition in the models with the same change. A column a child adds of its own isn't inherited, so it changes on that child like a column of any other table.

**R-1158** **Foreign keys on a rebuilt index.** A foreign key depends on the unique index it references, so Postgres won't drop that index, or the primary key or unique constraint that owns it, while the foreign key is there. On Postgres 18.6 and 17.11, a `varchar(10)` key with a unique index on `varchar_pattern_ops`, referenced by a foreign key, kept that class when changed in place to `text`, and `DROP INDEX` failed with `cannot drop index ... because other objects depend on it`, and `DROP CONSTRAINT` on a referenced primary key with `2BP01`. A foreign key added beside the old one, `NOT VALID`, with a column list or without, was tied to the old index, not to a new one built beside it, so Postgres gives no way to move a foreign key to a new index while the old one is there. So when R-1152's check must rebuild an index that a foreign key references, morm drops and adds back each such foreign key around the rebuild, in every form, never with `CASCADE`. Under `--fast` and in a one-transaction form, in the same transaction: it drops them, drops and creates the index again, attaching its primary key or unique constraint to it, and adds them back, validated, under the lock it already holds. In place on a live table, with no long lock and no moment when a row that breaks a foreign key could be written:

1. `no-tx`: build the new index as R-1152 says, under `_morm_new_<name>`.
2. `tx`: one short transaction that gives way to live transactions under R-1072's rule, with its settings, its scaled wait and `--terminate-blockers`. Lock the referenced table `ACCESS EXCLUSIVE`, then each referencing table in name order, drop the foreign keys, drop the old index or its constraint, rename the new index to `<name>`, attaching a primary key or unique constraint to it with `ADD CONSTRAINT <name> PRIMARY KEY USING INDEX` or `UNIQUE USING INDEX`, and add each foreign key back with its name, columns, actions, `MATCH` type and deferrability, `NOT VALID`. Every statement is a catalog change, with no scan.
3. `tx` per foreign key: `VALIDATE`, which takes `SHARE UPDATE EXCLUSIVE` on the referencing table and `ROW SHARE` on the referenced one, so writes carry on.

The new foreign keys hold from the moment step 2 commits, so every write after it is checked, and every row before it was checked by the old ones, with no write in between while step 2 held its locks. `NOT VALID` only skips the scan of rows already there, which `VALIDATE` then proves. A foreign key from a table no model declares, or one the models don't declare, is refused with exit code `2` before the first step, naming it with `pg_get_constraintdef`, because morm would drop and recreate a constraint it doesn't manage: `makemigrations` checks scratch, and `migrate` and `rollback` preflight check the live database. On `--resume`, a rerun of step 2 reads the catalog first and does only what's missing, and a foreign key left `NOT VALID` is validated again. Measured on Postgres 18.6 and 17.11, with a key table of 200,000 rows referenced by two tables of 200,000 rows with `ON DELETE CASCADE`, under 8 `pgbench` clients nonstop inserting a parent and its children, moving a child to another parent, joining, and deleting the parent: step 2 got in on its first attempt, each of its statements took under 1 ms, the two `VALIDATE`s took 200 to 240 ms together, no app transaction failed, no row was orphaned, an orphan inserted between steps 2 and 3 was refused, and both foreign keys ended validated on the new primary key under their own names. A `DEFERRABLE INITIALLY DEFERRED` foreign key came through the same way. On 18.6 the key's `NOT NULL` constraint stayed when the primary key was dropped, and on 17.11 `attnotnull` did, so attaching the primary key again took no scan.

**R-1159** **Values that would merge on a unique index.** A swap's conversion can make two values equal, such as `1.0051` and `1.0149` both becoming `1.01` in `numeric(10,2)`, `'01'` and `'1'` both becoming `1` from `text` to `integer`, `'abc'` and `'ABC'` under a case-insensitive collation, or `02:30` and `03:30` on the day clocks go forward, both becoming the same `timestamptz`. On a unique index that holds the column, R-1153's concurrent build would then fail mid-run and leave the index invalid. So before R-0566's swap changes anything, it runs one `GROUP BY` for each unique index that holds a swapped column, in a read-only transaction with `statement_timeout` off, and refuses with exit code `2` any values that would merge, naming the table, the index, the values and how many rows hold each. No answer can make two rows one, so it's a refusal, not a decision. The query is built with no SQL parser. Its keys and predicate are the shadow index's, read on scratch with `pg_get_indexdef` and `pg_get_expr` as R-1153 reads them, and it reads from a subquery that adds the shadow column under its own name, with the value the copy gives it: the cast with its collation, the migration's `USING`, or R-1135's zone. A row with a null in any key is left out, unless the index is `NULLS NOT DISTINCT`. `migrate` and `rollback` preflight run it. When the new type doesn't exist yet, because the migration creates it, the swap's first step runs it in its own transaction once the type exists, and a merge rolls that transaction back and stops the migration as `failed` with exit code `2`, before the swap has changed a table. It's skipped only for a change between `smallint`, `integer` and `bigint`, where each value keeps its number or fails with an error. A merge written after the check fails the concurrent unique build, which stops that step as `failed`, and `rollback --failed` drops the shadow objects. Until cutover, a write that would merge gets `Error::Unique` on the shadow index, as R-1153 says. On Postgres 18.6 and 17.11, this query found `1.01` twice for `numeric(10,4)` to `numeric(10,2)`, the same `(1, 1)` twice on a partial two-column unique index for `text` to `integer`, rows outside its predicate left out, and `abc` twice for a change to a case-insensitive ICU collation, with the nulls left out, while building the same unique index concurrently on the copied values failed with `could not create unique index` and left it invalid. Both `America/New_York` times above gave the same `timestamptz`, and so did `01:30` before and after clocks went back, going the other way.

**R-1160** **Partitioned tables in the other safe forms.** Postgres can't build an index concurrently on a partitioned table, or attach an index to a constraint there. On Postgres 18.6 and 17.11, `CREATE INDEX CONCURRENTLY` and `CREATE UNIQUE INDEX CONCURRENTLY` on one failed with `cannot create index on partitioned table ... concurrently`, and `ADD CONSTRAINT ... USING INDEX` failed with `ALTER TABLE / ADD CONSTRAINT USING INDEX is not supported on partitioned tables`, even on an index built without `CONCURRENTLY`. So R-0319's concurrent indexes, R-0560's unique key, R-0561's primary key, R-0562's index, and R-1152's and R-1158's rebuilds in place each refuse a partitioned table with exit code `2` before the migration's first step, naming the table and saying `--fast` handles it. The models can't declare a partitioned table, so scratch never has one, and `migrate` and `rollback` preflight check the live database. Under `--fast` each runs as one plain `CREATE INDEX`, `ADD CONSTRAINT ... UNIQUE (...)` or `ADD PRIMARY KEY (...)` on the partitioned table, which builds the index on every partition under the lock it takes. It reaches every partition, so it runs only when each is declared by a model, under R-1168's rule, and is refused otherwise, under `--fast` too. Postgres refuses a unique key or a primary key on a partitioned table that leaves out a column of the partition key, with `unique constraint on partitioned table must include all partitioning columns`, so preflight refuses that too, under `--fast` as well, naming the partition key's columns. A partition on its own is a plain table to these forms: `CREATE UNIQUE INDEX CONCURRENTLY` and `ADD CONSTRAINT ... UNIQUE USING INDEX` on one worked on both versions, so they run there with no long lock.

**R-1167** **`NOT VALID` foreign keys from a partitioned table.** Postgres 15 to 17 can't add a foreign key `NOT VALID` on a partitioned table. On Postgres 17.11, `ADD CONSTRAINT ... FOREIGN KEY ... NOT VALID` on one failed with `cannot add NOT VALID foreign key on partitioned table "p" referencing relation "k"`, whether the table it referenced was plain or partitioned, while on 18.6 it ran, reached every partition, and `VALIDATE` then validated them all. On both, a foreign key `NOT VALID` on a partition on its own, and one from a plain table to a partitioned table, worked. So on Postgres 15 to 17, each foreign key morm would add `NOT VALID` on a partitioned table is refused with exit code `2` before the migration's first step, changing nothing, naming the table, the foreign key and the server's version, and saying `--fast` handles it: R-0559's foreign key, the foreign keys R-1158's in-place form adds back, and the foreign keys step 38's rollback of a retire adds back. The models can't declare a partitioned table, so scratch never has one, and `migrate` and `rollback` preflight read `server_version_num` and `pg_class.relkind` on the live database. Under `--fast`, each is added validated in one statement, which on Postgres 18.6 and 17.11 took `SHARE ROW EXCLUSIVE` on the table it references, on the partitioned table and on every partition, so writes to them wait while it checks every row, and a row that breaks it fails the statement, changing nothing, naming the partition, as `insert or update on table "p1" violates foreign key constraint`. There, step 38's decision for rows that break a restored foreign key doesn't offer to keep it `NOT VALID`. On Postgres 18 these run as R-0559 says, and R-1168 applies to the partitions they reach.

**R-1168** **Changes that reach a child or a partition.** Postgres carries many statements from a table to its children and partitions. On Postgres 18.6 and 17.11, on an inheritance parent and on a partitioned table, `ADD COLUMN`, with a default or without, `DROP COLUMN`, `RENAME COLUMN`, `SET NOT NULL`, `DROP NOT NULL`, `SET DEFAULT`, `DROP DEFAULT`, and adding, dropping and validating a CHECK, valid or `NOT VALID`, each reached every child, grandchild and partition, and an `UPDATE` on the parent changed the children's rows too. On a partitioned table, so did `CREATE INDEX`, `DROP INDEX`, a unique key, adding and dropping a foreign key, creating and dropping a row trigger, and `ADD GENERATED ... AS IDENTITY`, all of which an inheritance parent keeps to itself, and `DROP TABLE` dropped every partition with no `CASCADE`. `ALTER TABLE ONLY` on the parent didn't stop them: it was refused with `column must be added to child tables too`, `constraint must be added to child tables too` and `inherited column ... must be renamed in child tables too`. On a child or a partition alone, Postgres refused what it holds from its parent, with `cannot rename inherited column`, `cannot drop inherited column`, `cannot drop inherited constraint`, `column ... is marked NOT NULL in parent table`, `cannot drop index ... because index ... requires it`, `cannot drop trigger ... because trigger ... requires it` and `cannot add column to a partition`. So R-1157's rule for a type or collation change holds for every statement morm writes on an existing table that Postgres carries to children or partitions, in place, under `--fast`, in a `down.sql`, in `rollback` and in `purge`: step 30's ops, step 36's triggers, step 38's retire, its rollback and `purge`, this step's safe forms, and a later step's form. Scratch has no inheritance, so `migrate`, `rollback` and `purge` preflight read `pg_inherits` and `pg_class` on the live database for every table a statement touches. A statement Postgres carries runs only when every child and partition it reaches is declared by a model and, for a change to a column, that model makes the same change. Identity on a partitioned table's column is the one exception: a partition's model never declares identity, under step 29's rule for a partition's identity, so adding or dropping it on the parent needs every partition declared, with no change to identity in their models. Then it runs once, on the top parent, where the first step in that tree sits, under R-1157's rule, and each other table's step finds by its precondition that it's done. A statement Postgres makes only through the parent is refused on a child or a partition without the same change on its top parent: a rename or a drop of an inherited column, `DROP NOT NULL` on one, on every version, though 17.11 let an inheritance child drop an inherited `NOT NULL` that 18.6 refused, `ADD COLUMN` on a partition, and dropping a constraint, an index or a trigger a child or a partition holds from its parent. What Postgres doesn't carry runs on each table as it would on any other: an index, a foreign key, a row trigger or identity on an inheritance parent, what a child adds of its own, and a child's own default. A batched backfill or copy walks each table's own rows with `UPDATE ONLY`, by that table's copy key, before the step that validates on the top parent, so no batch mixes the rows of two tables, whose keys are unique only within each. Retiring a table moves only that table, `purge`'s `DROP TABLE` on a partitioned table drops every partition, and on an inheritance parent Postgres refuses it, so a table with children or partitions is retired only together with every one of them, each declared by a model and retired in the same migration, and `purge` drops them before their parent. Otherwise preflight refuses with exit code `2` before the first step, changing nothing, naming the statement, the table, its top parent and every child and partition it reaches: a statement that would reach a child or a partition no model declares, or whose model doesn't make the same change to a column, a statement Postgres makes only through a parent, on a child or a partition alone, and a retire that leaves a child or a partition behind. `--fast` doesn't lift this, because it changes how a statement locks, not which tables it reaches. `purge` reads `pg_inherits` again before each drop, because a child can be created in the 30 days before it, and refuses the same way. morm never changes a table it doesn't manage, and the message says to declare every child and partition in the models with the same change.

**R-1179** **The index check on children and partitions.** R-1152's check compares only a table's own indexes, under step 29's rule, so an index a partition holds from its partitioned table's index is checked once, as the parent's, and rebuilt only through it. Under `--fast` and in a one-transaction form, dropping and creating the parent's index builds it again on every partition, each declared under R-1168's rule, and a partition's index is never dropped or rebuilt on its own, which Postgres refuses with `cannot drop index ... because index ... requires it`. Rebuilding the parent's index in place is refused as R-1160 says. A partition's declared `pk` is the key it holds, under step 29's rule for a partition's key, so its index is checked once too, as the parent's. A partition's own index, and every index of an inheritance child, which holds none from its parent, is checked and rebuilt on its own table like any other.

**R-1184** **A partition's `pk` in a migration.** Under step 29's rule for a partition's key, a partition's model with `pk` on the key it holds from its parent and one without it describe the same live table. So an op that adds that `pk` to a partition's model, or removes it, while the partition holds its parent's key on those columns under that name, changes nothing on the partition: preflight finds the op done, R-1168 doesn't refuse the removal as a drop of what the partition holds, which Postgres refuses with `cannot drop inherited constraint`, and its inverse in `rollback` and `down.sql` changes nothing either. When a migration adds a key to a partitioned table under `--fast`, as R-1160 says, and its partitions' models add `pk` on the same columns, the parent's `ADD PRIMARY KEY` builds each partition's key as `<partition>_pkey`, and each partition's op then finds it done, under R-1168's rule. A partition whose model already declares `pk` on those columns, with its own key under `<partition>_pkey`, keeps it: on Postgres 18.6 and 17.11 the parent's `ADD PRIMARY KEY` took that key over, setting its `conparentid`, and the model's `pk` then matches the key the partition holds. A partition's `pk` that can't match its parent's key, before the migration or after it, such as one on other columns, one kept while the parent's key is dropped, or a partition's own key on other columns when the parent gets one, stops the run in preflight, as step 33 says.
