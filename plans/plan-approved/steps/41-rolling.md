## Goal

Keep old and new binaries working through a deploy.

## Deliverables

- `phase`, expand and contract, rename sync triggers, `deprecated` steps, `db.check_schema()` with its per-model column list, data migration hooks run through `morm-mgr` with `--hooks`, and holding a narrowing Postgres would round or cut silently for `contract`

## End-to-end check

An old binary boots and works during an expand phase, a migration with a Rust data hook runs through `--hooks ./morm-mgr`, and `check_schema` reports a dropped default. A narrowing Postgres would round silently is refused by plain `migrate` and runs under `--phase contract`.

## Out of scope

- New features

### Crates and tools

- **R-0044** `morm-mgr` also runs a migration's Rust data hooks, and nothing else. Build it in CI and ship the binary with the migrations. `migrate --hooks ./morm-mgr` and `rollback --hooks ./morm-mgr` call it as `morm-mgr hook ID up` or `down`, and a migration with hooks refuses to run without it, or if that binary doesn't contain the hook, because `morm-admin` holds no project code. A hook connects with the migration role and runs as a `no-tx` step, so it must be safe to run again on `--resume`.

### Migrations / Rolling deploys

**R-0612** Static column lists mean a dropped column breaks the old binary mid-deploy. Migrations carry `phase: expand | contract`, and `--phase` splits them. `contract` refuses while a required `#[col(deprecated)]` hasn't shipped. Marking a `NOT NULL` column with no default as `deprecated` generates an expand step dropping that `NOT NULL`, because the new binary stops writing it. A rename decision offers an expand/contract form for live tables: add the new column, keep both in sync with a generated trigger, backfill in batches, and drop the old column and trigger in `contract`. `db.check_schema()` checks compatibility at startup, not equality, so an old binary restarting during an expand phase still boots. Every column the binary reads or writes must exist, with a type the field can decode in the same family as the type it was built against, so only an unrelated kind fails. These are the families, and there are no others: for a field of a Rust integer type, `smallint`, `integer`, `bigint` and `numeric(p,0)` with any `p`, and never a `numeric` with a scale or with no precision, because an integer field has no way to read a fraction; for `Decimal`, `numeric` with any precision and scale, or with none, and `smallint`, `integer` and `bigint`, because every one of their values fits in its 28 digits; for `morm::Numeric`, `numeric` with any precision and scale, or with none; for `String`, `text`, and `varchar` with any length or none; for a `String` built against `char(n)`, `char` with any length; for `DateTime<Utc>` and `Timestamp`, `timestamptz` with any precision, and for `NaiveDateTime`, `timestamp` with any precision; and for an array of any of these, an array of its element's family. Every other field needs the same type, with the same length or precision, as `format_type` prints it from `atttypid` and `atttypmod`. `char` is a family of its own, apart from `text` and `varchar`, because Postgres pads a `char` value with spaces to its length and a change to `text` or `varchar` drops them, so `'ab '` would read as `'ab'`. Postgres treats those trailing spaces as insignificant, so a `String` field built against `char(n)` reads `char` of any length through a decoder that trims trailing spaces back to `n`: on `char(4)`, `'ab  '` reads as `'ab '`, as it did on `char(3)`, and `'abcd'`, with no spaces to trim, reads whole. `timestamp` and `timestamptz` are different kinds here, because a change between them converts each value through the `TimeZone` of the session that runs it, with no error, so the same stored `12:00` becomes `12:00` UTC under one session and `06:00` UTC under another, and no decoder could tell which. Any other difference fails the check, such as `text` for an integer field, `numeric(25,2)` for an integer field, or `text` or `varchar(3)` for a field built against `char(3)`. Within a family, the field reads through the decoder for the column's real type, chosen once per statement when it's prepared, and chosen again when a cached statement is re-prepared because Postgres reports that its result type changed, as it does after a cutover. When the types match, the path is the one the binary always ran. A field wider than the column reads every value losslessly. A field narrower than the column checks each value's range, and only a value that can't fit errors: an integer field returns `Error::OutOfRange` naming the column, never a wrapped value, and `Decimal` returns `Error::Decimal` for a value it can't hold exactly, past its 28 significant digits, as it does on unbounded `numeric`. `morm::Numeric`, and `String` on `text` and `varchar`, read every value whole. Nothing read is rounded. A write goes as the column type the binary was built against, and Postgres converts it to the column's real type, so a value the column can't hold, such as a number with more digits before the point than it allows or a text longer than its length, gets the database's error for that write. Where Postgres would round or cut the write silently instead, R-1108 holds the change for `contract`. So a type change never stops a running binary, and one restarting after it still boots. A type change has no expand and contract of its own and never waits for `contract`, apart from R-1108's silent narrowings, and `contract` still guards dropped columns and removed enum values. Extra columns and objects are fine. Two cases that would fail that binary's inserts are reported: an extra `NOT NULL` column with no default, and a column the binary may leave out that is no longer nullable and has lost its default.

**R-1108** **A narrowing Postgres would change silently waits for `contract`.** Postgres rounds or cuts some writes to a narrower column with no error, so an app built for the old shape would store a value other than the one it wrote, and nothing would tell it. These are the silent narrowings, and there are no others: a lower scale, where a `numeric` with no precision counts as unlimited and `smallint`, `integer` and `bigint` count as 0, so `1.0051` written to a column changed from `numeric(20,4)` to `numeric(20,2)` is stored as `1.01`, `1.00005` from `numeric` to `numeric(20,4)` as `1.0001`, and `1.25` from `numeric(12,2)` to `integer` as `1`; a lower precision on `timestamptz` or `timestamp`, where no precision counts as 6, so `.123456` from `timestamptz` to `timestamptz(3)` is stored as `.123`; and a shorter length on `varchar` or `char`, where `text` and a `varchar` with no length count as unlimited, because Postgres cuts trailing spaces to fit, so `'abc  '` from `text` to `varchar(3)` is stored as `'abc'`, and `'abc '` from `char(4)` to `char(3)` as `'abc'`. morm reads which it is from the column's old and new definition, as `format_type` prints them, with no SQL parser. A change that's one of these and widens something else, such as `numeric(8,4)` to `numeric(10,2)`, is one. Every other narrowing raises a real error on a write that doesn't fit, such as fewer digits before the point, `bigint` to `integer`, `numeric(12,0)` to `integer`, or a shorter length for a value whose extra characters aren't all spaces, so it runs online as R-0612 says, with no gate. In online mode, which is a live run of a migration `makemigrations` wrote without `--fast`, morm always assumes an app built for the old shape is still running, and never tries to detect one. So `makemigrations` puts every step of a silent narrowing in `contract`, the online swap's shadow column, sync trigger and copy included, because the sync trigger would already narrow what an old app writes. The same holds for a migration `revert` writes, because a widening's down is a narrowing. It runs only under `migrate --phase contract`, which the operator runs once the new release is out everywhere. `makemigrations --fast` writes it in the one-transaction form, because `--fast` means a maintenance window with apps stopped. That form takes phase `contract` too, and plain `migrate` runs it. Plain `migrate` refuses the online form in preflight with exit code `2`, before that migration's first step, naming the table and column, the old and new definition, the silent change it would cause, such as `1.0051` stored as `1.01`, and the two ways to run it: `migrate --phase contract` once the new release is out everywhere, or `makemigrations --fast` for a maintenance window with apps stopped. `--phase expand` runs the migration's other `expand` steps and leaves the narrowing pending for `contract`.

### Migrations / Data migrations

**R-0613** SQL steps first, including `batch` steps, covered by checksums. Custom Rust data hooks are registered by migration id and use raw SQL only, since model types change. A hook needs a matching down hook, or the migration is declared irreversible.

### Managed enums

- **R-0997** **Enums in `check_schema`.** The per-model list also holds each enum's labels. Every labelled variant's label must exist, or its `was` label, and a `deprecated` variant may be missing. Extra labels in the database are fine, because a binary only fails on a row that holds one, and `Error::UnknownEnumValue` names it.
- **R-0998** **Enum phases.** Adds, renames and the online swap's steps before its cutover are `expand`. A cutover that removes a label is `contract`, because binaries that still write it would fail. A cutover that only reorders stays in `expand`. In one migration that adds and removes, the add goes in `expand`, so a value and its replacement exist together through the rollout. A `--fast` swap takes the phase its cutover would.
- **R-0999** **Removing a value in a rolling deploy.** `#[pg_enum(deprecated)]` on a variant says that value is on its way out. `contract` refuses a swap that removes a label until a release with that variant marked `deprecated` has shipped, the same gate `#[col(deprecated)]` uses.
- **R-1000** **Renaming a value in a rolling deploy.** A rename runs instantly by default, so old binaries fail on that value during the rollout: reads of rows holding it return `Error::UnknownEnumValue`, and writes of the old label return `22P02`. The rename decision also offers expand/contract: add the new label in `expand`, copy rows across in batches, and remove the old label by swap in `contract`. With `was`, a new binary reads both labels through either path. `was` answers only whether it's a rename. The path stays a decision with the instant rename as its default.
