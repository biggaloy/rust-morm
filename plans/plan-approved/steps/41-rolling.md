# Step 41: Rolling deploys

- **Phase:** Migrations
- **Depends on:** 40, 15
- **Can run beside:** 19, 20, 21, 22, 23, 24, 25, 27, 43, 44, 46, 47, 48
- **Crates:** `morm-migrate`, `morm-admin`, `morm`, `morm-macros`, `morm-core`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

Keep old and new binaries working through a deploy.

## Deliverables

- `phase`, expand and contract, rename sync triggers, `deprecated` steps, `db.check_schema()` with its per-model column list, data migration hooks run through `morm-mgr` with `--hooks`, holding a narrowing Postgres would round or cut silently for `contract` in `migrate` and `rollback`, `check_schema` refusing a binary built for the wider shape, the `lossy` decision for such a narrowing, worded for a key other tables reference, counting the live rows such a narrowing would change, with a decision showing the count at `rollback` and `migrate` when there are any, and `check_schema` run when each pool starts, with its `check_schema = "off"` setting, counting a lost identity as a lost default, refusing a partition's model that sends the column its parent's identity fills, refusing a model on any table whose inserts send a `GENERATED ALWAYS` identity column, and one on a table that isn't a partition whose inserts send a `BY DEFAULT` identity column, the warning and deploy order for a migration that adds identity to an existing column, with a default or without, and the `deprecated` step and the rename form on tables with children or partitions

## End-to-end check

An old binary boots and works during an expand phase, a migration with a Rust data hook runs through `--hooks ./morm-mgr`, and `check_schema` reports a dropped default. A narrowing Postgres would round silently opens a `lossy` decision, is refused by plain `migrate` and runs under `--phase contract`, a plain `rollback` of a widening is refused the same way, and a binary built for the old shape fails `Db::connect()` with `Error::SchemaMismatch` after it. `rollback --fast` of a widening runs with no decision when no row holds a value only the wider column can, and stops with exit code `3` on a decision showing the count when rows do, until `rollback --decide` accepts it.

### Migrations / Rolling deploys

**R-0612** Static column lists mean a dropped column breaks the old binary mid-deploy. Migrations carry `phase: expand | contract`, and `--phase` splits them. `contract` refuses while a required `#[col(deprecated)]` hasn't shipped. Marking a `NOT NULL` column with no default as `deprecated` generates an expand step dropping that `NOT NULL`, because the new binary stops writing it. A rename decision offers an expand/contract form for live tables: add the new column, keep both in sync with a generated trigger, backfill in batches, and drop the old column and trigger in `contract`. `check_schema` checks compatibility, not equality, at startup, where morm runs it when each pool starts, as R-1116 says, and when `db.check_schema()` is called, so an old binary restarting during an expand phase still boots. Every column the binary reads or writes must exist, with a type the field can decode in the same family as the type it was built against, so only an unrelated kind fails. These are the families, and there are no others: for a field of a Rust integer type, `smallint`, `integer`, `bigint` and `numeric(p,0)` with any `p`, and never a `numeric` with a scale or with no precision, because an integer field has no way to read a fraction; for `Decimal`, `numeric` with any precision and scale, or with none, and `smallint`, `integer` and `bigint`, because every one of their values fits in its 28 digits; for `morm::Numeric`, `numeric` with any precision and scale, or with none, and `smallint`, `integer` and `bigint`, as for `Decimal`; for `String`, `text`, and `varchar` with any length or none; for a `String` built against `char(n)`, `char` with any length; for `DateTime<Utc>` and `Timestamp`, `timestamptz` with any precision, and for `NaiveDateTime`, `timestamp` with any precision; and for an array of any of these, an array of its element's family. Every other field needs the same type, with the same length or precision, as `format_type` prints it from `atttypid` and `atttypmod`. `char` is a family of its own, apart from `text` and `varchar`, because Postgres pads a `char` value with spaces to its length and a change to `text` or `varchar` drops them, so `'ab '` would read as `'ab'`. Postgres treats those trailing spaces as insignificant, so a `String` field built against `char(n)` reads `char` of any length through a decoder that trims trailing spaces back to `n`: on `char(4)`, `'ab  '` reads as `'ab '`, as it did on `char(3)`, and `'abcd'`, with no spaces to trim, reads whole. `timestamp` and `timestamptz` are different kinds here, because a change between them converts each value through the `TimeZone` of the session that runs it, with no error, so the same stored `12:00` becomes `12:00` UTC under one session and `06:00` UTC under another, and no decoder could tell which. Any other difference fails the check, such as `text` for an integer field, `numeric(25,2)` for an integer field, or `text` or `varchar(3)` for a field built against `char(3)`. Within a family, the check also fails a field built against a type that the column's real type is one of R-1108's silent narrowings of, because Postgres would round or cut what that binary writes with no error: a field built for `numeric(6,2)` on `numeric(4,1)` or on `integer`, for `numeric` on `numeric(6,2)`, for `varchar(3)` on `varchar(2)`, for `text` on `varchar(10)`, for `char(3)` on `char(2)`, for `timestamptz` on `timestamptz(3)`, or for `numeric(6,2)[]` on `numeric(4,1)[]`. It names the column, both definitions and the silent change, such as `1.25` stored as `1.3`. A running binary never meets this, because R-1108 holds such a change for `contract`, which runs once every binary is built for the new shape, or for `--fast`, with apps stopped. So only a binary built for the old shape that starts after it, such as an older build brought back, is refused, and it fails to start loudly, with R-1116's `Error::SchemaMismatch`, rather than storing values other than the ones it writes. A narrowing that raises a real error on a write that doesn't fit still passes, such as a field built for `numeric(6,2)` on `numeric(5,2)` or for `bigint` on `integer`. Within a family, the field reads through the decoder for the column's real type, chosen once per statement when it's prepared, and chosen again when a cached statement is re-prepared because Postgres reports that its result type changed, as it does after a cutover. When the types match, the path is the one the binary always ran. A field wider than the column reads every value losslessly. A field narrower than the column checks each value's range, and only a value that can't fit errors: an integer field returns `Error::OutOfRange` naming the column, never a wrapped value, and `Decimal` returns `Error::Decimal` for a value it can't hold exactly, past its 28 significant digits, as it does on unbounded `numeric`. `morm::Numeric`, and `String` on `text` and `varchar`, read every value whole. Nothing read is rounded. A write goes as the column type the binary was built against, and Postgres converts it to the column's real type, so a value the column can't hold, such as a number with more digits before the point than it allows or a text longer than its length, gets the database's error for that write. Where Postgres would round or cut the write silently instead, R-1108 holds the change for `contract`. So a type change never stops a running binary, and one restarting after it still boots, apart from a binary built for the old shape of one of R-1108's silent narrowings, which the check above refuses. A type change has no expand and contract of its own and never waits for `contract`, apart from R-1108's silent narrowings, and `contract` still guards dropped columns and removed enum values. Extra columns and objects are fine. Two cases that would fail that binary's inserts are reported: an extra `NOT NULL` column with no default, and a column the binary may leave out that is no longer nullable and has lost its default. A column that has lost its identity counts as one that has lost its default, because a binary built while it had one never sends it, so each of its inserts would fail with `NOT NULL`.

**R-1108** **A narrowing Postgres would change silently waits for `contract`.** Postgres rounds or cuts some writes to a narrower column with no error, so an app built for the old shape would store a value other than the one it wrote, and nothing would tell it. These are the silent narrowings, and there are no others: a lower scale, where a `numeric` with no precision counts as unlimited and `smallint`, `integer` and `bigint` count as 0, so `1.0051` written to a column changed from `numeric(20,4)` to `numeric(20,2)` is stored as `1.01`, `1.00005` from `numeric` to `numeric(20,4)` as `1.0001`, and `1.25` from `numeric(12,2)` to `integer` as `1`; a lower precision on `timestamptz` or `timestamp`, where no precision counts as 6, so `.123456` from `timestamptz` to `timestamptz(3)` is stored as `.123`; and a shorter length on `varchar` or `char`, where `text` and a `varchar` with no length count as unlimited, because Postgres cuts trailing spaces to fit, so `'abc  '` from `text` to `varchar(3)` is stored as `'abc'`, and `'abc '` from `char(4)` to `char(3)` as `'abc'`. The same change to an array's element type is one too, because Postgres applies it to each element, so `{1.0051}` from `numeric(20,4)[]` to `numeric(20,2)[]` is stored as `{1.01}`. morm reads which it is from the column's old and new definition, as `format_type` prints them, with no SQL parser. A change that's one of these and widens something else, such as `numeric(8,4)` to `numeric(10,2)`, is one. Every other narrowing raises a real error on a write that doesn't fit, such as fewer digits before the point, `bigint` to `integer`, `numeric(12,0)` to `integer`, or a shorter length for a value whose extra characters aren't all spaces, so it runs online as R-0612 says, with no gate. In online mode, which is a live run of a migration `makemigrations` wrote without `--fast`, morm always assumes an app built for the old shape is still running, and never tries to detect one. So `makemigrations` puts every step of a silent narrowing in `contract`, the online swap's shadow column, sync trigger and copy included, because the sync trigger would already narrow what an old app writes. The same holds for a migration `revert` writes, because a widening's down is a narrowing. It runs only under `migrate --phase contract`, which the operator runs once the new release is out everywhere. `makemigrations --fast` writes it in the one-transaction form, because `--fast` means a maintenance window with apps stopped. That form takes phase `contract` too, and plain `migrate` runs it. Plain `migrate` refuses the online form in preflight with exit code `2`, before that migration's first step, naming the table and column, the old and new definition, the silent change it would cause, such as `1.0051` stored as `1.01`, and the two ways to run it: `migrate --phase contract` once the new release is out everywhere, or `makemigrations --fast` for a maintenance window with apps stopped. `--phase expand` runs the migration's other `expand` steps and leaves the narrowing pending for `contract`.

**R-1110** **`rollback` holds a silent narrowing too.** A migration's down can be one of R-1108's silent narrowings, such as the down of a widening from `numeric(20,2)` to `numeric(20,4)`, and apps built for the wider shape may still be running when it's rolled back, so their writes would be rounded or cut with no error. So `rollback` refuses it in every form, `--last`, `--to`, `--orphans` and `--failed`, with exit code `2`, before the first step it would undo, changing nothing. Its message is the one `migrate` gives, naming the table and column, the old and new definition as the down changes them, and the silent change it would cause, such as `1.0051` stored as `1.01`, with `rollback`'s two ways to run it in place of `migrate`'s: `rollback --phase contract` once every app runs a release built for the narrower shape, or `rollback --fast` for a maintenance window with apps stopped. Either flag lets it through. `--phase contract` changes nothing else: `rollback` runs the same steps of `down.sql`. `--fast` also runs each step of the down in its one-transaction form where the down holds one, as step 34 says for `rollback --fast`, so a narrowing whose down is an online swap runs as one `ALTER COLUMN ... TYPE`, as `makemigrations --fast` would write it. For a silent narrowing, neither flag changes anything else. A narrowing that raises a real error on a write that doesn't fit isn't held, as R-1108 says. morm reads which it is from the column's definitions in the migration's `schema_before` and `schema_after`, from the ledger's copy of `meta.json`, so the check works when the migration's files are gone.

**R-1111** **A silent narrowing of stored data is `lossy`.** A type change that's one of R-1108's silent narrowings also changes rows already stored, as it does a write, with no error: `1.0051` becomes `1.01` when `numeric(20,4)` becomes `numeric(20,2)`, `1.25` becomes `1` as `integer` from `numeric(12,2)`, `.123456` becomes `.123` as `timestamptz(3)`, `.5` becomes the next second as `timestamp(0)`, `'abc       '` becomes `'abc'` as `varchar(3)` from `varchar(10)`, and `{1.0051}` becomes `{1.01}` as `numeric(20,2)[]`. The online swap's batched copy and sync trigger change them the same way. So the op that runs one in direction `up` has data effect `lossy`, in the online form and in the `--fast` form alike, and `makemigrations` opens a decision for it, as step 32 does for every lossy change, naming the table and column, both definitions and the change, such as `1.0051` stored as `1.01`. An accepting answer writes the migration, and an answer that refuses exits with code `2`, under step 32's exit codes. A `revert` plans its forward migration the same way, so a revert of a widening opens it too. A widening's `down` is one of these narrowings, but `makemigrations` opens no decision for it: scratch holds no live rows, so whether rolling a widening back changes any is asked at `rollback`, as R-1114 says. `makemigrations` sees only scratch, so `migrate` also counts the live rows the change would alter, and asks again showing the count when there are any, as R-1115 says. A narrowing that raises a real error, such as `bigint` to `integer`, changes no stored row, because a row that doesn't fit stops the change, so it isn't `lossy`. That column isn't a preserved column in step 32's with-data proof, because `up` is meant to change its values, and every other column still is.

**R-1113** **Counting the rows a silent narrowing would change.** Before `rollback` undoes, or `migrate` runs, a step that's one of R-1108's silent narrowings, its preflight counts the live rows that step would change, on the live database. morm builds the count from the column's old and new definition as `format_type` prints them, with no SQL parser. A row counts when the change would leave it a value that isn't equal, in the old type, to the one it holds, and the change raises no error on it. For a lower scale `s`, where `smallint`, `integer` and `bigint` count as 0, that's `col <> round(col, s)`. For a lower timestamp precision `p`, it's `col <> CAST(col AS timestamptz(p))`, or `timestamp(p)`. For a shorter length `n`, to `varchar(n)`, it's `length(col) > n AND length(rtrim(col, ' ')) <= n`, and to `char(n)` from `text` or `varchar`, it's `col <> rtrim(col, ' ') AND length(rtrim(col, ' ')) <= n`, because a `char` value loses its trailing spaces when read as text. From `char` to a shorter `char`, no row counts, because Postgres treats a `char` value's trailing spaces as insignificant, so `'abc '` in `char(4)` and `'abc'` in `char(3)` are equal. On an array, a row counts when any element does, through `unnest`. A `NULL` never counts, and neither does a row the change refuses with an error, such as `'abcd'` into `varchar(3)` or `NaN` into `integer`, because that row stops the change instead. On Postgres 18.6 and 17.11, each of these counts matched the rows `ALTER COLUMN ... TYPE` changed, compared in the old type, including `-1.0050` to `numeric(20,2)`, `1.50` and `-1.50` to `integer`, `9999.9999` from `numeric(8,4)` to `numeric(10,2)`, `'ab '` from `text` to `char(3)`, and `{{1.0051},{2}}`. The count is one `SELECT count(*)` per column, in a read-only transaction of its own, with `statement_timeout` off, so a role's timeout can't leave it unknown. It takes only `ACCESS SHARE`, so reads and writes go on while it runs: on both versions, an `UPDATE`, an `INSERT` and a `DELETE` from another session with a `500ms` `lock_timeout` went through while it was held. No index can answer it, so it reads the whole table, and Postgres can run it as a parallel sequential scan. It always runs to the end, however big the table, because only a full read shows that no row would change. That stays cheap beside the change itself, because every silent narrowing rewrites the whole table and its indexes, under `ACCESS EXCLUSIVE` in the one-transaction form, or copies every row in the online form: on both versions, the table's file changed for `numeric(20,4)` to `numeric(20,2)`, `timestamptz` to `timestamptz(3)`, `varchar(10)` and `text` to `varchar(3)`, and `numeric(20,4)[]` to `numeric(20,2)[]`, and stayed the same for a widening. So the count adds one read of what the change reads and rewrites anyway. On a table of 10 million rows and 1.2 GB, held in memory, with two parallel workers, it took 0.31 s on both versions, while the change took 15.4 s on 18.6 and 16.6 s on 17.11. A huge table takes as long as one sequential read of it, and like any long read the count holds back vacuum for that time. Where R-1108 or R-1110 holds the step, it counts only once the hold lets the step through, so a refused run stops at once without reading the table. The count is taken as of preflight. The rows it's about are the ones apps built for the wider shape wrote, and those holds mean such apps no longer write when it runs: `--phase contract` runs once every app runs the release built for the narrower shape, and `--fast` with apps stopped. It's a preflight check of the op, so `rehearse` runs it in each pass, as step 40 says, and a rehearsal on real data shows the count before production does.

**R-1114** **`rollback` asks before it changes stored rows.** When R-1113's count for a step `rollback` would undo is above 0, `rollback` opens a decision in its preflight, in direction `down`, under step 34's rules, in every form, `--last`, `--to`, `--orphans` and `--failed`, before the first step of that migration it would undo, changing nothing. It reads the column's definitions from the ledger's copy of `meta.json`, so it works when the migration's files are gone. It names the table and column, both definitions as the down changes them, the silent change, such as `1.0051` stored as `1.01`, and the count, such as `2 rows would change`, and it offers to accept or refuse, refusing by default. The run stops with exit code `3` until `rollback --decide ID=OPT` accepts it, and an answer that refuses exits with code `2`. `--yes` and `--accept-data-loss` don't answer it. With a count of 0 it opens no decision, and the step runs. Its ID is built as step 32 builds one for a database object, with the table's `regclass` text and the column's name as its signature, and its hash covers both definitions and the count. So an answer covers only the count it was shown: if the count changes before the run that answers it, the ID changes, and that run stops again with exit code `3`, showing the new count. This is apart from R-1110's hold, which still needs `--phase contract` or `--fast`.

**R-1115** **`migrate` shows the rows a silent narrowing changes.** R-1111's `lossy` decision is answered at `makemigrations`, which sees only scratch. So when `migrate` runs a step that's one of R-1108's silent narrowings, in the online form under `--phase contract` or in the `--fast` form, and R-1113's count is above 0, its preflight opens a `lossy` decision of its own on the live database, in direction `up`, under step 33's rules, before that migration's first step, changing nothing. It names the table and column, both definitions, the change, such as `1.0051` stored as `1.01`, and the count, such as `3 rows would change`, and it offers to accept or refuse, refusing by default. Its ID is built as R-1114's is, so the answer `meta.json` holds from `makemigrations` doesn't cover it, and an answer covers only the count it was shown. The run stops with exit code `3` until `migrate --decide ID=OPT` accepts it, an answer that refuses exits with code `2`, and `--yes` answers none. With a count of 0 it opens nothing, and the step runs, because `makemigrations`' answer accepted the change and no stored row would change. A `revert` of a widening is migrated the same way. `--plan` shows the count and records nothing.

**R-1136** **A silent narrowing of a key other tables reference.** When the column is a key that foreign keys reference, which step 60 changes together with every referencing column, R-1111's `lossy` decision, and R-1114's and R-1115's decisions with their live counts, name every referencing column with its table, and say that the key's values change in every one of those tables with it, such as `1.0051` becoming `1.01` in `orders.id` and in `order_lines.order_id`, with each column's count. They also say that copies of the key held outside the database, such as in caches, URLs, other services, logs and exports, keep the old values and won't match.

**R-1116** **`check_schema` runs when a pool starts.** morm runs `check_schema` by itself on every pool, before the pool serves anything, so a build that doesn't match the schema refuses to start. `Db::connect`, `connect_as` and `connect_to` run it on the first connection their pool opens, before they return, and return `Error::SchemaMismatch` when it fails, holding every finding. Each finding names the table and column, the definition the field was built against, the column's, and what's wrong: a missing column, an unrelated kind, one of R-1108's silent changes, such as `1.25` stored as `1.3`, one of R-0612's two insert cases, R-1190's partition column that its model's inserts send, R-1194's `GENERATED ALWAYS` identity column that its model's inserts send, or R-1198's `BY DEFAULT` one. So `let db = morm::Db::connect().await?;` stops the app at startup with that error, and none of the app's queries has run. A pool that `db.pool(name)` adds runs it before its first query. While it fails, every call through that pool returns the same error and runs the check again, so a replica that hadn't yet replayed a migration passes once it has. A pool that passed never checks again. Every pool runs it, `read_only` ones included, because a named pool can reach another host or log in as another role, and the pool must be able to serve every model the binary holds. The check covers every model in the binary, through the per-model column list, in one statement over the catalog, run through `query_typed` with no prepare round trip and no session state. So it works unchanged behind PgBouncer in transaction mode, where it checks the database PgBouncer connects that connection to, as the app's queries reach it. It costs one round trip on a pool's first connection and none after: checkouts, later connections and queries send nothing more. On Postgres 18.6 and 17.11, with 2,000 tables in the catalog, reading every column of 200 tables of 20 columns, with type, `NOT NULL`, default and enum labels, took 3.2 to 3.7 ms on a local connection and returned about 95 KB, and 20 tables took 0.6 to 1.2 ms. The connection `morm-mgr` opens to run a data hook doesn't run it, because a hook runs in the middle of a migration, against a schema no build matches, and it uses raw SQL only. `db.check_schema()` runs the same check whenever it's called, whatever R-1117's setting says.

**R-1117** **Turning the startup check off.** The pool setting `check_schema` is `"on"` by default, and `"off"` turns R-1116's startup check off for that pool and nothing else. It's set like any pool setting: in `[pool]`, in one `[pools.<name>]`, or by `MORM_POOL_CHECK_SCHEMA` for the pool a process opens at startup. Any other value is `Error::Config`. With it off, that pool starts against any schema, so a missing column fails each query that names it, and a build brought back after `contract` stores rounded or cut values with no error.

**R-1230** **The startup check also checks the casts.** `check_schema`'s one catalog statement adds one array: the cast name of every column it checks, plus every `PgEnum`, `PgDomain` and `PgComposite` the binary registers, each resolved with `to_regtype` and compared with the column's `atttypid`, or checked to be not `NULL`. So a cast name that resolves to nothing, or through `search_path` to another schema's type of the same name, fails the pool's start with `Error::SchemaMismatch`, naming the field, the cast and what it resolved to. The same statement compares each field's column type with the types its Rust type declares through `SqlType` that it carries, so a field whose column was changed to a type it can't carry is a finding too. It adds no round trip. With `check_schema = "off"` nothing is checked, and a name that resolves to nothing fails its first query with `42704`. Owner decisions DH2 and DH3.

**R-1234** **The startup check also checks the session's zone.** morm's sessions always run in UTC, and behind PgBouncer in transaction mode that rests on the role's `timezone`, because no startup parameter is sent. So `check_schema`'s one catalog statement also reads `current_setting('TimeZone')`, with no extra round trip, and when it isn't `UTC` the pool doesn't start: `Db::connect`, `connect_as`, `connect_to` and a pool `db.pool(name)` adds return `Error::Config`, naming the zone the session reported and saying to run `ALTER ROLE <role> SET timezone = 'UTC'`, before any of the app's queries has run. While it fails, every call through that pool returns the same error and runs the check again, as for a schema finding. A session given `UTC` by the startup parameter or by the role reports `UTC`, so a direct connection always passes. With `check_schema = "off"` the statement isn't run, so the zone isn't checked either. Owner decision DI1.

**R-1169** **Children and partitions in a rolling deploy.** The expand step that drops a `deprecated` column's `NOT NULL`, and every statement of a rename's expand/contract form, follow step 39's rule for statements Postgres carries to children and partitions. On a table with children or partitions, each runs only when every child and partition it reaches is declared by a model with the same change, once, on the top parent, and `migrate` and `rollback` preflight otherwise refuse with exit code `2` before the first step, changing nothing, naming the statement, the table, its top parent and those tables. On Postgres 18.6 and 17.11, `ADD COLUMN` and `DROP NOT NULL` on a parent reached every child and partition, and a row trigger on a partitioned table fired for every partition's rows, while one on an inheritance parent fired for none of a child's rows, even for an `UPDATE` run through the parent. So the sync trigger is created once on a partitioned table, and on every table of an inheritance tree, and the backfill walks each table's own rows with `UPDATE ONLY`, by that table's key.

### Migrations / Data migrations

**R-0613** SQL steps first, including `batch` steps, covered by checksums. Custom Rust data hooks are registered by migration id and use raw SQL only, since model types change. A hook needs a matching down hook, or the migration is declared irreversible.

### Managed enums

- **R-0997** **Enums in `check_schema`.** The per-model list also holds each enum's labels. Every labelled variant's label must exist, or its `was` label, and a `deprecated` variant may be missing. Extra labels in the database are fine, because a binary only fails on a row that holds one, and `Error::UnknownEnumValue` names it.
- **R-0998** **Enum phases.** Adds, renames and the online swap's steps before its cutover are `expand`. A cutover that removes a label is `contract`, because binaries that still write it would fail. A cutover that only reorders stays in `expand`. In one migration that adds and removes, the add goes in `expand`, so a value and its replacement exist together through the rollout. A `--fast` swap takes the phase its cutover would.
- **R-0999** **Removing a value in a rolling deploy.** `#[pg_enum(deprecated)]` on a variant says that value is on its way out. `contract` refuses a swap that removes a label until a release with that variant marked `deprecated` has shipped, the same gate `#[col(deprecated)]` uses.
- **R-1000** **Renaming a value in a rolling deploy.** A rename runs instantly by default, so old binaries fail on that value during the rollout: reads of rows holding it return `Error::UnknownEnumValue`, and writes of the old label return `22P02`. The rename decision also offers expand/contract: add the new label in `expand`, copy rows across in batches, and remove the old label by swap in `contract`. With `was`, a new binary reads both labels through either path. `was` answers only whether it's a rename. The path stays a decision with the instant rename as its default.

**R-1180** **`check_schema` on children and partitions.** `check_schema` reads only columns, and in the catalog a child's or a partition's columns are its own, inherited or not, so it checks each table against its own model as on any other table.
