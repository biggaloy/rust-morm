# Step 52: Managed enums: online swap

- **Phase:** Migrations
- **Depends on:** 39, 54, 59
- **Can run beside:** 08, 09, 19, 20, 21, 22, 23, 24, 25, 26, 27, 42, 43, 44, 45, 46, 47, 48
- **Crates:** `morm-migrate`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

Remove or reorder enum values on a live table with no long lock.

## Deliverables

- The online swap as the default on existing tables, `--fast` for the one-transaction form, keyset copy, with a unique `NOT NULL` key for a table with no primary key, definitions read from Postgres on scratch, materialized views built beside the old ones, cutover, retired columns and types, refusals, recovery
- Partitioned and inherited tables refused, shadow indexes under `_morm_new_<name>`, and step 39's index check on the one-transaction form
- Inherited enum columns changed only through their top parent in the one-transaction form, with the form's other statements, foreign keys dropped and added back around an index rebuild, and the check for labels that would merge on a unique index

## End-to-end check

On Postgres 15–18, a swap with a map runs on a table under live writers with a cutover of milliseconds, no table rewrite and no lost write, and the process killed at every step still reaches the right state.

## Context from other steps

> Step 39 builds the sync trigger, batched copy and concurrent index forms for column type changes, and `--fast`. It also builds the rules this form follows for what sits above the column: a managed view is recreated in the cutover, and a materialized view is built beside the old one with its indexes, owner, comment and grants, opens a decision about its contents, stays unpopulated if it was created `WITH NO DATA`, and is swapped by rename, leaving the old copy retired until `purge`. It reads each object's text from Postgres on a throwaway scratch, after renaming the column there, so names in strings stay as they are and output columns keep their names, it checks a view whose text differs for the same meaning, and it refuses a `USING` view's table if the live columns don't sit where scratch's do. Step 39 also refuses a partitioned table, a partition and a table in old-style inheritance online, names each index it builds on a shadow column `_morm_new_<name>`, and after every `ALTER COLUMN ... TYPE` morm writes runs one check that compares each index holding a changed column with the definition the target schema builds on scratch, and recreates each that differs, in the same transaction under a one-transaction form. When it must rebuild an index a foreign key references, it drops and adds back that foreign key around the rebuild, in the same transaction under a one-transaction form. Step 39 changes an inherited column only through its top parent, in one `ALTER`, and refuses, naming them, a change to a child's or a partition's inherited column alone and one that would reach a child or a partition no model declares. Before its online swap, step 39 runs one `GROUP BY` for each unique index holding a swapped column, built from the shadow index's keys and predicate read on scratch, over a subquery that gives the shadow column the value the copy gives it, and refuses values that would merge, at `migrate` and `rollback` preflight. When the migration creates the new type, preflight runs it in a transaction of its own that creates the type, runs the check and always rolls back, so a merge leaves nothing behind and no migration `failed`. Step 14's `Error::Unique` maps a unique index named `_morm_new_<name>` to the field of `<name>`. Step 38 retires columns and types. Step 53 finds dependents, step 59 refreshes functions, and step 54 handles domains and composite types in the one-transaction form.
>
> Measured on Postgres 18.6 and 17.11 with 2 million rows, under readers on a view and a materialized view and 2 writers: a cutover that rebuilt two materialized views took 1.1 to 1.2 s, with every read and write waiting on it. Built beside the old ones in about 1.2 s, the same cutover took about 2 ms, the longest read and write took 2 ms, and nothing failed.
>
> Step 39's route also fits this step's indexes and CHECKs. Tested on Postgres 18.6 and 17.11 on a column with the same name as its enum type: a partial index, a unique partial index, an expression index and CHECK constraints, with casts to the type and `'status'` in a string, were read through `pg_get_indexdef` and `pg_get_constraintdef` after renaming the column and the type on scratch, built on live, and each matched the models exactly after cutover. A materialized view with `USING` between two tables swapped together read the shadow columns of both.
>
> Step 39 builds how a cutover gives way, and this cutover follows it. By default a migration never kills a live app transaction. Each attempt runs with `lock_timeout` set to `[migrations] cutover_lock_timeout`, default `"50ms"`, and one that gets `55P03` or `40P01` changes nothing, waits `cutover_pause`, default `"250ms"`, and tries again, up to `cutover_attempts`, default `600`. Preflight reads the server's `deadlock_timeout`, and each lock waits `min(cutover_lock_timeout, deadlock_timeout / (2 × locks))`, so a whole attempt stays under half of it, and the output says when that's shorter than `cutover_lock_timeout`. After the last attempt the step stops as `failed` with exit code `2` and nothing changed, and `migrate --resume` starts it again after rebuilding any materialized view built beside the old one. `--terminate-blockers` has a second connection call `pg_terminate_backend` on what `pg_blocking_pids` names during an attempt, and it lists each one in `_morm.history`.
>
> Under nonstop traffic an app transaction was killed on all 20 cutovers with no short lock timeout, in two shapes: a transaction that touches a table and then reads the view above it, and this form's two-table cutover against a reader joining them in the opposite order. A 50 ms lock timeout killed nothing, and the cutover could starve and give up.
>
> `down.sql` is always the one-transaction form.

### Migrations / Managed enums / Online swap

- **R-1046** **Online by default.** On an existing table a swap uses this form, and `--fast` uses the one-transaction form. `max_rewrite_mb` doesn't apply here, because nothing is rewritten under a full lock.

- **R-1154** **Indexes after the one-transaction form.** The one-transaction form, under `--fast` and in `down.sql`, runs step 39's index check after its `ALTER COLUMN ... TYPE`: each index on an affected table that holds the column is compared with the definition the target schema builds on scratch, and each that differs is dropped and created again from that definition in the same transaction, under the lock it already holds, with no `CASCADE`. A foreign key that references an index it rebuilds is dropped before the rebuild and added back after it, validated, in the same transaction, with its name, actions, `MATCH` type and deferrability, as step 39 does, because Postgres won't drop an index a foreign key depends on.

- **R-1161** **Inherited columns in the one-transaction form.** The one-transaction form, under `--fast` and in `down.sql`, changes an inherited enum column only through its top parent, in one `ALTER`, under step 39's rule, because on Postgres 18.6 and 17.11 changing an inherited column's type on a child or a partition alone failed with `cannot alter inherited column`. So the change runs only when the migration makes the same swap on the column's top parent and on every child and partition it reaches, each declared by a model, and `migrate` and `rollback` preflight otherwise refuse with exit code `2` before the first step, changing nothing, naming the column, its top parent and every child and partition: a swap of a child's or a partition's inherited column without its top parent, one that would reach a child or a partition no model declares or whose model doesn't make the same swap, and one on a column inherited from more than one parent. Every other statement the form runs on such a table follows step 39's rule for statements Postgres carries to children and partitions in the same way, once, on the top parent: dropping and restoring the column's default and what step 53 drops, and adding and filling the retired column, whose one `UPDATE` there fills every child's and partition's rows. On Postgres 18.6 and 17.11, `DROP DEFAULT`, `SET DEFAULT`, `ADD COLUMN`, and dropping and adding a CHECK on a parent each reached every child and partition, and an `UPDATE` on the parent changed the children's rows.

- **R-1162** **Labels that would merge.** A map that sends two labels to one, such as `pending` to `active` when `pending` is removed, can make two rows equal on a unique index that holds the column, such as `UNIQUE (uid) WHERE status = 'active'`, and step 4's concurrent build would then fail mid-run and leave the index invalid. So the online swap runs step 39's check for values that would merge on each unique index of an affected table that holds the column, with the shadow column given its mapped label as the new type, and refuses with exit code `2` any values that would merge, naming the table, the index, the values and how many rows hold each. The mapped label needs the new type, which the migration creates, so `migrate` and `rollback` preflight run the check under step 39's rule for a type the migration creates: in a transaction of their own that creates the new type, runs the check and always rolls back. A merge is then a preflight refusal with exit code `2` before the first step, with nothing recorded and no migration left `failed`. That transaction takes only `ACCESS SHARE` on the table and its indexes, and on the schema and the old type, so app reads and writes go on while it runs. A swap whose map sends no two labels to one runs no check. A merge written after the check fails step 4's build, which stops as `failed`, and `rollback --failed` drops the shadow objects. On Postgres 18.6 and 17.11, mapping `pending` to `active` found uid `7` twice on that index, inside the transaction that created the new type, and rolling it back left no type behind. Held open after the check, that transaction let an `UPDATE`, an `INSERT`, a `DELETE` and `ALTER TYPE ... ADD VALUE` on the old type through from another session with a `500ms` `lock_timeout`.

- **R-1047** **The steps,** each with its own boundary:

1. `tx`: create the new type under a temporary name.
2. `tx` per table: add the shadow column and a sync trigger on every insert and update, applying the map.
3. `batch` per table: copy by key, with a resumable cursor.
4. `no-tx`: build each index on the shadow column with `CREATE INDEX CONCURRENTLY`, or `CREATE UNIQUE INDEX CONCURRENTLY` for a unique one, named `_morm_new_<name>`, made from the real index's name `<name>` through the 63-byte name function, so step 14 maps a unique violation on it to the field of `<name>`, such as a write of a label the map turns into one another row holds.
5. `tx`, then a separate `tx`: for a `NOT NULL` column add `CHECK (shadow IS NOT NULL) NOT VALID`. For a nullable one add `CHECK (<col> IS NULL OR shadow IS NOT NULL) NOT VALID`, dropped at cutover. Then `VALIDATE`. Any CHECK naming the column goes the same way.
6. `ANALYZE`, because statistics follow the column through a rename.
7. `tx` per materialized view above the column: build it beside the old one on the shadow column, as late as possible, with R-1051's text.
8. `tx`: the cutover, below.

- **R-1048** **The copy walks by key up to a bound,** the highest key read once the sync trigger has committed, and reads that bound and each batch after the trigger has committed. `CREATE TRIGGER` waits for every open write, so any row above the bound was written through the trigger, while a walk that went on until nothing was left chased new inserts for 6,283 batches under nonstop load and finished only when the load stopped, where the bounded copy took 104. A range worked out before the trigger attached misses rows inserted just before it did. `VALIDATE` is the safety net: it fails if any row was missed.

- **R-1147** **The copy's key.** Each table's copy walks by its primary key. A table with none is walked by a unique `NOT NULL` key: a unique constraint or unique index with no predicate and no expression, whose columns are all `NOT NULL`, the one with the fewest columns, then the first by name, with the cursor and the bound on it as on a primary key. A table with neither is refused in this form with exit code `2` before the swap's first step, naming the table and saying `--fast` handles it, because the copy would have nothing to bound it or resume it by.

- **R-1049** **The cutover** is one short transaction across all affected tables, and it gives way to live transactions under step 39's rule, with the same settings and the same `--terminate-blockers`, because a waiting lock holds up new readers behind it, and a wait past `deadlock_timeout` lets Postgres kill a transaction. If it can't get in, it stops with nothing changed, and `--resume` carries on from there. It takes each carried view's lock with its own `DROP VIEW`, from the outside in, dropping anything carried above a view before that view, then locks the tables in sorted order and walks `pg_depend` again, because a reader locks the view first, locking the table first deadlocked every time, and `LOCK TABLE` on a view takes every table under it at once. Sorted order is each table that a foreign key from another affected table references, in name order, then the rest in name order, as step 60's cutover takes the key table first, because readers, and writers going from a parent to its children, lock the parent first, and a cutover that locked the referencing tables first got in on none of 176 attempts under nonstop traffic. It drops the sync trigger, the old indexes and the rest of step 53's dependents, apart from materialized views, renames the old column to a retired column with `NOT NULL` and its default removed, and renames the shadow column to the real name. It sets `NOT NULL` from the validated check, for a column that had it, renames each `_morm_new_<name>` index to `<name>`, re-attaches unique constraints with `ADD CONSTRAINT ... USING INDEX`, and copies the column's comment and grants. It retires the old type, renaming each of its labels to `_morm_retired_<label>` as step 38 retires an enum type, so code still compiled against it fails with `22P02` naming it instead of running on the old order, gives the new type the real name and restores defaults. It swaps each materialized view by rename, under step 39's rules, retiring the old copy, because rebuilding one here would run its query under the lock and break a cutover of milliseconds. Then it recreates the dependents, copies the owner, comment and grants, and refreshes functions. Owner decision SA.

- **R-1050** **Old values stay.** The retired column holds every old value and keeps the retired type alive until `purge`, which drops any retired materialized view, then the column, then the type. Its rows read as `_morm_retired_<label>`, because the cutover renames the retired type's labels, and down and rollback map each back to its recorded label. So a map's data effect here is `retires`, and down restores a value only where the row still holds what it was mapped to. Owner decision SA.

- **R-1051** **Text on the shadow column.** A partial index, an expression index, a CHECK or a materialized view that names the column takes its text from Postgres by step 39's route. On its throwaway scratch, the new column, the new type and each new object are renamed to their temporary names, and morm reads `pg_get_indexdef`, `pg_get_constraintdef` or `pg_get_viewdef`. So a cast reads the temporary type's name with no text replaced, even when the column and its type share a name. The scratch proof confirms the result: after cutover, each definition must match the one built from the models, and a view whose text differs is checked for the same meaning, as step 39 says.

- **R-1052** **Refused in this form, allowed with `--fast`,** naming the cause: a partitioned table or a partition, because concurrent indexes don't work on the parent and Postgres can't add a column to a partition; a table in old-style inheritance, as a parent or as a child, naming its parent or children, because `ADD COLUMN` on a parent adds the column to every child, `ALTER TABLE ONLY` can't stop that, and an inherited column's type can't change on a child alone; enum columns in a primary key or foreign key, because every referencing column would have to swap with the key, and step 60's online form for a referenced key covers only a change within one of the type families step 41's `check_schema` accepts, which an enum swap isn't; stored generated columns that read the column, because recreating them rewrites under lock; columns of a domain or composite type; exclusion constraints and extended statistics on the column; and a view or materialized view that would still read the retired column once recreated, such as `SELECT *`. `migrate` and `rollback` preflight check the live database for partitions and inheritance, and the cutover reads `pg_inherits` again under its lock and stops with nothing changed if a table has gained a parent, a child or a partition since. With `--fast`, a partitioned or inherited table changes as R-1161 says.

- **R-1053** **Recovery.** Each step has a precondition, so `--resume` continues, the copy resumes from its cursor, and failed concurrent indexes are rebuilt. `rollback --failed` drops the shadow objects and leaves the old column and type in place.

- **R-1054** **Column position.** The real column moves to the end of the table. Position isn't compared, and morm's own queries name columns, but a raw `SELECT *` read by position changes, so `--plan` says so.
