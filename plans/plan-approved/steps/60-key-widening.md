# Step 60: Online widening of a referenced key

- **Phase:** Migrations
- **Depends on:** 52
- **Can run beside:** 08, 09, 19, 20, 21, 22, 23, 24, 25, 26, 27, 42, 43, 44, 45, 46, 47, 48
- **Crates:** `morm-migrate`
- **PR approval:** CI and an independent review

Read `../rules.md`, `../contracts.md` and, once it exists, `../proofs.md` first. Everything needed for this step is in those files and this one.

## Goal

Change the type of a key that foreign keys reference, such as an `integer` primary key to `bigint`, on live tables with no long lock, together with every column that references it and its identity sequence.

## Deliverables

- The group op over the key, every referencing column and the identity or owned sequence, its steps with their boundaries, the shadow unique indexes and checks, the new foreign keys, the cutover, the sequence carried with its options and position, the refusals with their evidence, `--fast`'s refusal of an undeclared foreign key and `max_rewrite_mb` per table, the inverse for `rollback` and `revert` with its range check, and recovery at each boundary

## End-to-end check

On Postgres 15–18, an `integer` identity primary key referenced by two tables widens to `bigint` under live readers and writers, cascading deletes included, with a cutover of milliseconds, no failed app transaction and no lost write, and ends on the catalog a fresh build gives. It goes back down online and up again, and the process killed at every step still reaches the right state.

### Migrations / Online widening of a referenced key

**R-1121** **What changes together.** A type change on a column that a foreign key references, where the table has to be rewritten and the old and new types are in the same one of the type families step 41's `check_schema` accepts, runs online by default in this form, in either direction, such as an `integer` primary key becoming `bigint` or going back. The group is every column of the changed key, plus every column that references it, followed transitively: a referencing column that is itself referenced brings its own referencing columns in. The group also includes the identity or owned sequence, every index and constraint on those columns, and the views and materialized views over them, carried as step 39 carries them. A composite key changes only the columns whose type changes, and keeps its other columns in each index and foreign key. A self-referencing table gets a shadow column for the key and one for the referencing column, with one sync trigger. Step 06's typed foreign keys make the models change every referencing column with the key, so the diff shows the whole group, and the planner makes it one op. A widening that needs no rewrite, such as a longer `varchar` or a higher precision on `numeric(p,0)`, stays step 39's change in place, and a change across families, such as `integer` to `uuid`, keeps step 39's refusal on a live table, with `--fast`.

**R-1122** **The steps,** each with its own boundary, and each brief lock taken under `lock_timeout` with retries, as step 33 says:

1. `tx` per table, the key table first: add a shadow column for each changed column, and one sync trigger, `BEFORE INSERT OR UPDATE`, that copies each old column into its shadow. `ADD COLUMN` takes `ACCESS EXCLUSIVE` and `CREATE TRIGGER` takes `SHARE ROW EXCLUSIVE`, each for under a millisecond.
2. `batch` per table: copy by the table's own primary key, up to its bound, the highest key read once that table's trigger has committed, as step 52's copy does, with the cursor in `_morm.steps`.
3. `no-tx`: `CREATE UNIQUE INDEX CONCURRENTLY` for each primary key or unique index that holds a changed column, and `CREATE INDEX CONCURRENTLY` for every other index that holds one, each with the shadow column in place of the old one, so a composite key keeps its other columns.
4. `tx`, then a separate `tx`: add a `CHECK ... NOT VALID` on each shadow column, then `VALIDATE` it. For a `NOT NULL` old column the check is `(new IS NOT NULL AND new = old)`, and for a nullable one it's `(new IS NOT DISTINCT FROM old)`. Any other CHECK naming a changed column is added on its shadow column `NOT VALID` and validated the same way. `VALIDATE` takes `SHARE UPDATE EXCLUSIVE`, so writes carry on.
5. `tx`, then a separate `tx`, for each foreign key that references a changed column: lock the referenced table `SHARE ROW EXCLUSIVE`, then add the new foreign key on the shadow columns, `REFERENCES` the referenced table's shadow columns, with the same actions, `MATCH` type and deferrability, `NOT VALID`. Then `VALIDATE` it, which takes `SHARE UPDATE EXCLUSIVE` on the referencing table and `ROW SHARE` on the referenced one, so writes carry on.
6. `no-tx`: `ANALYZE` the shadow columns.
7. `tx` per materialized view above the group: build it beside the old one, as late as possible, as step 39 does.
8. `tx`: the cutover, as R-1123 says.

Each index and CHECK on a shadow column takes its text from Postgres, by the route steps 39 and 52 use. Step 4's check proves two things in one scan: every row was copied, and with the same value. It also lets Postgres skip the scan when the cutover sets `NOT NULL` or adds the primary key, which `CHECK (new = old)` alone doesn't. Step 5 waits for every copy and for step 3, because a key that isn't copied yet would fail the new foreign key's checks on app writes. The new foreign key references the shadow columns' unique index before that index becomes the primary key, which Postgres allows, and the cutover turns that same index into the key, so the foreign key stays tied to it. Step 5 takes the referenced table's lock before the referencing table's, because the other order waited on app transactions for hundreds of attempts.

**R-1123** **The cutover** is one short transaction across every table in the group, and it gives way to live transactions under step 39's rule, with the same settings, the same `--terminate-blockers` and the same `--resume`. In order:

1. Take each carried view's lock with its own `DROP VIEW`, from the outside in, as step 39 does. Then lock the tables `ACCESS EXCLUSIVE`: the key table first, then the referencing tables in name order. Readers, and writers going from a parent to its children, lock the key table first, and under nonstop traffic a cutover that locked the referencing tables first got in on none of 176 attempts.
2. Walk the group again under the lock, reading `pg_constraint` for every foreign key that references a changed column. Anything new stops the cutover with nothing changed.
3. Take the sequence's lock with a same-value `ALTER SEQUENCE ... INCREMENT BY <current>`, because `LOCK TABLE` refuses a sequence, then read `last_value` and `is_called`.
4. Drop the sync triggers and the old foreign keys.
5. On each table: drop the identity, which drops its sequence, the old primary key or unique constraints and the other old indexes on the changed columns. Retire each old column as step 38 does, dropping its `NOT NULL` and default and renaming it to its retired name. Rename each shadow column to the real name, then `SET NOT NULL` where the old column had it, which the validated check proves with no scan, and set the old column's default. Re-attach the primary key with `ADD CONSTRAINT <name> PRIMARY KEY USING INDEX` and each unique constraint with `ADD CONSTRAINT <name> UNIQUE USING INDEX`, then carry the sequence as R-1124 says.
6. Drop the checks, and rename the new foreign keys and indexes to the real names. Move a `REPLICA IDENTITY USING INDEX` on a replaced index to its new index, because dropping the old one leaves the table with no replica identity index.
7. Recreate the carried views and swap the materialized views, as step 39 does, refresh functions, as step 37 does, copy column comments and grants, and write the step as `done` in `_morm.steps`, all in this same transaction.

It holds `ACCESS EXCLUSIVE` on every table in the group, `SHARE ROW EXCLUSIVE` and then `ACCESS EXCLUSIVE` on the sequence, and each carried view's lock. Everything inside it is a catalog change, with no scan and no rewrite.

**R-1124** **The sequence.** An identity key keeps its sequence's name and position. Once the shadow column has the real name, the cutover runs `ADD GENERATED ALWAYS` or `BY DEFAULT AS IDENTITY (SEQUENCE NAME <old name>, <old options>)`, the same kind as before, with the old start, increment, cache and cycle, and with a minimum or maximum the old sequence set past its type's default. A minimum or maximum that was the old type's default becomes the new type's, so an `integer` identity widened to `bigint` can reach `bigint`'s maximum. Then `setval` sets the `last_value` and `is_called` read under the lock. The new sequence doesn't keep the old one's owner, grants or comment, so the cutover copies them. A session open across the cutover gets `55000` from `currval` and `lastval` on that sequence until its next `nextval`, because the sequence is new under the same name, and the README says so. A `serial` key, with an owned sequence and no identity, keeps the same sequence, with its OID and position: `ALTER SEQUENCE ... AS <new type>` changes its type, moving a maximum that was the old type's default to the new type's and keeping one set explicitly, and `OWNED BY` and `SET DEFAULT` move it to the new column.

**R-1125** **Refused online, with the evidence.** Each of these is refused with exit code `2` before the op's first step, changing nothing. `makemigrations` checks what scratch shows, `migrate` and `rollback` preflight check the live database, and the cutover's second walk checks again under its lock, where anything new stops it with nothing changed.

1. A foreign key on a changed column from a table no model declares, or one the models don't declare. The evidence is the referencing table, the constraint's name and `pg_get_constraintdef`, its deferrability and the table's estimated rows. morm can't change a column it doesn't manage, and if that column stayed narrow, its foreign key would fail once a value passed the old limit. It's a refusal, not a decision, because no answer would make the change safe. The fix is to declare the table in the models, or to drop that foreign key first. `--fast` refuses it too, as R-1126 says. The cutover's `DROP CONSTRAINT`, which never uses `CASCADE`, is the last check, because Postgres refuses to drop a key a foreign key needs, with `2BP01`.
2. A partitioned table or a partition in the group, because `ADD CONSTRAINT ... USING INDEX` isn't supported on a partitioned table, Postgres 15 to 17 can't add a `NOT VALID` foreign key from one, and Postgres can't add a column to a partition. `--fast` handles it.
3. A table in the group that's in any publication, or is a subscription's target, naming the publication or subscription, because the shadow columns and the cutover each stop replication with `missing replicated column`. `--fast` handles it, and the subscriber keeps working.
4. What step 52 refuses for an enum swap, on a column in the group: exclusion constraints and extended statistics, stored generated columns that read one, a domain or composite type, and a view or materialized view that would still read the retired column once recreated, such as `SELECT *`. Each of these needs a rewrite, or a definition morm can't move with no lock. `--fast` handles them.
5. Anything step 39 refuses above a swapped column, such as a view no model declares.

An enum key keeps step 52's refusal, because an enum swap isn't a change within one family.

**R-1126** **`--fast` on a referenced key.** With `--fast`, a type change on a key that foreign keys reference changes every column in its group with `ALTER COLUMN ... TYPE` in one transaction, as step 39 does. It refuses a foreign key from a table no model declares, or one the models don't declare, with exit code `2` and R-1125's evidence, because Postgres would change the key and leave that column as it was, so its foreign key would fail once a value passed the old limit. Step 51's `max_rewrite_mb` applies to each table in the group: preflight refuses with exit code `2` when any one of them is bigger, for `migrate` and `rollback`, naming that table and its size.

**R-1127** **The inverse, for `rollback` and `revert`,** runs this form in the other direction, online, and so does a migration that narrows a referenced key within one family. The retired columns become the shadow columns again: a sync trigger from the new columns to the old, a full copy, because rows changed since the cutover need it too, the indexes, checks and foreign keys, then a cutover that renames back and moves the identity back to a sequence of the old type. So the old columns come back at their original positions. Once `purge` has dropped them, it adds new shadow columns, as the up does. Preflight of `migrate` and `rollback` refuses with exit code `2` before the first step when any value in a changed column, or the sequence's position, doesn't fit the old type, naming the table, the column and the value, and the cutover reads the sequence again under its lock and stops with nothing changed if its position no longer fits. Nothing can make that change safe once a value doesn't fit, so it's a refusal, not a decision. From the first step, an app write the old type can't hold, such as an identity value past `2^31 - 1`, gets `22003` from the sync trigger. That's step 41's rule for a narrowing, the database's error for that write, applied from the first step rather than from the cutover.

**R-1128** **Recovery.** Each step has a precondition, so `--resume` carries on from the boundary where it stopped. A rerun of steps 1 and 3 to 5 reads the catalog first and does only what's missing. A concurrent index left `indisvalid = false` is dropped and built again, a constraint left `NOT VALID` is validated again, and the copy resumes from its cursor. The cutover is one transaction, so a process killed inside it changes nothing, and a rerun starts it again. `rollback --failed` drops the shadow objects, which are the sync triggers, shadow columns, new indexes, checks and foreign keys, and leaves the old columns, keys and sequence in place.
