## Goal

Diff two schemas into typed operations with inverses.

## Deliverables

- Diff, `Op` with inverse, lock, transaction and data properties, topological planning, ops for tables, columns, constraints, indexes, schemas and extensions, and identity added to a column with rows with its sequence set past the highest value, and to a column that already has a default, such as `serial`, in one op that carries the old sequence's position and name, with its inverse and its preflight refusal

## End-to-end check

For a set of schema pairs, the diff produces ops whose forward and inverse SQL move a real database between both states exactly.

### Migrations / Typed operations

**R-0551** The diff yields `Op` values, not SQL strings. Each declares:

| ID | Property | Use |
|---|---|---|
| R-0552 | forward SQL | up step |
| R-0553 | inverse op | down exists **by construction** |
| R-0554 | lock level, rewrite, scan | `lint`, `--plan`, ordering |
| R-0555 | transaction mode | `tx`, `no-tx`, `batch` |
| R-0556 | data effect | `none`, `retires`, `lossy`, `irreversible` |
| R-0557 | precondition | catalog check that makes re-running safe |

**R-0558** The planner topologically sorts ops (foreign key cycles are resolved by adding constraints last), takes table locks in a consistent order to avoid deadlocks, and groups ops into **steps**, each with its own transaction boundary.

**R-1132** **Adding identity to a column with rows.** Postgres starts a new identity's sequence at its start value whatever the column holds: on Postgres 18.6 and 17.11, after `ADD GENERATED BY DEFAULT AS IDENTITY` on a column holding 1 and 2, the next insert failed with `duplicate key value violates unique constraint`, on key 1. So the op that adds identity to an existing column also runs `setval` on the new sequence, found through `pg_depend` as the one the identity owns, to the column's highest value, in the same transaction, under the lock `ADD GENERATED` takes, so the next insert gets the value after it. On an empty table the sequence stays at its start.

**R-1199** **Adding identity to a column that already has a default.** Postgres refuses `ADD GENERATED ... AS IDENTITY` on a column with a default, such as the `nextval` one `serial` and `bigserial` give, with `column "id" of relation "t" already has a default value`. Dropping the default first isn't enough: the old sequence stays, owned by the column, so the identity's sequence takes another name and `pg_get_serial_sequence` still returns the old one. On Postgres 18.6 and 17.11, after `DROP DEFAULT` and `ADD GENERATED BY DEFAULT AS IDENTITY` on a `serial` column holding 1 and 2, `pg_get_serial_sequence` gave `naive_id_seq`, the identity's sequence was `naive_id_seq1`, a `setval` through `pg_get_serial_sequence` left the identity's at its start, and the next insert failed with `23505` on key 1. So adding identity to a column that has a default is one op, in one transaction, under the table's `ACCESS EXCLUSIVE` lock, taken first. It takes the lock of each sequence the default calls, found through `pg_depend` from the default's `pg_attrdef` row, with a same-value `ALTER SEQUENCE ... INCREMENT BY`, because `LOCK TABLE` refuses a sequence, and reads each one's next value from `last_value`, `is_called` and its increment. It drops the default. It drops the sequence the column owns, found through `pg_depend` with `deptype = 'a'`, as `serial` makes one, after reading its privileges and comment. It adds the identity with `SEQUENCE NAME` set to that sequence's schema-qualified name, so the identity's sequence takes its name, even one that isn't `<table>_<column>_seq`, such as after a table rename. It finds the identity's own sequence through `pg_depend` with `deptype = 'i'`, never through `pg_get_serial_sequence`, and sets it with `setval(..., false)` so that its next value is the greater of each old sequence's next value and the value after the column's highest, so no key the old sequence gave is given again, even one whose row was deleted. It gives the identity's sequence the old one's privileges and comment, so a role granted `SELECT` and `UPDATE` on it, as `.explicit_ids()` needs, keeps them. A default that calls no sequence, such as `0`, is dropped the same way, with only the column's highest value to pass. A sequence the default calls that the column doesn't own, such as a `pg_sequence!` one, has its position carried and is left as it is, and the identity's sequence takes the name Postgres gives it. The inverse is one op in one transaction too. It reads the next value, owner, privileges and comment of the identity's sequence the same way, drops the identity, which drops its sequence, rebuilds the old sequence under its name from the definition the schema before holds, with its type, start, increment, minimum, maximum, cache and cycle, `OWNED BY` the column, with that owner, those privileges and that comment, sets it so that its next value is the greater of the identity's next value and the value after the column's highest, and sets the old default back as `pg_get_expr` printed it. A sequence the old default calls that the column doesn't own is moved forward to that value only when it's behind it, and never back. A diff that takes identity off a column and gives it back a default calling a sequence the column owns, such as a model that goes back to `serial`, gives that inverse, written as a forward op. On a partitioned table, Postgres carries the `DROP DEFAULT`, the identity and the restored default to every partition, so the op runs on the parent under step 39's rule for such statements. On Postgres 18.6 and 17.11, on a `serial` key holding 1 to 3 after rows 4 and 5 were deleted, with `SELECT` and `UPDATE` on `t_id_seq` granted to a role and a comment on it, the op under `BY DEFAULT` left one sequence, `t_id_seq`, the identity's, with the grant and the comment, `pg_get_serial_sequence` returned it, and the next insert got 6. The inverse left `t_id_seq` `OWNED BY` the column, with `nextval('t_id_seq'::regclass)` as the default, the grant and the comment, the next insert got 7, and the op run again gave 8. A `bigserial` key on a table renamed after its sequence was made kept the sequence's name, `t2old_id_seq`, both ways, under `GENERATED ALWAYS`. An unused sequence at `START 1000` on an empty table gave 1000, and 1001 after the inverse. `DEFAULT 0` came back as `0`. A sequence the column didn't own, whose last value 51 the table held, gave the identity 52, and after it was set back to 10 the inverse moved it to 53. On a partitioned table, a partition made by `PARTITION OF` and one attached with its own default on the parent's sequence both lost their default and read the parent's identity, inserts through a partition and through the parent got the carried values, and the inverse put the default back on all three.

**R-1200** **A sequence something else uses.** Postgres drops a sequence only when nothing else depends on it, and refuses otherwise with `cannot drop sequence ... because other objects depend on it`: on Postgres 18.6 and 17.11 it did for another table's default calling the sequence, and so did `DROP IDENTITY` for a default and for a view on the identity's sequence. A view and a `BEGIN ATOMIC` function calling `nextval` on a sequence each showed in `pg_depend` on it. An inheritance child's default on the parent's sequence is dropped by the parent's `DROP DEFAULT`, while the identity stays on the parent alone, so the child's inserts failed with `23502` on both versions. So R-1199's op adds a preflight check that refuses it with exit code `2`, changing nothing, when anything in `pg_depend` depends on the sequence the column owns other than that column's default on its table and on the table's partitions, such as another column's default, an inheritance child's default, a view or a function. It names the sequence, the column and each dependent, and says to keep the default, or to give each dependent a sequence or default of its own in an earlier migration. The same check refuses R-1199's inverse, and any other op that drops identity, when anything other than its column depends on the identity's sequence. `makemigrations` refuses the same way when scratch shows such a dependent, and `migrate` and `rollback` preflight check the live database, because scratch can't see what no model declares.

### Managed enums

- **R-0987** **Step boundaries.** An op can declare that its step ends after it, so the planner puts whatever follows in a new transaction. Step 51 needs this for `ALTER TYPE ... ADD VALUE`, because nothing can use a new value until the transaction that added it commits.

**R-1175** **Children and partitions in the diff.** The diff compares the reader's `Schema` IR, where what a child or a partition holds from its parent sits only on the parent, as step 29 says. So a parent's CHECK, foreign key, primary key, unique key or index is one object and yields one op, on the parent, never one on each child or partition, and what a child's or a partition's model declares is its own, compared as on any table. A partition's `pk` that matches the key it holds from its parent, under step 29's rule for a partition's key, is that key, the parent's, so on a live tree it yields no op of its own, and a partition whose model leaves `pk` out compares the same. Between two sets of models, where every table is plain, adding or removing a partition's `pk` is an op on that table like any other, and step 39 says how it runs on a live partition. A declared `pk` on the parent's key columns that the partition holds under another name, such as `p3_other` or `p5_pkey1`, doesn't match it, under that rule, so on a live tree the diff gives one difference on that partition, between the key under the name it has and the `pk` its model declares, never the parent's key and a second one, and that's the difference `verify` and the fingerprint gates report as drift. Identity a partition's column holds from its parent is the parent's, under step 29's rule for a partition's identity, so a change to it is one op, on the parent, and none on a partition. An op on a parent that Postgres carries to children and partitions runs under step 39's rule for such statements.
