### Migrations / Typed operations

**R-0551** The diff yields `Op` values, not SQL strings. Each declares:

| ID | Property | Use |
|---|---|---|
| R-0552 | forward SQL | up step |
| R-0553 | inverse op | down exists **by construction** |
| R-0554 | lock level, rewrite, scan | `lint`, `--plan`, ordering |
| R-0555 | transaction mode | `tx`, `no-tx`, `batch` |
| R-0556 | data effect | `none`, `retires`, `lossy`, `irreversible` |
| R-0557 | precondition | catalog check that makes re-running safe |

**R-0558** The planner topologically sorts ops (foreign key cycles are resolved by adding constraints last), takes table locks in a consistent order to avoid deadlocks, and groups ops into **steps**, each with its own transaction boundary.

**R-1132** **Adding identity to a column with rows.** Postgres starts a new identity's sequence at its start value whatever the column holds: on Postgres 18.6 and 17.11, after `ADD GENERATED BY DEFAULT AS IDENTITY` on a column holding 1 and 2, the next insert failed with `duplicate key value violates unique constraint`, on key 1. So the op that adds identity to an existing column also runs `setval` on the new sequence to the column's highest value, in the same transaction, under the lock `ADD GENERATED` takes, so the next insert gets the value after it. On an empty table the sequence stays at its start.

### Managed enums

- **R-0987** **Step boundaries.** An op can declare that its step ends after it, so the planner puts whatever follows in a new transaction. Step 51 needs this for `ALTER TYPE ... ADD VALUE`, because nothing can use a new value until the transaction that added it commits.

**R-1175** **Children and partitions in the diff.** The diff compares the reader's `Schema` IR, where what a child or a partition holds from its parent sits only on the parent, as step 29 says. So a parent's CHECK, foreign key, primary key, unique key or index is one object and yields one op, on the parent, never one on each child or partition, and what a child's or a partition's model declares is its own, compared as on any table. A partition's `pk` that matches the key it holds from its parent, under step 29's rule for a partition's key, is that key, the parent's, so on a live tree it yields no op of its own, and a partition whose model leaves `pk` out compares the same. Between two sets of models, where every table is plain, adding or removing a partition's `pk` is an op on that table like any other, and step 39 says how it runs on a live partition. An op on a parent that Postgres carries to children and partitions runs under step 39's rule for such statements.
