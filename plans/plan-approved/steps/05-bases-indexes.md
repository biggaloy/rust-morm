### Models / Bases

**R-0122** Defaults are the best choice for new tables. Anything else is declared explicitly, so models can match any existing table.

| ID | Base | Adds |
|---|---|---|
| R-0123 | `base = "common"` | `id bigint GENERATED BY DEFAULT AS IDENTITY` PK, `created_at`, `updated_at` |
| R-0124 | `base = "common_uuid"` | `id uuid` PK (UUIDv7), `created_at`, `updated_at` |
| R-0125 | `base = "pk_only"` | `id bigint GENERATED BY DEFAULT AS IDENTITY` PK only |
| R-0126 | `base = "pk_uuid_only"` | `id uuid` PK (UUIDv7) only |
| R-0127 | `base = "bare"` (or omitted) | Nothing. You define every column and your own PK: single, composite, or none |
| R-0128 | `base = MyBase` | Your own base, below |

**R-0129** `BY DEFAULT` allows explicit ids where needed, such as data imports, through `.explicit_ids()` (section 8). `serial` and `bigserial` remain available through `sql`, for matching existing tables.

**R-0130** PK-based helpers come through a `HasPk` trait, so a model without a PK simply doesn't have them: a compile error, not a runtime failure. To match an existing table, write for example `#[col(pk, sql = "serial")] id: i32`, with explicit index and constraint names.

**R-0131** **Custom bases** are ordinary structs:

**R-0132**

```rust
#[morm::base(base = "common_uuid")]             // a base can extend another base
pub struct Tenanted {
    #[col(fk = Tenant::id, index)]
    pub tenant_id: Uuid,
    #[col(groups = "staff")]
    pub created_by: Option<Uuid>,
}

#[model(table = "invoices", base = Tenanted)]
pub struct Invoice { pub total: Decimal }       // invoice.tenant_id is a plain field
```

- **R-0133** The fields become real fields of the model, with every `#[col]` option, so `invoice.id` works and there is no nested struct or runtime cost.
- **R-0134** A macro can't read another struct's fields, so `#[morm::base]` generates a `macro_rules!` macro holding its fields, and `#[model]` calls it to get them. Bases work across crates, and they carry indexes and `ordering`.
- **R-0135** A field defined in both the base and the model is a compile error.
- **R-0136** The built-in bases use this same mechanism.
- **R-0137** `flatten` remains for a nested reusable struct, as in `order.shipping.city`.

### Models / Struct options (`#[model(...)]`)

| ID | Option | Meaning |
|---|---|---|
| R-0140 | `schema` | Postgres schema, as in `schema = "billing"`. Generated SQL then uses `"billing"."invoices"`, and migrations create the schema. Omitted, the table resolves through the pinned `search_path` |
| R-0141 | `base` | `"common"`, `"common_uuid"`, `"pk_only"`, `"pk_uuid_only"`, `"bare"`, or a `#[morm::base]` type |
| R-0144 | `indexes(...)` | list of indexes (section 7) |
| R-0145 | `extensions` | Postgres extensions the model needs |
| R-0151 | `checks(...)` | table-level CHECK constraints, tracked by migrations: `checks(name = "ends_after_starts", sql = "ends_at > starts_at")` |
| R-0152 | `storage` | table storage settings, tracked by migrations: `storage = "fillfactor=90"` |

### Models / Field options (`#[col(...)]`)

| ID | Option | Meaning |
|---|---|---|
| R-0157 | `unique`, `index`, `index(using = ..., ...)` | single-column shortcuts; `index = "hash,btree"` makes two. Rules in section 7 |
| R-0158 | `deferrable` | with `unique` or `fk`, a constraint checked at commit; `deferrable = "initially deferred"` sets the start state |
| R-0160 | `fk = Type::field`, `on_delete`, `on_update` | typed foreign key, checked at compile time; actions: `cascade`, `restrict`, `set null`, `set default`, `no action` |

### Models / Plain structs, no `save`

**R-0202** **Doc comments are schema comments.** `///` on a model or field becomes `COMMENT ON TABLE` or `COMMENT ON COLUMN`, tracked by migrations, so the schema explains itself in `psql` and database tools. Comments reach only `morm-mgr`, except where `json_schema()` uses them.

### Indexes

**R-0285** Declared in `indexes(...)` on the struct, or with field shortcuts.

| ID | Option | Meaning | Default |
|---|---|---|---|
| R-0286 | `cols` | columns, each with optional `ASC`/`DESC`, `NULLS FIRST`/`NULLS LAST` | required unless `expr` |
| R-0287 | `expr` | expression index, e.g. `lower(email)` | none |
| R-0288 | `unique` | unique index | off |
| R-0289 | `deferrable` | with `unique`, a constraint checked at commit. It can't be an `upsert` target | off |
| R-0290 | `nulls_not_distinct` | with `unique`, treat NULLs as equal, so only one NULL is allowed | off |
| R-0291 | `using` | `btree`, `hash`, `gin`, `gist`, `brin`, `spgist` | `btree` |
| R-0292 | `ops` | operator class, e.g. `jsonb_path_ops`, `gin_trgm_ops` | none |
| R-0293 | `filter` | `WHERE` clause (partial index) | none |
| R-0294 | `include` | extra non-key columns (covering index) | none |
| R-0295 | `name` | explicit name | generated |

**R-0296**

```rust
indexes(
    index(cols = "category_id, created_at"),
    index(cols = "price DESC NULLS LAST, id"),
    index(cols = "sku", using = "hash"),
    index(cols = "attrs", using = "gin", ops = "jsonb_path_ops"),
    index(cols = "created_at", using = "brin"),
    index(cols = "email", unique, filter = "deleted_at IS NULL"),
    index(expr = "lower(email)", unique),
    index(cols = "vendor_id", include = "price, stock"),
    index(name = "products_search_idx", cols = "name, sku"),
)
```

**R-0297** Rules:

- **R-0298** **`unique` gives both a constraint and an index.** Postgres backs a UNIQUE constraint with a unique index of the same name, so morm creates one object that serves as both. This applies to `#[col(unique)]` and to `index(cols = "a, b", unique)`, and `include` is kept on the constraint. A unique index with `filter` or `expr` stays an index only, because constraints can't be partial or use expressions.
- **R-0299** **Duplicates are compile errors.** The macro sees every declaration, so it rejects a second btree index with the same columns in the same order, as `#[col(unique, index)]`, `#[col(unique)]` plus `index(cols = "email")`, a repeated `indexes(...)` entry, or an index matching the primary key. Inherited base fields are included. Indexes differing in `using`, `ops`, `filter`, `expr` or `include` are allowed, and `lint` reports the ones that look redundant.
- **R-0300** `morm-admin mgr lint` warns about foreign key columns without an index, and redundant indexes such as a hash and a btree on one column, or an index on `a` when one on `a, b` exists.
- **R-0301** On existing tables, migrations build indexes concurrently by default (section 10).

### Indexes / Names

**R-0302** The convention is python-morm's, so models can match its databases without explicit names:

| ID | Object | Name |
|---|---|---|
| R-0303 | Unique on one column | `__UNQ_{table}_{column}__` |
| R-0304 | Unique on several columns | `__UNQ_{table}_{name}__` |
| R-0305 | Index on one column | `__IDX_{table}_{column}_{method}__` |
| R-0306 | Index on several columns | `__IDX_{table}_{name}_{method}__` |
| R-0307 | Foreign key | `__FK_{table}_{column}__` |
| R-0308 | Check | `__CHK_{table}_{name}__` (new; python-morm has no convention for it) |

**R-0309** `{name}` is the `name` you give, or the column names joined by `_`. For an `expr` index with no `name`, it's the expression with everything but letters, digits and `_` collapsed to `_`, so `lower(email)` gives `lower_email`. `Product::UK` uses the same `{name}`. A primary key keeps the Postgres name `{table}_pkey`, and an identity column's sequence keeps `{table}_{column}_seq`.

- **R-0310** **63-byte limit:** Postgres silently cuts longer names, so two long names could collide. morm counts bytes, not characters. A longer name is cut and ends in 8 hex characters of its full SHA-256, as `__IDX_{start of name}_{hash}__`, so it stays at 63 bytes, is stable across builds and still shows the table.
- **R-0311** A generated name used twice in one model, for example two partial indexes on one column, is a compile error asking for an explicit `name`.
- **R-0312** An explicit `name` is used as written. Over 63 bytes is a compile error.
- **R-0313** `morm-admin import` keeps existing names, as explicit `name` values where they differ.
