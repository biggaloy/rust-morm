## Goal

Forward-only production, with safe ways to undo and tidy up.

## Deliverables

- `mode` with `--confirm`, `rollback` guards and the emergency override, `revert`, `rehearse`, `squash`

## End-to-end check

A new database refuses `rollback`, `revert` restores retired data through a forward migration, and a squashed chain gives the same schema as the full one.

## Out of scope

- Rolling deploys (step 39)

### Migrations / Production is forward only

**R-0574** Rolling back after new data has been written can fail or lose that data, so production moves forward only. `down.sql` is still proven for every migration, because `revert` and development depend on it.

- **R-0575** **`mode development` must name the database,** as in `mgr mode development --confirm app_staging`, so a command aimed at the wrong URL can't remove the protection.
- **R-0576** **Every database is production until marked otherwise.** The mode is stored in `_morm`, not in an environment variable, so a wrong setting on a host can't turn it off, and a backup restores with it. Forgetting to mark a database leaves it safe.
- **R-0577** `morm-admin mgr mode development` marks a local or staging database, and `mode` shows the current value. Every change goes in `_morm.history`.
- **R-0578** **On a production database,** `rollback` and `rehearse` exit with code `2`. To rehearse on a clone of production, mark the clone first.
- **R-0579** **`morm-admin mgr revert ID`** is the way to undo in production. It creates a new forward migration from that migration's down, runs the full proof on scratch, and needs the same decisions, such as `down_fill`. Retired columns and tables come back with their data, and the chain stays linear, so every database has the same history.
- **R-0581** **Emergency override:** `rollback --production --reason "..."` works but is logged to `_morm.history`, and it still needs `--accept-data-loss` where that applies.

### Migrations / Commands

- **R-0613** `rehearse`: pending up → down → up on a clone or restored backup, with **real data**. The recommended last gate.
- **R-0617** `squash --to ID`: replaces the chain up to `ID` with one baseline generated by replaying it. A database that has applied all of them just continues, and one partway through is refused until it catches up. Run it only when every database has passed `ID`. It refuses while retired objects from those migrations haven't been purged, because their rollback path would be gone.

| ID | Mistake | Caught by |
|---|---|---|
| R-0757 | Rolling back a production database | Refused, exit code `2`, unless marked `development`; `revert` is the forward path |
